# Сайт Sfera и Vault: переход к Vue SSR + Django REST

**Статус:** архитектурное предложение, не начатая миграция.
**Дата:** 28.11.2026.
**Контекст:** сайт `vault-msg.ru` / `vault-msg.tech` уже существует и
обслуживает мессенджер Vault. Sfera — второй продукт, которому нужен
раздел с руководством, загрузками и будущими публичными каналами.

> **Инварианты сервера.** На той же машине работают SSH, nginx, релей
> Vault, приём обратной связи, ЮKassa и выдача чеков. Переезд сайта не
> должен их затрагивать. Обязательные preflight/postflight-проверки —
> `docs/SITE-MIGRATION-RUNBOOK.md`. До них не менять nginx, systemd, DNS,
> certbot и env релея.

---

## 1. Что есть сейчас

Каталог `/home/maksim/vault-site` — статический сайт:

- `index.html` — лендинг Vault с разделами «Как работает», «Функции»,
  «Руководство», «Безопасность», «План развития», «Скачать», «Тарифы»,
  «FAQ»; весь CSS встроен в страницу;
- `pricing.html`, `pay.html` — тарифы и оплата;
- `privacy.html`, `terms.html`, `offer.html`, `pd.html`,
  `requisites.html` — юридические страницы;
- `en/` — английская копия тех же страниц;
- `releases/`, `latest.json`, `latest-en.json` — артефакты и манифесты
  обновлений;
- `store/` — тексты для магазинов приложений.

Развёртывание — `rsync` в `server:sites/vault-msg/ru/` и `/en/`, nginx
отдаёт статику. EN-сайт открывается доменом `vault-msg.tech`, а не путём
`/en/`.

### Чем это плохо для роста

- каждая страница — отдельный HTML с копией CSS и разметки;
- нет общего layout, меню, хлебных крошек и версий документов;
- нет модели контента: цены, релизы, FAQ и юридические тексты
  дублируются вручную;
- нет полноценного руководства: раздел «Руководство» — пять шагов на
  лендинге, а не документация с поиском и версиями;
- RU и EN расходятся; китайский UI Sfera вообще не имеет сайта;
- нельзя отдать страницу публичного канала из проверенной витрины;
- SEO держится на ручных `<title>`/`canonical`; новые страницы легко
  забыть в `sitemap`.

При этом сайт **не является одностраничным приложением**: это набор
статических страниц. «Одностраничность» здесь — не SPA, а отсутствие
контентной модели и общего шаблона. Переход нужен не ради моды, а чтобы
документация, релизы и публичные каналы не превратились в ещё больше
рукописных HTML-файлов.

## 2. Решение

Стандартная структура из двух приложений:

```
sfera-site/
├── backend/                 # Django + Django REST Framework
│   ├── config/              # settings, urls, wsgi, asgi
│   ├── apps/
│   │   ├── content/         # страницы, документы, FAQ, релизы, тарифы
│   │   ├── feedback/        # обращения с сайта
│   │   └── public/          # прокси/кэш витрины публичных каналов
│   ├── requirements.txt
│   └── manage.py
├── frontend/                # Vue 3 + Vite SSR
│   ├── src/
│   │   ├── entry-client.js
│   │   ├── entry-server.js
│   │   ├── router/
│   │   ├── i18n/
│   │   ├── layouts/
│   │   ├── pages/
│   │   └── components/
│   └── vite.config.js
├── content/
│   └── docs/                # markdown-руководство, источник правды
├── deploy/
│   ├── nginx/
│   ├── systemd/
│   └── scripts/
└── README.md
```

- **Django REST** — единственный источник контента и метаданных.
- **Vue 3 + Vite SSR** — публичный фронт: HTML приходит с сервера, затем
  гидрируется. Не SPA-only: поисковик и читатель без JS видят текст.
- **PostgreSQL** — контент, версии, релизы, обращения.
- **gunicorn + nginx** — API; отдельный Node-процесс — SSR; статика — nginx.
- **Markdown в git** — руководство; Django импортирует его management-
  командой, чтобы тексты проходили ревью в PR, а не редактировались
  вслепую в админке.

### Почему не оставить статику

Статика остаётся допустимой для лендинга, но не для документации:
версии, поиск, переводы, хлебные крошки, `sitemap`, публичные каналы и
редиректы быстро превращаются в ручную работу. Django даёт модели и
админку, Vue SSR — общий layout и SEO без потери интерактивности.

### Почему не чистый SPA

Чистый SPA отдаёт пустой `<div id="app">`: поисковики и превью в
мессенджерах видят пустоту. Для документации и юридических страниц это
недопустимо. SSR обязателен.

## 3. Границы продуктов

Один сайт, два продукта, одна структура разделов:

| Раздел | Vault | Sfera |
|---|---|---|
| Лендинг | `/vault` (и `/` как главная) | `/sfera` |
| Документация | `/vault/docs` | `/sfera/docs` |
| Статьи | `/vault/docs/<slug>` | `/sfera/docs/<slug>` |
| Тарифы | `/vault/pricing` | `/sfera` + документы о монетизации |
| Оплата | `/vault/pay` и существующий `/pay` | пока нет платежей |

Старые адреса `/pricing`, `/pay`, `/docs` сохраняются как совместимые
алиасы; канонические адреса — с префиксом продукта. Документы обоих
продуктов лежат в одном `docs`-приложении с полем `product`, поэтому
одинаковые slug (`privacy`) не конфликтуют.

**Vault** — текущие разделы и юридические страницы сохраняют URL.
**Sfera** — новый раздел `/sfera` (RU) и `/sfera` на EN-домене.

Почему не отдельный домен сразу:

- домены `vault-msg.ru` и `vault-msg.tech` уже работают, у них есть
  история и сертификаты;
- раздел `/sfera` можно запустить без DNS-работ и нового бренда;
- если Sfera станет самостоятельным брендом, `sfera.vault-msg.ru` или
  отдельный домен добавляются как второй `server_name` без переписывания
  контента.

Юридические страницы (privacy, terms, offer, pd, requisites) остаются
общими для сайта, но получают поле `product`, чтобы можно было указать
различия Vault и Sfera. Нельзя публиковать политику Vault как политику
Sfera без проверки: у продуктов разные данные и транспорт.

## 4. Модели Django

### `Product`

`slug` (`vault`, `sfera`), `name`, `domain`, `description`, `is_active`.

### `Page`

`product`, `slug`, `locale`, `title`, `subtitle`, `body_markdown`,
`seo_title`, `seo_description`, `og_image`, `updated_at`, `published`.

Для лендингов, «Скачать», «Тарифы», «Безопасность».

### `DocPage`

`product`, `slug`, `parent` (дерево), `order`, `locale`, `title`,
`summary`, `body_markdown`, `version`, `updated_at`, `published`.

Источник — `content/docs/**/*.md`; импорт командой
`python manage.py sync_docs`. В админке документы только для просмотра,
чтобы не появилось две версии правды.

### `FaqItem`

`product`, `locale`, `question`, `answer_markdown`, `order`, `published`.

### `Release`

`product`, `version`, `channel` (`apk`, `aab`, `desktop`, `direct`),
`url`, `sha256`, `size`, `notes`, `published_at`, `is_latest`.

Манифесты `latest.json`/`latest-en.json` генерируются из этой модели, а не
правятся руками.

### `Plan`

`product`, `code`, `locale`, `name`, `price`, `period`, `limits` (JSON),
`features` (JSON), `is_active`.

Цены и лимиты не должны дублироваться в HTML и в приложении.

### `LegalDocument`

`kind` (`privacy`, `terms`, `offer`, `pd`, `requisites`), `locale`,
`version`, `effective_at`, `body_markdown`, `published`.

Версия и дата — обязательны: юридический текст без версии невозможно
сравнить с тем, что было принято пользователем.

### `Feedback`

`name`, `email`, `message`, `product`, `page_url`, `created_at`,
`ip_hash`, `user_agent`, `status`.

Без паролей и ключей. Валидация и антиспам — на сервере, не в Vue.

## 5. API

Версия в пути: `/api/v1/`.

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/api/v1/health` | живость API и БД |
| GET | `/api/v1/products` | список продуктов |
| GET | `/api/v1/pages/{product}/{slug}?lang=ru` | страница |
| GET | `/api/v1/docs/{product}/tree?lang=ru` | дерево руководства |
| GET | `/api/v1/docs/{product}/{slug}?lang=ru&version=` | документ |
| GET | `/api/v1/faq?product=sfera&lang=ru` | FAQ |
| GET | `/api/v1/releases/{product}/latest` | последний релиз |
| GET | `/api/v1/plans?product=sfera&lang=ru` | тарифы |
| GET | `/api/v1/legal/{kind}?lang=ru` | юридический документ |
| POST | `/api/v1/feedback` | обращение |
| GET | `/api/v1/public/channels/{id}` | витрина канала (прокси) |

Правила:

- ответы только JSON, ошибки — `{"error": {"code", "message"}}`;
- `ETag`/`Cache-Control` для публичных GET;
- POST `/feedback` — CSRF, honeypot, лимит по IP, без логирования текста
  в открытом виде;
- никаких ключей, e-mail переписки и внутренних путей в ответах;
- API не доверяет клиенту: продукт, язык и версия проверяются на сервере.

## 6. Vue SSR

### Маршруты

```
/                         Vault, лендинг
/pricing                  тарифы Vault
/pay                      оплата Vault (пока существующий сценарий)
/privacy, /terms, ...     юридические страницы Vault
/sfera                    лендинг Sfera
/sfera/download           сборки Sfera
/sfera/docs               оглавление руководства
/sfera/docs/{slug}        страница руководства
/sfera/channels/{id}      публичный канал (после готовности витрины)
```

EN-домен `vault-msg.tech` отдаёт те же маршруты с `locale=en`; путь
`/en/` не вводим, чтобы не ломать текущие ссылки и canonical.

### Рендеринг

- `entry-server.js`: создаёт приложение, ждёт данные API, отдаёт
  `renderToString`.
- `entry-client.js`: гидрирует тот же HTML.
- `@unhead/vue` — title, description, canonical, hreflang, OG.
- `vue-i18n` — ru/en; zh для Sfera добавить после вычитки.
- SSR-сервер — Node-процесс (как `medauto-ssr` на этом сервере), nginx
  проксирует HTML-запросы; API — отдельный upstream Django.

### Чего не делаем

- не тянем данные в браузере для первого экрана;
- не рендерим юридические тексты из непроверенного HTML;
- не вставляем `v-html` для пользовательского контента;
- не добавляем аналитику, которая следит за читателем, без отдельного
  решения владельца.

## 7. Документация

### Источник

`content/docs/ru/*.md` и `content/docs/en/*.md` (позже `zh`). Каждый файл:

```yaml
---
slug: getting-started
title: Установка и первый запуск
summary: ...
order: 10
version: 0.1.0
updated: 2026-11-28
---
```

### Импорт

`sync_docs` читает front matter, проверяет обязательные поля и
перезаписывает `DocPage`. Ошибка в front matter — падение команды, а не
молчаливый пропуск страницы.

### Отображение

- дерево слева, статья справа, «предыдущая/следующая»;
- якоря заголовков, подсветка кода, копирование ссылки;
- версия и дата внизу;
- поиск: сначала PostgreSQL FTS по `title`/`body`; внешний поисковик не
  нужен;
- `TechArticle`/`FAQPage` JSON-LD;
- старые `.html`-адреса → 301 на новые.

### Черновик

`docs/USER-GUIDE-DRAFT.md` в репозитории Sfera — исходный текст. При
переносе он разбивается на страницы; не публиковать целиком как один
длинный HTML.

## 8. Публичные каналы

Витрина уже есть в Rust (`social-public`): она проверяет подпись манифеста
и каждого поста. Django **не должен** становиться вторым верификатором.

Схема:

```
браузер → nginx → Vue SSR → Django /api/v1/public/channels/{id}
                                   → social-public-serve (внутренний HTTP)
```

- Django проксирует ответ и кэширует его на 30 секунд;
- если Rust-витрина недоступна, API отдаёт 503, а не выдуманный кэш;
- подпись проверяет Rust; Django не пересобирает и не «улучшает» пост;
- страница канала — SSR: заголовок, описание, лента, дата, ссылка на
  манифест; без комментариев, пока их нет в протоколе;
- публичный канал не показывается в общем поиске, пока владелец явно не
  опубликует его.

## 9. SEO и метаданные

- SSR HTML для всех публичных страниц.
- `canonical` на основном домене; EN — на `vault-msg.tech`.
- `hreflang` ru/en (позже zh), `x-default`.
- `sitemap.xml` генерируется Django из опубликованных страниц и документов.
- `robots.txt` — закрыть `/api/`, `/admin/`, черновики.
- JSON-LD: `SoftwareApplication` для лендинга, `FAQPage` для FAQ,
  `TechArticle` для руководства.
- OG-картинки — по продукту и разделу, не одна на весь сайт.
- Не индексировать публичные каналы, пока нет решения владельца.

## 10. Деплой

```
nginx
├── /                → Node SSR (127.0.0.1:PORT)
├── /api/            → gunicorn (unix socket)
├── /static/         → dist assets
├── /media/          → uploads (если появятся; сейчас не нужны)
└── /admin/          → gunicorn
```

- systemd: `sfera-site-api.service`, `sfera-site-ssr.service`.
- PostgreSQL: отдельная база `sfera_site`, не база релея.
- Миграции — перед перезапуском API, с бэкапом.
- Секреты — в env/systemd, не в git.
- `DEBUG=0`, `ALLOWED_HOSTS`, `CSRF_TRUSTED_ORIGINS` — явно.
- Бэкап БД и `content/docs` — ежедневно; проверять восстановление.
- Health: `/api/v1/health` + SSR `/health`.

### Cutover без простоя

1. Поднять новые сервисы на временном порту.
2. Проверить SSR и API через `curl` с `Host`.
3. Переключить nginx upstream, сохранив статические файлы как fallback.
4. Проверить 200/301/404, canonical, sitemap, OG.
5. Через сутки убрать fallback, но оставить редиректы.

## 12. Риски и как их снимать

| Риск | Мера |
|---|---|
| Две версии правды (HTML и БД) | контент только в БД; docs — из markdown |
| Потеря SEO при смене URL | таблица 301 до cutover, canonical, sitemap |
| Юридические тексты устарели | версия и дата, ревью, отдельный `LegalDocument` |
| RU/EN расходятся | один `slug`, обязательные переводы, тест на пропуски |
| Публичный канал подделан | подпись проверяет Rust; Django только кэширует |
| Сайт тянет ключи | API не отдаёт ключи; публичная витрина без секретов |
| Сервер не тянет SSR | кэш, лимиты, отдельный процесс, мониторинг |
| Смешение Vault и Sfera | `product` в моделях и маршрутах; отдельные тексты |

## 13. Что не входит

- пользовательские аккаунты на сайте;
- комментарии к документации;
- платежи на сайте (платёжный контур остаётся у релея/кассы);
- реклама и трекеры;
- вторая копия проверки подписей на Python;
- автоматический перенос всех старых страниц без редиректов.

5. Нужны ли публичные каналы в поиске и на главной, или только по прямой
