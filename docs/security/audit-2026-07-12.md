# Security Audit Report — Vault (Vault)

**Date:** 2026-07-12
**Auditor:** Security Agent (automated)
**Scope:** vault-backend, vault-client, docker-compose, .env.example
**Method:** Static code analysis, dependency review, configuration audit

---

## Executive Summary

| Severity | Count |
|----------|-------|
| CRITICAL | 2     |
| HIGH     | 4     |
| MEDIUM   | 5     |
| LOW      | 3     |

**Overall assessment:** The project has foundational security issues that must be resolved before any production deployment. The most critical problems are hardcoded fallback secrets and encryption keys stored in plaintext despite being named `*_encrypted`.

---

## CRITICAL Findings

### C-1: Hardcoded JWT Secret Fallback

**Files:** `src/config.rs:26`, `src/auth/handlers.rs:60,93`, `src/auth/middleware.rs:29,65`

```rust
.unwrap_or_else(|_| "dev-secret-change-me".to_string())
```

The JWT secret falls back to a hardcoded string in 5 locations across 3 files. If `JWT_SECRET` env var is not set, all tokens are signed with a publicly known secret. An attacker can forge any JWT.

**Recommendation:** Panic on missing `JWT_SECRET` in production. Use `expect("JWT_SECRET must be set")` or validate at startup. Never allow silent fallback to a known value.

### C-2: Encryption Keys Stored in Plaintext

**Files:** `src/keys/handlers.rs:64-77`, `src/keys/models.rs:10-12`

```rust
.bind(&req.alpha_key)      // raw key from request, NOT encrypted
.bind(&req.columnar_key)   // raw key from request, NOT encrypted
.bind(&req.combined_key)   // raw key from request, NOT encrypted
```

Despite field names `alpha_key_encrypted`, `columnar_key_encrypted`, `combined_key_encrypted`, the handler inserts the raw user-provided key values directly into the database with **no encryption layer**. A database breach exposes all encryption keys.

**Recommendation:** Encrypt keys server-side before storage (e.g., AES-256-GCM with a master key from env/vault). Never trust client-provided "encryption" of keys.

## HIGH Findings

### H-1: Hardcoded Database Credentials

**File:** `src/config.rs:24`

```rust
.unwrap_or_else(|_| "postgres://vault:vault_dev_password@localhost:5432/vault".to_string())
```

Database connection string with password is hardcoded as fallback. Same pattern as C-1 — if `DATABASE_URL` is missing, the app connects with a known password.

### H-2: No .gitignore

**Root directory** has no `.gitignore` file. This means `.env` files, `Cargo.lock`, build artifacts, IDE configs, and any secrets files could be accidentally committed to version control.

**Recommendation:** Create `.gitignore` with at minimum: `.env`, `*.pem`, `*.key`, `target/`, `graphify-out/`, `.env.local`, `.env.production`.

### H-3: Database Error Messages Leaked to Clients

**Files:** `src/auth/handlers.rs:38,82`, `src/email_accounts/handlers.rs:22,43,63,84`, `src/keys/handlers.rs:23,79,94`

```rust
.map_err(|e| (StatusCode::INTERNAL_SERVER_ERROR, e.to_string()))?;
```

SQLx error messages (which may contain table names, column names, query fragments) are returned directly to the HTTP client. This leaks internal database schema to attackers.

**Recommendation:** Log full errors server-side, return generic messages to clients: `"Internal error"`.

### H-4: CORS Allows Any Origin

**File:** `src/main.rs:30-33`

```rust
let cors = CorsLayer::new()
    .allow_origin(Any)
    .allow_methods(Any)
    .allow_headers(Any);
```

Completely open CORS policy. Any website can make authenticated requests to the API (if cookies or credentials are used).

**Recommendation:** Restrict to specific allowed origins from environment config.

## MEDIUM Findings

### M-1: Encryption Keys Passed in Request Body in Plaintext

**File:** `src/keys/handlers.rs:72-75`

The `CreateKeyRequest` contains `alpha_key`, `columnar_key`, `combined_key` as plain `String` fields. These are sent over HTTP (no TLS enforcement in code) and stored without encryption (see C-2).

### M-2: User Model Has password_hash with Serialize

**File:** `src/models.rs:10`

```rust
pub password_hash: String,
```

The `User` struct derives `Serialize` and includes `password_hash`. While the `AuthResponse` struct doesn't include it, if `User` is ever returned directly in any endpoint, the password hash would be exposed.

**Recommendation:** Use `#[serde(skip)]` on `password_hash` or create a separate `UserResponse` struct without it.

### M-3: SMTP builder_dangerous Allows Unencrypted Connections

**File:** `src/email/smtp.rs:54`

```rust
AsyncSmtpTransport::<Tokio1Executor>::builder_dangerous(&self.server)
```

When `use_tls` is false, the SMTP transport is built with `builder_dangerous` which allows plaintext SMTP without any warning. Email passwords and content would be transmitted in the clear.

### M-4: No Rate Limiting on Auth Endpoints

**Files:** `src/auth/handlers.rs`, `src/main.rs:37-38`

The `/api/auth/register` and `/api/auth/login` endpoints have no rate limiting, enabling brute-force attacks on passwords and mass registration.

### M-5: No Input Validation on Registration

**File:** `src/auth/handlers.rs:30-69`

No email format validation, no minimum password length check, no username sanitization. A user can register with empty password or malformed email.

## LOW Findings

### L-1: rand 0.8 (Deprecated API)

**File:** `Cargo.toml:37`, `src/crypto/mod.rs:16`

`rand = "0.8"` uses `thread_rng()` which is deprecated in newer rand versions. Consider upgrading to rand 0.9+.

### L-2: Custom Crypto Instead of Standard Algorithms

**Files:** `src/crypto/alpha.rs`, `src/crypto/columnar.rs`

The project implements custom ciphers (Alpha cipher, Columnar cipher) instead of using established algorithms (AES-256-GCM, ChaCha20). Custom crypto is prone to subtle vulnerabilities and provides no security guarantees.

**Recommendation:** Use `aes-gcm` or `chacha20poly1305` crates for encryption. Keep custom ciphers only as an additional obfuscation layer, not as the primary encryption.

### L-3: JWT Access Token Expiry is 24 Hours

**File:** `src/auth/jwt.rs:27`

Access tokens are valid for 24 hours. Best practice for access tokens is 15-60 minutes with refresh token rotation.

## Configuration Audit

### .env.example

```
DB_PASSWORD=vault_dev_password    # OK for example, but no .gitignore
JWT_SECRET=dev-secret-change-me-in-production  # CRITICAL: too weak even for example
```

**Recommendation:** `.env.example` should show structure only, with placeholder values like `<your-secret-here>`. Never include real or realistic passwords.

### docker-compose.yml

- DB password uses `${DB_PASSWORD:-vault_dev_password}` — same hardcoded fallback issue
- PostgreSQL port exposed to host — acceptable for dev, remove for production
- pgAdmin commented out with `PGADMIN_DEFAULT_PASSWORD: admin` — should be removed entirely

## Positive Findings

1. **Argon2 for password hashing** — good choice, industry-standard algorithm
2. **SQLx with parameterized queries** — no SQL injection in current code
3. **EmailAccountResponse excludes password_encrypted** — proper API response design
4. **KeyResponse excludes raw key values** — proper API response design for keys
5. **Auth middleware validates JWT** — proper authentication flow
6. **TLS support for IMAP/SMTP** — `use_tls` flag with STARTTLS fallback
7. **Database health checks in docker-compose** — good operational practice

## Priority Remediation Plan

1. **Immediate (before any deployment):**
   - Add `.gitignore` (H-2)
   - Panic on missing `JWT_SECRET` instead of hardcoded fallback (C-1)
   - Panic on missing `DATABASE_URL` instead of hardcoded fallback (H-1)
   - Encrypt encryption keys before database storage (C-2)

2. **Before production:**
   - Sanitize all error responses to clients (H-3)
   - Restrict CORS origins (H-4)
   - Add rate limiting to auth endpoints (M-4)
   - Add input validation (M-5)
   - Add `#[serde(skip)]` to `password_hash` (M-2)

3. **Short-term:**
   - Install and run `cargo audit` regularly
   - Reduce JWT access token expiry to 15-30 minutes (L-3)
   - Evaluate replacing custom ciphers with standard algorithms (L-2)
