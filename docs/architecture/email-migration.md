# Смена почты (email migration) — дизайн

Дата: 24.08.2026
Статус: **проект на обсуждение** (не реализовано)
Задача: пользователь меняет email (транспортный адрес), но **остаётся тем же
человеком** для своих контактов: не шлёт новых приглашений, не принимает
новых, продолжает переписку и остаётся в группах.

---

## 0. Проблема: сегодня идентичность = email

Сейчас в Vault **email является идентичностью**:

| Хранилище | Ключ | Файл |
|---|---|---|
| Свой ключ | `keypair.json` (без привязки к email) | `~/.vault/keys/keypair.json` |
| Ключи контактов | `peer_keys.json` индексированы **по email** | `~/.vault/keys/peer_keys.json` |
| Профили (имя/аватар) | `profiles[email]` (JS) | localStorage/BД |
| Контакты | массив объектов с `email` | БД |
| Группы | `members[].email` | БД (`groups` sqlite) |
| Сообщения | `sender_id = email` отправителя | БД |

Последствия: смена почты = «новый человек»: все контакты видят незнакомца,
переписка не матчится, группы ломаются, ключи не находятся.

**Требование пользователя**: смена почты должна быть **миграцией адреса
доставки**, а не сменой личности.

---

## 1. Ключевая идея: отделить идентичность от транспорта

```
ИДЕНТИЧНОСТЬ (стабильна, навсегда):      ТРАНСПОРТ (меняется свободно):
- keypair X25519 (уже есть)               - email = адрес доставки
- fingerprint = SHA-256(public_key)       - IMAP/SMTP настройки
- «vault id» = короткая форма fingerprint
```

- Свой ключ **уже не привязан к email** (keypair.json без email) — это база.
- Всё, что ссылается на человека, должно ссылаться на **fingerprint ключа**,
  а email становится **полем доставки** (mutable), а не идентификатором.

## 2. Изменения по слоям

### 2.1 peer_keys.json — ключ записи = fingerprint
```json
{
  "fingerprint": "a1b2...",   // ключ записи
  "public_key": "base64...",
  "emails": ["old@mail.ru", "new@mail.ru"],  // ВСЕ известные адреса
  "primary_email": "new@mail.ru",            // текущий для доставки
  "label": "Маша",
  "added_at": "..."
}
```
- Один контакт = одна запись, сколько бы адресов ни сменил.
- Поиск: по любому из `emails` → один и тот же контакт.
- При получении письма с нового адреса от того же fingerprint: `emails.push(new)`,
  `primary_email = new` — **автоматически, без приглашений**.

### 2.2 Конверт сообщения — добавить `key` (fingerprint отправителя)
Сейчас `{vault:1,id,text,name,avatar}`. Добавить:
```json
{ "vault": 1, "id": "...", "key": "a1b2...", "text": "...", "name": "...", "avatar": "..." }
```
- Получатель: если `key` есть и уже известен → письмо от существующего контакта
  (сверка по fingerprint) → доставка переключается на новый email молча.
- Если `key` неизвестен → это НОВЫЙ контакт (приглашение как раньше).
- Backward-compat: старые клиенты без `key` работают по-старому (по email).

### 2.3 Приглашение/обмен ключами — не менять протокол
- Ключ уже обменивается через приглашение; достаточно того, что в конвертах
  появится `key`. Смена почты НЕ требует нового приглашения:
  1. Пользователь в настройках меняет email (и пароль приложения для новой
     почты).
  2. Vault логинится на новую почту, **старая остаётся доступной на чтение**
     (если пользователь не удалил ящик) — или просто шлёт письма с новой.
  3. Первое же сообщение с новой почты несёт `key` = старый fingerprint →
     контакты его узнают → обновляют `emails`/`primary_email`.
- **Важно**: пока контакты не узнали новый адрес, они шлют на старый. Поэтому:
  - Vault **продолжает читать старый ящик** (мульти-аккаунт: основной +
    legacy-входящие) и на сообщения отвечает с нового адреса;
  - при ответе контакт видит `from = новый email` + `key` → запоминает.

### 2.4 Группы — участники по fingerprint
Сейчас `members[].email`. Стало:
```json
{ "members": [{ "key": "a1b2...", "email": "new@mail.ru", "role": "member" }] }
```
- Рассилка в группе: по `primary_email` каждого участника из peer_keys.
- Если у участника сменился email — группа продолжает работать: адрес
  берётся из peer_keys (один источник правды).
- Смена почты участника = просто смена `primary_email` у его записи.
- Старые БД: миграция при загрузке (email → fingerprint по peer_keys).

### 2.5 Своя смена почты (в настройках)
1. `Настройки → Сменить почту`: ввести новый email + пароль приложения.
2. Проверка: SMTP/IMAP на новом ящике работает (как при первом входе).
3. Сохранить: credentials нового ящика; **старый ящик оставить в списке
   аккаунтов как legacy-входящий** (опция «продолжать читать старый ящик»,
   по умолчанию ВКЛ).
4. Всем контактам при следующем сообщении автоматически придёт письмо
   с нового адреса + `key` → они обновят адрес.
5. UI: в профиле показать «известные адреса» — сколько контактов узнали
   новый адрес (счётчик).

### 2.6 Стелс/безопасность
- Ничего не ломается: письма как письма, AAD="VAULT", пустые темы.
- fingerprint НЕ раскрывает ничего нового (это хэш публичного ключа,
  который и так ездит в ключах).
- Старый ящик после миграции можно удалить — доставка уже на новом.

---

## 3. Что это даёт (ответ на требование)

- ✅ Сменил почту → контакты **сами** узнают новый адрес (по `key`), ничего
  не меняя у себя.
- ✅ Не надо слать/принимать новые приглашения.
- ✅ Переписка не рвётся: история матчится по fingerprint.
- ✅ Группы продолжают работать: участники по ключу, адрес — поле доставки.
- ✅ Возможна многократная смена (список `emails` хранит все адреса).

## 5. Открытые вопросы

1. Мульти-аккаунт: сейчас в приложении один активный email. Смена почты
   требует читать 2 ящика одновременно (старый + новый) хотя бы переходный
   период. Это затрагивает EmailState (сейчас один). — **нужно решение**:
   либо «мастер-аккаунт + legacy», либо полноценный мульти-аккаунт.
2. Если старый ящик закрыт/недоступен: контакты не получат новые сообщения
   со старого адреса, но первое исходящее с нового адреса их обновит. Связь
   восстановится при первом же сообщении пользователя.
3. Пока контакт не обновился: он шлёт на старый адрес; Vault читает оба —
   ок. А если пользователь удалил старый ящик? Тогда письма на старый адрес
   пропадут. Решение: настройка «пересылать со старого на новый» на стороне
   почты (инструкция), или держать ящик.

## 6. Решение по приоритету

- **MVP (M2/M3)**: пункты 2.2 (envelope key) + 2.1 (peer_keys по fingerprint)
  + 2.5 (смена почты в настройках) — уже дают главное: смена почты без
  потери контактов. Группы по key — следом.
- **Не делать сейчас**: мульти-аккаунт как продуктовая фича; достаточно
  «старый ящик читается как legacy».
