## 1. Ниша (чем отличаемся от SimpleX и Delta Chat)

Одним предложением: **«приватный мессенджер, который живёт внутри обычной
почты (неотличим от неё), не требует серверов для работы, имеет звонки и
может ускоряться через собственные релеи»**.

| | Vault | SimpleX | Delta Chat |
|---|---|---|---|
| Транспорт | email (базовый) + relay (опция) | SMP-серверы (обязательны) | email |
| Серверы для работы | НЕ нужны (serverless) | Нужны (SMP) | chatmail |
| Звонки | ✅ (в работе, M3) | ✅ WebRTC | ❌ (PR закрыт) |
| Стелс | ✅ пустые темы, AAD="VAULT", неотличим от писем | пакеты идентифицируемы DPI | темы видно |
| Онбординг | обычный email — знакомо | одноразовые длинные ссылки | средний |
| Push | (планируется: relay+foreground service) | свой push | FCM |
| РФ/СНГ | Яндекс/Mail/Gmail, без Google-push | западная ориентация | западная |

- SimpleX — для параноиков-технарей; у нас обычные люди с почтой.
- Delta Chat — email-мессенджер без звонков; мы уже опередили по звонкам.
- Ключевое отличие: serverless-ядро — даже при блокировке всех релеев почта
  работает, приложение живо. У SimpleX без SMP-серверов ничего не работает.

## 2. Надёжность, блокировки, push — что даёт relay-слой (SimpleX-модель)

### Надёжность
- Сейчас: только email, доставка 30–60с; звонки страдают.
- С relay: конверт идёт двумя путями (email + relay), кто первый — тот и
  победил; доставка ~100–300мс через relay.
- Multi-tube (M6): при троттлинге/блокировке провайдера работает relay.
- Честно про блокировки: свой relay — новая точка блокировки. Решение —
  децентрализованные/ротируемые релеи (адреса не привязаны к одному серверу),
  relay = «труба, не читатель» (E2E, AAD="VAULT").

### Push при закрытом приложении на Android
- Сейчас: нет вообще.
- SimpleX-модель: свой push-сервер; получатель держит лёгкий WebSocket
  (или FCM); при новом сообщении relay будит приложение push-ом.
- Наш план: relay → push; Android foreground service (веха 2.2.1) держит
  WebSocket → мгновенный «толчок» при закрытом приложении. Без Google FCM
  (важно для РФ; FCM — опционально).

## 3. Монетизация

Архитектура serverless + E2E + каналы с ключами = **монетизация сети как
услуги, а не контента**. Нельзя монетизировать: рекламу (E2E не видит
контент), данные (не собираем), «приватность как платную опцию» (должна
быть бесплатной). Можно:

1. **Премиум-релеи** (модель SimpleX Pro): быстрее, приоритетный push,
   большие лимиты, свой домен. Бесплатно — базовые релеи.
2. **Каналы с платной подпиской (M2)**: автор ставит цену, платформа —
   комиссию. Ключ канала = доступ, криптографически проверяемо.
3. **Мини-приложения (M3, webxdc-паттерн)**: платные приложения внутри,
   комиссия платформы.
4. **B2B self-hosted**: свой релей + TURN + поддержка + SLA для компаний.
5. **Донаты/фонд** (Signal/SimpleX-модель) — покрытие базовых расходов.
6. **Видео (директива 30.08)**:
   - *Просмотр*: платные каналы с видео-контентом (подписка) +
     download-on-demand тяжёлого медиа через premium-релей — пейволл за
     «смотреть». Работает на транспорте каналов/релеев без новых компонентов.
   - *Приватные групповые видеочаты*: 3-4 участника — бесплатный P2P mesh
     (каждый каждому); большие группы — платный SFU-релей (единственный
     серверный компонент видеочатов, расширение модели премиум-релея).

Честные ограничения:
- Проблема «безбилетника»: пользователь чужих релеев бесплатно. Решение —
  качество сервиса: бесплатные медленнее, с лимитами, без гарантий.
  Аналогия: Fastmail зарабатывает на email, который «бесплатен» у Google.
- Для денег нужна база: мессенджер со звонками → каналы → соцсеть.

## 4. Расширение в распределённую соцсеть (M5) — на готовом фундаменте

Основные функции уже будут — расширение это достройка, не переписывание.

### Готовые кирпичи
- Профиль/аватар/имя: localProfile, UserAvatar, meta-рассылка аватара
- Посты = сообщения с вложениями (E2E-конверт, фото/аудио/файлы)
- Каналы (1→N): паттерн групп (инвайт, ключ, участники)
- Лента: merge каналов по времени
- «Просмотрено»/реакции: read-квитанции и реакции работают
- Офлайн: local-first репликация постов на устройство
- Звонки/стриминг: WebRTC (в работе)
- Заметки-черновики: «Заметки для себя»

### Надо построить
- Лента (merge каналов + UI) — средняя сложность, чистый фронт
- Download-on-demand (M1): превью + тяжёлое тело по запросу (P2P/релей)
- Контейнер удалённого доступа («устройство = сервер», видео друга):
  WebTorrent-паттерн поверх DataChannel — высокая, механизмы заложены
  (сигнализация E2E-сообщениями, TURN на 443)
- Модерация/роспуск каналов (сейчас модель «админ группы»)

### Оценка
- M1 (15.09): download-on-demand — средняя
- M2 (15.10): каналы — средняя
- M3: P2P-раздача тяжёлого медиа — высокая (WebRTC уже в работе)
- M5: лента + контейнер — средняя/высокая

Честное ограничение живого стриминга: P2P-видео требует устройства автора
онлайн и не усыплённого процесса → релей-зеркало (E2E-байты заранее) вместо
прямой раздачи. Лента/посты по email работают всегда, даже при офлайн-авторе.

Козырь: VK/Telegram-каналы блокируются одним решением РКН; нашу ленту —
только заблокировав весь интернет (serverless + multi-tube + стелс).
