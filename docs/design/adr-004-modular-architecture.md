# ADR-004: Модульная архитектура — независимость как инвариант

Дата: 15.10.2026 · Статус: принят к исполнению · Приоритет: 1
Связан: ADR-001 (связность и ctx), ADR-003 (слои фронтенда), ADR-002 (подпись постов)

## Почему это первый приоритет

Приложение должно расширяться до распределённой сети с потоковым видео. При
таком росте каждое изменение, задевающее чужую функциональность, приходится
искать месяцами. Сегодня именно такое положение вещей, и оно измерено:

| | значение |
|---|---|
| ctx-ссылок | **1225** в 442 местах |
| модулей | 44 |
| **полей, которые пишут НЕСКОЛЬКО модулей** | **12** |

И главное — не первая строка:

| поле | сколько модулей его пишет | где |
|---|---|---|
| `messages` | **7** | `attachments`(6), `messages`(5), `groups`(3), `send`(3), `history`, `calls`, `poll` |
| `groupKeys` | **5** | `groups`, `send`, `incoming`, `group-avatars`, `group-meta` |
| `sending` | **3** | `send`, `forward`, `poll` |
| `groupAvatars` | **3** | `groups`, `group-avatars`, `group-meta` |
| `pendingOutgoing` | 2 | `send`, `history` |
| `unreadCounts` | 2 | `incoming`, `calls` |
| `newMessage` | 2 | `drafts`, `send` |
| `isLoggedIn`, `emails`, `ecoMode`, `relayEnabled`, `relayDeliveryMode` | по 2 | — |

**`messages` пишут семь модулей.** Это не «зависимость от компонента» и не
«много `ctx`». Это **невидимый канал записи друг в друга**: правка
`attachments.js` может испортить переписку и сломать `send`, `poll`, `groups`,
`history`, `calls`, `messages` — а они об этом не узнают, потому что о
`attachments.js` ничего не знают. Состояние переписки — самое ценное, что есть
в приложении, и оно не принадлежит ни одной фиче.

`ctx` здесь лишь транспорт. Пока он есть, переименование его в «зависимость»
ничего не меняет: канал остаётся, меняется имя.

Дренаж `App.vue` (ADR-003, Этап 3, 17 партий) уменьшил файл с 7489 до 7080 строк
и добавил 1071 проверку, но **связность за это время выросла с 1217 до 1222**.
Это измерение, и оно говорит прямо: подход «переносить методы по одному» не
решает задачи независимости. Он решал задачу размера файла.

## Чего этот ADR требует

Одно из трёх, для каждой новой фичи и для каждого переносимого метода:

1. **Не брать состояние из компонента.** Данные принадлежат фиче, которая ими
   владеет, или отдельному хранилищу с одним владельцем.
2. **Не писать в чужое состояние.** Запись в поле, которым владеет другой
   модуль, запрещена. Точка приёма — новый писатель у поля.
3. **Зависимость объявлять явно.** Передавать узкий список того, что реально
   нужно, а не весь объект.

Нарушение пункта 2 ловится гейтом автоматически. Пункты 1 и 3 — предмет ревью.

### Исправление цифры, на которой строился этот ADR

Первая версия ставила на первое место `peerKeys` с **14 писателями** и
`peerPqKeys` с 13. **Цифра была неверной**, и на ней стоял бы весь план.

Дефект был в инструменте, а не в коде: шаблон поиска записи считал чтение по
индексу `ctx.peerKeys[email]` записью — в списке альтернатив стоял голый `[`.
Поэтому список писателей распух, а настоящий худший случай `messages` в первую
версию не попал вовсе.

**Фактические писатели `peerKeys` — три места** (`messages.js`, `incoming.js`,
`duress.js`); остальные одиннадцать модулей идут через помощник
`ctx.setPeerKey`. То есть для `peerKeys` канал уже почти закрыт, и выносить его
в первую очередь было бы пустой работой.

Вывод, который стоит записать: **план архитектуры, построенный на цифрах
инструмента, верен ровно настолько, насколько инструмент проверен.** Оба
инструмента этой сессии — храповик связности и построчный разбор смоуков —
сначала были неправильны, и обе ошибки пойманы проверкой на подставленном
нарушении, а не чтением кода. Порядок: сначала проверить измеряющий инструмент
на заведомо известном случае, потом строить на нём план.

## Целевая форма

### Сейчас

```
App.vue ──data()──▶ { peerKeys, groupKeys, messages, currentCall, … 442 поля }
   │
   ├──▶ calls.js        (ctx, 38 полей, 13 из них ПИШЕТ)
   ├──▶ messages.js     (ctx, 38 полей)
   ├──▶ send.js         (ctx, 37 полей, 4 пишут)
   └──▶ …44 модуля…
        │
        └──▶ ctx.peerKeys[…] = …   ← 14 модулей пишут в один словарь
```

### Должно стать

```
Композиционный корень (App.vue или отдельный composition-root.js)
   │
   ├── identityStore     ← ВЛАДЕЕТ peerKeys, peerPqKeys, fingerprint, publicKey
   ├── groupsStore       ← ВЛАДЕЕТ groupKeys, groupAvatars, groups
   ├── chatStore         ← ВЛАДЕЕТ messages, pendingOutgoing, unreadCounts, drafts
   │
   └──▶ calls.js  (deps: { session, keys, … 8 вместо 38 })
   └──▶ send.js   (deps: { keys, chat, relay, … })
```

Правила:

- **Store — единственный владелец.** Обращение к ключу только через метод
  хранилища: `identity.peerKeyOf(email)`, не `ctx.peerKeys[email]`.
- **Фича не знает про другие фичи.** `calls.js` не импортирует `messages.js` и
  не пишет в его состояние. Если нужны чужие данные — через хранилище, у
  которого один владелец.
- **Компонент — композиционный корень, а не мешок состояния.** Его задача —
  собрать зависимости и передать их. Не хранить.
- **UI-состояние (открыт ли попап, позиция меню) остаётся в компоненте.** Это
  правило из ADR-003 §2 остаётся в силе и не обсуждается.

## Что уже сделано, чтобы это не размылось

**`scripts/ctx-ratchet-gate.mjs` в `npm run build`.** Потолок, который можно
только затягивать: опции повышения нет, `--write` лишь записывает текущую
(не большую) величину. Ловит:

1. модуль взял новое поле из компонента — называет поле;
2. **поле получило нового пишущего модуля** — называет поле и модуль, и это
   главная проверка: именно она запрещает невидимый канал записи;
3. рост суммарного числа ссылок.

Эталон берётся из закоммиченной версии, и гейт ловит также ослабление рабочей
копии — иначе момент ослепления наступил бы позже, на ревью, где гейта нет.

Отличие от `ctx-coupling-gate`: тот меряет величину и останавливает рост сверх
baseline, а рост можно «осознанно принять». Это baseline, а не ограничение.

## Порядок работ

Порядок выведен из измерения, а не из удобства. Начинать с того, что даёт
наибольшее уменьшение связности на единицу работы и где дефект наиболее опасен.

### Этап A — развязать три поля-конфликта (главное)

Это **12 полей и около 40 мест записи**. После этого исчезает невидимый канал
между фичами, и всё остальное становится обычным рефакторингом.

| поле | владелец | писателей сейчас |
|---|---|---|
| `messages`, `pendingOutgoing`, `unreadCounts`, `newMessage` | новое `chat-store.js` | **7, 2, 2, 2** |
| `groupKeys`, `groupAvatars` | новое `groups-store.js` | **5, 3** |
| `sending` | владеет `send.js`, остальные только читают | 3 → 1 |
| `isLoggedIn`, `emails`, `ecoMode`, `relayEnabled`, `relayDeliveryMode` | `session.js` | по 2 |

Порядок выведен из числа писателей, то есть из цены поломки.

**`messages` — первым.** Это самое ценное состояние приложения и самое
разделяемое. Модуль-владелец получает API: `chat.setMessages()`,
`chat.addMessage()`, `chat.replaceMessage()`. Прямой доступ к массиву закрывается.

Каждое переводимое место — механическая замена вызова. Сначала один модуль
целиком, чтобы доказать, что работает, потом остальные.

### Этап B — capability-интерфейсы

Модули, читающие много, но почти не пишущие, получают явный список:
`calls.js` — 38 полей, из них 13 он пишет (это его состояние, см. ниже), а
остальные — зависимость. После Этапа A останется ~25 полей-возможностей:
`t`, `showToast`, `scrollToBottom`, `saveChatCache`, `isAndroid`, `msgTs`.

Это оформляется как `needs`-контракт: модуль объявляет, компонент собирает
ровно этот объект. Ошибка «метод не существует» (§5.5 ADR-003) становится
невозможной автоматически.

### Этап C — состояние, которым владеет модуль

`calls.js` пишет 13 полей: `currentCall`, `callState`, `callClockSec`,
`callRingTimer`, `callSoundEl`, `callMuted`, `callSpeaker`, `lastCallId`,
`_pendingKemct`, `_pendingSenderEk`, `callMediaConnected`, `_mediaFallbackTimer`,
`_connLostTimer`.

Это **не зависимость, это состояние**: сессия звонка, размазанная по полям
компонента. Два из них — `callSoundEl` и таймеры — вообще не состояние Vue, а
DOM-ручки, и в `data()` им не место.

Правильный исход: объект `callSession` внутри модуля, со своим жизненным
циклом. `calls.js` становится **заменяемым целиком**: удалить его — значит
удалить объект, а не править 38 мест в компоненте. Это и есть проверка на
независимость.

### Этап D — гейт правила слоёв

Запрет на импорт фичи из фичи, кроме явного списка примитивов. Сейчас таких
случаев 7.

## Критерий готовности

Модуль считается независимым, если выполняются все четыре:

1. его можно запустить в тесте без компонента (сейчас — да, у 44 модулей);
2. **он не пишет ни в одно поле, принадлежащее другому модулю**;
3. **он не импортирует другой модуль-фичу** (кроме примитивов из списка);
4. **его можно удалить, удалив ровно одно место в компоненте**.

Четвёртое — проверка на практике, и она в проекте ещё ни разу не проходила.
До Этапа A пункт 2 не выполнен ни для одного модуля. Ближе всех к цели
`peerKeys`: писателей три, остальные модули идут через помощник.

## Чего этот ADR не решает

- **Связность внутри одного модуля.** `messages.js` (38 полей) может быть
  независим от других и при этом остаться нечитаемым. Это вопрос размера, а не
  связности, и решается отдельно.
- **Циклы уже закрыты** (ADR-003, `ctx-cycles-gate`), это не входит сюда.
- **Скорость.** Ничего не измерялось. 1225 обращений к `ctx` — это ещё и время,
  но конкретных цифр нет, и выдумывать их не буду.
- **Android-клиент** (`vault-android`) — там своя копия кода, и правки
  `vault-desktop` на неё не распространяются.
