# Broadcast-каналы — дизайн-док (M2)

Статус: черновик для ревью · Дата: 15.09.2026 · Автор: Vault team

## 1. Цели и нецели

### Цели
1. **«Один вещает — многие читают»** поверх существующего email-транспорта:
   без новых серверов, без изменений wire-формата конвертов.
2. **Подписка без доверия к владельцу**: подписчик не раскрывает ни почту,
   ни факт чтения (privacy выше, чем у Telegram-каналов).
3. Переиспользование групповой инфраструктуры (ключи, инвайты, reactions,
   дедуп, релей-дубль) — канал = специализированная группа, не новая сущность.
4. Фундамент M5: стена = личный канал с contact-gated аудиторией.

### Нецели (M2)
- Платные подписки (payment hub t_34acf3d7 — отдельная задача поверх).
- Лента-агрегация стен (M5).
- Комментарии/обсуждения под постами (реакции достаточно; M5 решит).
- Video-стриминг (M3+).

## 2. Модель: канал = broadcast-группа

Delta Chat-модель, адаптированная под существующий код Vault:

| Аспект | Группа (есть) | Канал (новое) |
|---|---|---|
| Ключ | group_key (32B, симм.) | тот же group_key = **broadcast-секрет** |
| id | `grp_<hex8>` | `chn_<hex8>` (префикс отличает UI/роутер) |
| Отправка | любой участник | **только владелец** (broadcast) |
| Подписка | инвайт от участника | **самостоятельно по QR/ссылке** |
| Аудитория | known members list | неограниченная, владелец не видит подписчиков |
| Read | getGroupMessages (members) | тот же путь, но отправитель = владелец |

Ключевое отличие от группы: **подписчик получает broadcast-секрет из
QR-ссылки**, не из письма-инвайта. Владелец расшифровывает своим pubkey-ом
никого не должен — секрет уже в QR.

## 3. Wire-формат

### 3.1 QR-ссылка канала (подписка)

По образцу контактов (`VaultContactInvite:`), но самодостаточная:

```
vault://join-channel?c=<channel_id>&k=<broadcast_key>&n=<name_urlenc>&o=<owner_fpr>
```

- `c` — channel id (`chn_...`);
- `k` — broadcast-секрет (64 hex) — единственный способ войти: без ключа
  конверты канала не расшифровать;
- `n` — имя канала (просто удобство, реальное имя придёт в meta-конверте);
- `o` — fingerprint владельца (128-hex): привязка эмиттера постов, защита
  от подмены владельца при утечке ссылки (подпись post-конвертов, см. §3.3).

QR рендерится из ссылки (тот же qrcode-генератор, что у контактов).
Текстовая ссылка также кликабельна из письма/чата (Tauri opener).

### 3.2 Post-конверт

Тот же E2E-конверт, что и групповые сообщения (AAD="VAULT", XChaCha20-Poly1305,
ключ канала), payload:

```json
{ "channel": 1, "id": "<env.id>", "ts": <unix>,
  "post": { "body": "<текст/markdown>", "images": ["<dataURL>…"] },
  "meta": false }
```

- `channel:1` — маркер типа для роутера (не путать с group-конвертами);
- Stealth: **пустая тема** (как все сообщения), получатель классифицирует
  по содержанию после расшифровки ключом канала;
- Вложения: пока вложения канала = те же email-вложения (лимит провайдера);
  images как dataURL в post.body — компактные (≤100KB суммарно, shrinkImage).

### 3.3 Channel-meta-конверт (описание, аватар, смена ключа)

```json
{ "channel": 1, "meta": 1, "name": "...", "about": "...",
  "avatar": "<dataURL>", "key_version": 1, "prev_key": null }
```

- Отправляется владельцем при создании/правке; повторная отправка последних
  10 постов новому подписчику НЕ делается (email-ящик хранит историю;
  подписчик тянет при первом входе через обычный fetch — см. §5).
- **Ротация ключа** (выписка подписчика/утечка): `key_version+1`, новый
  `broadcast_key` рассылается… нет — broadcast-модель не позволяет владельцу
  адресно выслать новый ключ неизвестным подписчикам. Ротация = владелец
  публикует новый QR (новый канал), meta старого канала получает
  `migrated_to: <new_channel_id>`; подписчики при виде миграции
  автоподписываются (ключ нового канала приходит в meta старого — тот же
  компромисс, что и у Delta Chat, там отзыв QR тоже не отзывает доступ).

### 3.4 Подтверждение подписки (только по желанию)

По умолчанию подписка **тихая** — владелец не узнаёт. Опционально подписчик
может отправить `{"channel":1,"hello":1}` (обычный E2E-конверт на pubkey
владельца из QR) — если хочет, чтобы владелец знал и мог DM. Не условие
получения постов.

## 4. Отправка/приём (переиспользование группового пути)

- Отправка поста: `api.sendGroupMessage(channel_id, body)` — групповой путь
  as-is: письмо каждому известному участнику? НЕТ — канал не знает списка.
  Владелец шлёт пост ОДНО письмо самому себе (Bcc-механики нет в stealth),
  подписчики сами забирают из ящика владельца? Тоже нет — они не имеют
  доступа к его ящику.

**Решение**: пост уходит **письмом от владельца в ЕГО ЖЕ ящик** (self-To) —
подписчики не могут читать чужой ящик. Broadcast-канал должен «доставляться».
Смотрим на реальный транспорт: email может только адресную доставку.

### 4.1 Доставка: subscriber-pull через ящик владельца невозможна → доставка = адресная рассылка

Владелец не знает адресов подписчиков (privacy-цель §1.2). Противоречие
классического push-broadcast с serverless-email.

Разрешение — **релей-трансляция** (relay уже жив, M2.1-M2.4 закрыты):

1. Владелец публикует post-конверт в relay одним `pub` с `to = channel_token`
   (read-токен канала, общий для всех подписчиков — broadcast-секрет и есть
   авторизация). Реализация (channels-6, relay-server/src/tokens.rs): токены
   детерминированно выводятся КЛИЕНТОМ из broadcast-ключа (серверного
   HMAC(server_key,...) клиент вычислить не может — server_key не покидает
   релей): `read = base64url(kid8 ‖ 'c' ‖ 0xFFFFFFFF ‖ HMAC(bcast, "vault-relay-channel-read"))`,
   `write = тот же kid (от read-MAC) ‖ 'C' ‖ 0xFFFFFFFF ‖ HMAC(bcast, "vault-relay-channel-write")`.
   Владение токеном = владение ключом (256-битная способность); rotation
   ключа = новые токены сами (миграция §3.3). Сервер для каналов проверяет
   структуру + kid-связку write↔read-очереди, не MAC.
2. Relay хранит конверт ≤24ч, TTL-очистка; все подписчики поллят
   `/relay/poll` со своим аккаунтом — но токен канала общий, значит каждый
   poll отдаёт конверт каждому подписчику (fan-out на read-стороне, не на
   store-стороне — Cheap: O(subscribers) reads, O(1) store).
3. Email-фолбэк: если владелец знает адреса (opt-in список «известных
   подписчиков» — те, кто отправил hello или добавлен вручную), пост
   дополнительно уходит email-рассылкой им (механика групп, cap 50).
   Для остальных подписчиков email-копии нет — только relay.

**Честная формулировка для прода**: бесплатный relay-канал = instant delivery
пока релей жив; если релей лёг — новые посты не доходят до «анонимных»
подписчиков до его восстановления (или владелец вручную публикует email-дубль
списку известных). Premium-релей (t_34acf3d7) поднимает лимиты/гарантии.

### 4.2 Приём: роутер

`incoming.js classify()` — новая ветка после групповой расшифровки:
- конверт расшифровался канальным ключом (перебор ключей каналов из kv
  `channels:<id>`) → `channel_post` / `channel_meta`;
- `id` → дедуп (processedUnreadIds, кросс-канальный env.id — уже есть);
- уведомление: как групповое, но без имени отправителя («Канал X: новый пост»);
- `hello:1` владельцу — покажем карточкой в канале (N подписчиков «на связи»).

## 5. Хранение и UI

- SQLite: `channels` таблица (id, name, about, avatar, owner_fpr, key,
  key_version, created_at, last_ts, is_owner). Rust: `channels.rs` по образцу
  `groups.rs` (groups.json → channels.json MVP, sqlite в M2.x по мере надобности).
- UI: вкладка/список «Каналы» рядом с «Группы» (тот же sidebar-паттерн):
  - создание: «+» → «Создать канал» (имя, описание, аватар) → QR-ссылка;
  - подписка: «Присоединиться по ссылке» (вставка vault://join-channel...);
  - чтение: тот же MessageItem-рендер (reactions работают? Да — сигнальные
    конверты групп применимы, react в канале = `{react:1}` на post.id);
  - владелец: composer заблокирован для остальных, «Написать автору» —
    кнопка 1:1-чата (hello уже несёт pubkey владельца).
- Локальные метки: mute/папки/архив — групповая механика (t_folders) as-is.

## 6. Спам/безопасность

- Канальный ключ — секрет; leaked QR = подписка (не катастрофа: read-only,
  умеренный вред = чтение). Ротация через migration-механику §3.3.
- Владелец не может спамить DM: подписчик не раскрывает адрес (кроме hello).
- Relay-спам: pub-лимиты уже есть (free 100/сутки, 429+Retry-After);
  channel_token — write-scoped, отдельный от личных read-токенов.
- Post-подпись: post-конверт шифруется канальным ключом, которого у
  подписчика нет права перехвата — подделка поста возможна только при
  утече broadcast-секрета (как и в Delta Chat; owner_fpr в QR — доп.
  верификация hello-каналом).

## 9. Решения, которые нельзя регрессить

- Stealth: пустые темы везде, классификация по содержанию (18.08).
- Канал не заменяет почту — relay-дубль + email известным (фолбэк-принцип M2.1).
- Подписчик не раскрывает email владельцу (privacy-инвариант, отличие от
  групп; если нужен DM — hello opt-in).
- Владелец = единственный эмиттер (broadcast; Moderator-роль — M2.x, если
  вообще (в Delta Chat нет).
