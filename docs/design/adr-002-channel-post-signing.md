# ADR-002: подпись постов канала владельцем (Ed25519)

Статус: предложение к реализации. Дата: 14.10.2026.
Закрывает дыру, найденную при переводе канальных токенов в Rust (ADR-001, `d247a92`).

## 1. Что не так сейчас

Канальный токен — это bearer-credential, который релей **не проверяет криптографически**.

`tokens.rs::parse_v1` для канальных scope выходит раньше сверки MAC и проверяет
только структуру и kid-связку (`main.rs:320-346`, `channel_matches` = scope-пара
+ равенство `key_id`). Это **не недосмотр**: `channels-protocol.md:126-132`
фиксирует, что токены выводятся клиентом из broadcast-ключа, а релей не владеет
им и проверить `HMAC(broadcast_key, …)` физически не может.

Настоящая причина слабости глубже. Ссылка приглашения содержит сырой
broadcast-ключ (`channels.js:57`: `k=${ch.key}`), и он нужен подписчику для
дешифрования конвертов. Значит **подписчик вычисляет write-токен легитимно**, без
подделки. Никакая серверная проверка токена это не изменит.

Итог: «только владелец публикует» держится только на клиенте —
`App.vue:352` прячет поле ввода, `App.vue:2827/2883` гвардят `is_owner`.
Подписчик с изменённым клиентом публикует в канал владельца.

## 2. Почему «просто подписать посты» недостаточно

Первая идея — владелец подписывает конверт Ed25519, релей проверяет подпись.
Проблема: **владельца и подписчика релей не различает**, у обоих один и тот же
broadcast-ключ. Подписчик зарегистрирует свой публичный ключ как «ключ владельца»
и станет им. Без аутентифицированного канала регистрации схема не работает.

## 3. Предлагаемая схема

Релей умеет проверять **личные** токены (`server_key` у него есть). Это и есть
опора: идентичность владельца устанавливается его личным токеном.

| Элемент | Механизм |
|---|---|
| Регистрация канала | `POST /relay/channel-key` c `Authorization: Bearer <личный write-токен>` + `{kid, pubkey}`. Релей проверяет токен и записывает `kid → (hash личного токена, pubkey)`. Первый claim побеждает; повторная регистрация с другим pubkey отклоняется |
| Публикация | Поле `sig` в `PubRequest` (base64url, 64 Б). Если для `kid` есть pubkey — релей **обязан** проверить подпись конверта и отклонить (401/403) при невалидной |
| Миграция | `kid` **без** регистрации → поведение v1 как сегодня (структура + kid). Регрессии нет, старые каналы живут |
| Выход из конфликта | Ротация ключа канала (`channels-protocol.md` §3.3 уже спроектирована) даёт новый `kid` — владелец регистрирует первым |

Подписываемый байтовый поток, чтобы клиент и релей не разошлись:
`"channel-post:v2\0" ‖ kid_be_u64 ‖ env_id ‖ body` (Ed25519, без base64 между шагами).

## 4. Что появляется в коде

**Клиент (Rust, `src-tauri`)**
- `channel_signing.rs`: пара ключей Ed25519 владельца канала; приватный — в
  `key_store` (не в `channels.json`, там он был бы на виду).
- Команды: `channel_owner_key`, `channel_sign_post`.
- `sendChannelPost`/`sendChannelMeta` подписывают перед `pub`.
- Поле `sig` в запросе; `serde(default)` — старый релей его просто игнорирует.

**Релей (Rust)**
- `channel_keys.rs`: `kid → (owner_hash, pubkey)`, персист в JSON рядом с остальным
  состоянием.
- Эндпоинт регистрации + проверка подписи в `relay_pub` после определения `is_channel`.
- Переходный флаг `VAULT_RELAY_REQUIRE_SIG` (default `off`). Включать только
  когда все живые каналы зарегистрированы — иначе они перестанут публиковать.

**Зависимость:** `ed25519-dalek` отсутствует и в клиенте, и в релее. Это новая
крипто-зависимость; её версия и аудит — предмет явного согласования, а не молчаливого
`cargo add`.

## 5. Порядок развёртывания (без простоя)

1. Релей: проверка подписи **выключена** флагом, эндпоинт регистрации есть,
   хранилище пустое. Публикация идёт как раньше. Ничего не ломается.
2. Клиент: новая сборка устанавливает флаг и шлёт `sig` (relay его игнорирует —
   поле опциональное).
3. Владелец создаёт/открывает канал → клиент регистрирует pubkey на релее.
4. Проверка: релей отвергает публикацию в зарегистрированный канал без валидной
   подписи (тест на живом стенде, не в проде).
5. Когда все каналы зарегистрированы — обсуждаем включение `REQUIRE_SIG`.

## 6. Чего это НЕ решает

- Владелец **не узнаёт**, кто подписчик, — это исходная privacy-цель (§1.2),
  она не меняется.
- Публикация по подписи защищает от подписчика, но не от компрометации
  устройства владельца.
- Личный токен владельца должен оставаться секретным: он и есть доказательство
  права на регистрацию канала.

## 7. Открытый вопрос

Если считать конфликт регистраций неприемлемым, нужна либо передача pubkey
владельца вне релея (тогда релей берёт его из первой подписанной публикации —
но это снова гонка), либо отдельный канал доверия. Пока предлагается «первый
claim побеждает» + ротация как выход; это осознанный компромисс, а не чистое
решение.
