# ADR-006: Vault Sfera — распределённая соцсеть на тех же ключах и транспорте

**Дата**: 19.11.2026
**Статус**: предложение к ревью (до начала кода)
**Основание**: указание владельца 19.11.2026 — следующая часть проекта,
отдельное приложение; медиа у пользователя (свой диск / Google Drive / Яндекс
Диск / API-хранилище), видимость только для контактов и сфер, E2E как в
мессенджере; вся логика — Rust, Vue/JS — только UI; горизонт — видеохостинг,
стриминг и собственное хранилище.
**Связанные документы**: ADR-005 (логика в Rust, границы фич = границы
сервисов), ADR-004 (модульная независимость), `docs/design/channels-protocol.md`
(каналы), `docs/research/social-network-architecture.md` (анализ чужого опыта),
`docs/design/feature-service-map.md` (карта «фича → будущий сервис»).

---

## 1. Решение в одном абзаце

Vault Sfera — **не новая платформа, а новый тип контента в уже существующем
E2E-конверте**. Пост — это типизированное сообщение (как пост канала), медиа —
зашифрованные блобы в хранилище, которое выбрал пользователь, а лента —
локальная агрегация на устройстве. Аудитория — граф контактов мессенджера и
сферы (именованные наборы контактов), поэтому «соцсеть» не требует ни центрального сервера, ни
нового аккаунта, ни отказа от приватности. Приложение — тонкая оболочка Tauri 2
над общим Rust-ядром; **мобильная и десктопная версии обязательны и
равноправны**, терминального клиента нет.

## 2. На кого похожа и на кого ориентируемся

| Что берём | У кого | Почему |
|---|---|---|
| Закрытый граф, «только свои» | **Path** (лимит друзей), **BeReal** (friends-only) | Аудитория — контакты, а не весь интернет; нет публичных счётчиков и вирусности |
| Сферы и адресность | **Google+ Circles** (идея), **Telegram-группы** (механика) | Один пост — разным наборам людей; привычная модель «сфера = набор контактов» |
| Медийная лента | **Instagram** (только UX ленты и просмотрщика) | Сетка, полноэкранный просмотр, свайп; без алгоритма и рекламы |
| Broadcast-канал | **Telegram-каналы**, **Delta Chat Channels** | Один вещает — многие читают; у Delta Chat это уже работает поверх email |
| Типизированные события | **Nostr** (NIP-99 и др.) | Пост/объявление/реакция — типы, а не отдельные подсистемы |
| Переносимый аккаунт и репозиторий | **Bluesky AT Protocol** (PDS) | Личные данные и история — в репозитории пользователя, а не на платформе |
| Медиа у пользователя | **Immich**, **Nextcloud** | Файлы лежат там, где решил владелец; приложение — клиент |
| E2E и группы | **Signal** | Шифрование на устройстве, ключи не уходят на сервер |

**На кого НЕ похожа и почему**: Mastodon/ActivityPub — каждый узел это сервер
с чужим хранилищем и точкой блокировки; Facebook/VK — централизованный профиль,
алгоритм и реклама; Telegram — центральный сервер и отсутствие E2E по
умолчанию. Наш продукт — «закрытая соцсеть, которую нельзя выключить целиком:
контакты, лента и медиа остаются у людей».

**Формулировка для пользователя**: «Лента для своих. Фото и видео лежат в
вашем облаке, провайдер видит только зашифрованные файлы. Кто видит пост,
решаете вы — контакты, сфера или никто».

## 3. Инварианты (не регрессировать)

1. **Нет нового аккаунта.** Идентичность — та же, что в мессенджере: почтовый
   адрес + ключи X25519/Ed25519. Соцсеть не просит регистрацию.
2. **Нет нового транспорта.** Доставка — те же E2E-конверты, почта и релей;
   stealth (пустые темы, классификация по содержанию) сохраняется.
3. **Провайдер хранилища не видит контент.** Только шифротекст, размер и время.
4. **Лента хронологическая и локальная.** Нет серверного ранжирования, рекламы
   и рекомендаций; нет публичных метрик (лайки не являются рейтингом).
5. **Аудитория явная.** Перед публикацией пользователь видит, кто получит пост
   («Сфера „Семья“ · 6 человек»). Молчаливой публикации «всем» нет.
6. **Логика — в Rust, UI — в Vue.** JS не принимает решений о формате, правах,
   ключах, ретраях и порядке доставки (ADR-005).
7. **Фича не знает про фичу.** Только порты ядра и композиционный корень.
8. **Ключи не покидают устройство.** Никакого серверного сканирования,
   восстановление — только явный эскроу пользователя (как в мессенджере).

## 4. Модель данных: пост = типизированный конверт + манифест медиа

Продолжаем модель исследования 22.08: «всё — типизированное сообщение».
Новые типы (версия 1):

```json
{
  "v": 1,
  "type": "social_post",
  "author": {
    "fp": "xx:xx:…:****",
    "pub_key": "<ed25519 hex, 32 байта>"
  },
  "ts": 1795000000,
  "audience": {
    "id": "aud_<hex>",
    "epoch": 3,
    "spec": { "kind": "all_contacts|sphere|selected|all_except", "...": "параметры вида" }
  },
  "body": "текст или markdown",
  "media": [
    {
      "blob_id": "<sha256(ciphertext), hex 64>",
      "thumb_blob_id": "<...>",
      "mime": "image/jpeg",
      "size": 1048576
    }
  ]
}
```

**Подпись лежит рядом, а не внутри.** Подписывается JCS этой формы (без
`sig`), а сам `sig` хранится в `SignedPost { post, sig }` — иначе подпись была
бы самозависимой. `id`, `device`, `locators`, `width/height`, `chunks` —
дополнительные поля следующих версий; опциональные поля сериализуются только
когда заданы, поэтому подпись уже опубликованных постов не ломается.
Реализовано в `social-post`: `PostV1`, `compose`, `sign_post`, `verify_post`
(подпись — та же `sign_value`/`verify_value` и домен `sfera-post:v1\0`).

Другие типы: `social_profile`, `social_sphere`, `social_reaction`,
`social_comment` (фаза 2), `social_contact_request`, `social_contact_accept`,
`social_contact_decline`, `social_contact_block`, `social_role_grant`,
`social_history_grant`, `social_audience_key` (ротация ключа аудитории),
`social_device_cert` (связанное устройство), `social_repo_head` (репозиторий
автора, §7.4).

**Правила схемы.**
- `v` — версия конверта; неизвестные поля игнорируются, неизвестные типы
  сохраняются как «неподдерживаемое» и не ломают ленту.
- Подпись — Ed25519 по каноническому JSON (JCS), а не по строке: иначе
  перестановка полей ломает проверку.
- **`author` — отпечаток (`xx:…:****`), а не email.** Это ID пользователя: как и
  в мессенджере, он стабилен при смене ящика и решает, кто это
  (`vault-core/identity.rs::fingerprint_from_public_key`). `author_pub` —
  открытый ключ, которым проверяется `sig`; отпечаток выводится из него
  детерминированно (первые 8 байт → `xx:…:****`). Префикс `fp:` в KV-хранилище
  мессенджера — namespace записи, а не часть самого отпечатка. Email в конверте
  — только опциональное поле доставки `deliver_to`, не идентичность.
- `id` детерминирован от автора, `ts` и nonce; повторная отправка не создаёт
  дубль (дедуп как у сообщений).
- Тело и медиа-ключи лежат **внутри** E2E-конверта; провайдер хранилища их не
  получает.

**Аудитории.**
- `all_contacts` — все принятые контакты, которым выдан доступ.
- `sphere` — именованный набор (сфера), членство хранится у автора и
  синхронизируется между его устройствами.
- `selected` — явный список на один пост.
- `all_except` — все контакты, кроме перечисленных (частый случай: «всем,
  кроме работы»).
- **Ключ аудитории** — 32B, эпоха `epoch`; ротация при удалении участника.
  В режиме группы ключ приходит адресно; в режиме канала (broadcast) —
  выводится из broadcast-секрета, как в `channels-protocol.md` §3.1.
  Реализовано в `social-audience` (`AudienceKeys`): эпоха растёт при ЛЮБОМ
  изменении состава, а новый ключ — **свежая случайность, не вывод из
  старого** (иначе удалённый участник вывел бы новый и сохранил доступ).
  История `epoch → key` хранится для чтения уже полученных постов; обёртку
  ключа текущей эпохи каждому текущему участнику делает `social-delivery`
  (`wrap_audience_key` отказывает не-участнику), ключи не сериализуются и не
  уходят в JS.

### 4.1 Контакты: заявка → решение владельца

Отношение двустороннее и подтверждаемое:
`none → requested → contact | declined | blocked`.

1. Новый пользователь находит владельца по QR/ссылке-приглашению (в ней
   **fingerprint и публичный ключ**) или по email, если владелец это разрешил
   (email — лишь подсказка для доставки, не ID).
2. Отправляет `social_contact_request`: **fingerprint**, публичный ключ,
   профиль, подпись, короткое сообщение. `fp` извлекается из подписанного
   ключа, а не из email. Если ключ владельца известен — конверт E2E; если
   известен только адрес — минимальное приглашение без личного содержания.
3. Владелец видит заявку в «Заявках»: профиль, общие контакты, сообщение,
   дата.
4. Решение владельца:
   - **Добавить** → выбрать роль, сферы и показывать ли прошлые посты;
   - **Отклонить** → заявка закрывается (можно молча);
   - **Заблокировать** → новые заявки игнорируются.
5. При добавлении устройство владельца создаёт отношение, выдаёт ключи
   текущих аудиторий и (если включено) историю, отправляет
   `social_contact_accept` с профилем и выданной ролью.
6. **Без устройства владельца заявка не одобряется**: сервера, который сделал
   бы это за него, нет. Это осознанное ограничение serverless-модели.

**Кто может отправлять заявки** — настройка владельца: `link_only`
(по умолчанию), `everyone`, `nobody`. Ссылка-приглашение — capability: её
можно отозвать и перевыпустить.

**Односторонний просмотр** (подписка без взаимности) — фаза 2. В MVP
добавление делает контакт взаимным, а роль ограничивает действия.

### 4.2 Права и роли

Роль — пресет прав, назначенный владельцем конкретному контакту. Роль не
заменяет аудиторию: аудитория решает, **какие посты** человек получит, роль —
**что он может с ними делать**.

| Роль | Видит посты | Медиа | Реакции | История стены | Профиль |
|---|---|---|---|---|---|
| Близкий | все, куда входит | да | да | да | да |
| Друг | все, куда входит | да | да | по настройке | да |
| Знакомый | все, куда входит | да | нет | нет | кратко |
| Ограниченный | все, куда входит | **нет** (ключи медиа не выдаются) | нет | нет | нет |

Точечные переключатели поверх роли: `can_react`, `can_view_media`,
`can_view_history`, `can_see_profile`, `can_request_chat`. Права проверяются
в Rust (`social-rights`), UI только показывает; решение о том, кому выдать
ключ, принимает ядро.

Реализовано (спайк 2): `social-rights::evaluate` сводит отношение × аудиторию ×
роль в одно решение (`Access { delivered, permissions, deny }`); `Role::preset`
повторяет таблицу выше; `social-contacts::transition` — чистый автомат
`none → requested → contact | declined | blocked`. JS матрицу не повторяет:
гейт `rights-contract` проверяет только wire-форму и продуктовые инварианты
(«Ограниченный» без медиа, «Друг» без истории по умолчанию).

**Почему «Ограниченный» реально ограничен.** Тело поста шифруется ключом
аудитории, а ключи медиа заворачиваются **отдельно для каждого получателя**.
Не выдать ключ медиа — значит не отдать файл, а не «спрятать кнопку».

### 4.3 История и изменение доступа

- Новый контакт по умолчанию видит **новые** посты; прошлые — по настройке
  владельца (`history: none | all_contacts | spheres`). При добавлении UI
  показывает, сколько постов откроется: «Аня увидит 42 поста».
- История выдаётся пакетом `social_history_grant`: ключи постов и медиа за
  выбранный период, батчами; устройство владельца должно быть онлайн.
- Удаление контакта: ротация ключа аудитории; новые посты ему недоступны,
  старые копии остаются (свойство E2E, честно пишем в UI).
- Блокировка: отношение `blocked`, заявки игнорируются, ключи не выдаются.

## 5. Медиа: шифрование, чанки, провайдеры

### 5.1 Формат блоба

Конкретная раскладка (все целые — little-endian; заголовок ровно 71 байт):

```
offset size field
0      10    magic = b"VAULTBLOB1"
10     1     ver = 1
11     4     chunk_size(u32)           // по умолчанию 4 MiB, но хранится в заголовке
15     32    blob_id = SHA256(ciphertext)
47     16    nonce_prefix              // 16 случайных байт на блоб
63     8     total(u64)                // длина plaintext в байтах
71     ...   chunks (подряд):

chunk i: ct_i = XChaCha20-Poly1305(file_key,
             nonce = nonce_prefix || i(u64)      // 16 + 8 = 24 байта
             aad   = AAD_DOMAIN || nonce_prefix || i(u64) || total(u64))
         |ct_i| = |pt_i| + 16 (Poly1305 tag)
         |pt_i| = min(chunk_size, total - i*chunk_size); pt_0..n-1, n = ceil(total/chunk_size)
AAD_DOMAIN = b"vaultblob:v1\0"
```

**Почему в AAD стоит `nonce_prefix`, а не `blob_id`.** В черновике было
`aad = blob_id || i || total`, но это циклическая зависимость: `blob_id` есть
SHA-256 шифротекста, то есть **результат** шифрования, и он не может одновременно
быть **входом** в это же шифрование. `nonce_prefix` — случайный на блоб и
известен до шифрования; он даёт ровно то же свойство «чанк из блоба A не вставишь
в блоб B» (подмена ломает AAD), без цикла. `blob_id` остаётся чисто адресом:
SHA-256 шифротекста, который уходит в `Locator`.

- `file_key` — случайные 32 байта на файл; в пост попадает в завёрнутом виде
  (ключом аудитории или ключом получателя).
- Чанки независимы → **Range-запросы и стриминг**: плеер запрашивает нужный
  кусок, не скачивая файл целиком. Это же — фундамент будущего видеохостинга и
  стриминга.
- Миниатюра — отдельный маленький блоб, ключ =
  `HKDF-SHA256(ikm=file_key, salt=none, info="vaultblob:thumb:v1", L=32)`.
- `blob_id` — SHA-256 **шифротекста**: провайдер не может сопоставить одинаковые
  файлы, дедупликация сознательно принесена в жертву приватности. Для двух
  шифрований одного plaintext с разными `file_key`/`nonce_prefix` ID различаются.

### 5.2 Доступ: capability URL + ключ в конверте

Провайдеры (Google Drive, Яндекс Диск, WebDAV, S3) не умеют «доступ для
контактов». Работает простая и переносимая схема:

1. Автор публикует блоб по **неугадываемому пути** (`/vault/blobs/blb_<hash>`)
   и делает ссылку доступной по ссылке (Google Drive «anyone with link»,
   Яндекс «поделиться по ссылке», Nextcloud public share, S3 public-read
   bucket).
2. Ссылка и ключ уходят **только внутри E2E-конверта** получателям.
3. Утечка ссылки бесполезна без ключа; утечка ключа возможна только вместе с
   конвертом (компрометация устройства получателя).

Для будущего **Vault Storage** тот же порт, но доступ строже: подписанные
per-recipient токены и отзыв. Фичи от этого не меняются — меняется адаптер.

### 5.3 Несколько локаций (locators)

У блоба может быть несколько локаций: исходный провайдер + зеркало в Vault
Storage. Это даёт:
- миграцию между провайдерами без перевыпуска постов (добавили локацию —
  старые ссылки живы);
- устойчивость к отзыву ссылки у одного провайдера;
- будущий «переезд в наше хранилище» одной кнопкой.

Порядок локаций — предпочтение, а не истина: клиент пробует по очереди и
запоминает рабочую.

## 6. Хранилище: порт и адаптеры

```rust
pub trait BlobStore: Send + Sync {
    fn caps(&self) -> StoreCaps;                    // public_link, range, quota, auth
    async fn put(&self, id: &BlobId, r: Box<dyn AsyncRead>, size: u64) -> Result<Locator>;
    async fn get(&self, loc: &Locator, range: Option<Range>) -> Result<Box<dyn AsyncRead>>;
    async fn stat(&self, loc: &Locator) -> Result<BlobStat>;
    async fn delete(&self, loc: &Locator) -> Result<()>;
}
```

**Правила.**
- Фичи видят только `BlobStore`, `Locator`, `BlobId`; ни один доменный крейт не
  импортирует HTTP-клиент провайдера.
- Адаптер отвечает за OAuth/ключи, ретраи, лимиты, квоты и преобразование
  ошибок в общий `StorageError`.
- Токены доступа — в OS keychain, не в SQLite и не в логах.

**Порядок подключения (по стоимости входа, а не по популярности).**

| Очередь | Провайдер | Почему так |
|---|---|---|
| 1 | **Устройство** (папка) | Ноль настройки, работает офлайн, честный дефолт |
| 2 | **WebDAV** (Nextcloud/ownCloud) | Простейший протокол, логин/пароль, без OAuth-ревью |
| 3 | **S3-совместимое** (Selectel, VK Cloud, MinIO) | Ключи, public-read, РФ-локализация, дёшево |
| 4 | **Яндекс Диск** | OAuth без долгой верификации, привычен в РФ |
| 5 | **Google Drive** | OAuth-верификация и ограничения `drive.file`; подключать последним |
| 6 | **Vault Storage** | Наш адаптер; тот же порт, плюс токены и отзыв |

Google Drive важен для охвата, но дорог в запуске: экран согласия, верификация,
лимиты. Поэтому он не должен быть единственным путём MVP.

### 6.1 Пресеты провайдеров и ручной ввод (как в почте)

Механизм повторяет `mailProviders.js` мессенджера, но каталог и решение —
в Rust (`storage-providers`), UI только рисует список и поля:

```rust
pub struct StoragePreset {
    pub id: &'static str,          // "nextcloud", "selectel", "custom"…
    pub label: &'static str,
    pub kind: StoreKind,           // WebDav | S3 | OAuth | Local
    pub endpoint: Option<&'static str>,
    pub region: Option<&'static str>,
    pub bucket_template: Option<&'static str>,
    pub auth: AuthKind,            // Password | Token | OAuth | Keys
    pub public_link: bool,
    pub range: bool,
    pub max_file_mb: u32,
    pub hint: &'static str,
}
```

- `detect_by_url(url)` — пользователь вставил ссылку/endpoint, пресет
  подсветился; `preset_fields(id)` — какие поля показать и что предзаполнить.
- `custom` («Другое») — все поля вручную: URL, логин, пароль/токен, bucket,
  регион. Это ровно тот же путь, что «свой IMAP/SMTP» в мессенджере.
- OAuth-провайдеры (Яндекс, Google) полей не показывают — только кнопку входа.
- MVP-каталог: **Устройство**, **Nextcloud/ownCloud** (WebDAV), **Generic
  WebDAV**, **Selectel / VK Cloud / MinIO** (S3), **Яндекс Диск**. Google
  Drive — позже; `kind = OAuth` и пресет закладываются сразу, чтобы добавление
  было данными, а не правкой фичи.
- Новый провайдер = один пресет + адаптер, прошедший `provider-conformance`.
  Лента, пост и медиа не меняются.

## 7. Доставка, лента и репозиторий автора

### 7.1 Доставка

- **Малые аудитории (контакты, сфера)** — адресные E2E-конверты, как групповое
  сообщение: письмо на каждого получателя + релей-дубль.
- **Большие аудитории (канал)** — broadcast-модель `channels-protocol.md`:
  пост в релей с channel-token, подписчики поллят; email-дубль известным.
- Конверт несёт манифест: локации блобов и ключи. Медиа не в письме — только
  ссылки, поэтому лимиты почтового провайдера не мешают.
- Исходящая очередь (outbox) — в Rust, с ретраями и идемпотентностью; UI
  показывает «отправлено N из M», а не врёт «опубликовано».

Реализовано (спайк 7): `social-sync` — `RetryPolicy` (экспоненциальная задержка
с потолком и числом попыток), `Quota` (фиксированное окно по байтам и числу
отправок), `Outbox` (идемпотентная постановка, `due`, `mark_failed`,
`drain_due` с замыканием отправки) и `ingest` (идемпотентная вставка в `Feed`:
подпись проверяется, дубликаты считаются отдельно). Транспорт — тонкий
адаптер, поэтому ядро синхронное и тестируемое.

### 7.2 Лента

- Локальная SQLite-таблица `social_feed` (своя у фичи, не общая с чатами).
- Сортировка хронологическая; фильтры — сфера/контакт/тип медиа; «непрочитанное»
  считается локально.
- Медиа подгружается лениво: сначала миниатюры, полный файл — по тапу.
- Нет серверного счётчика просмотров; «доставлено» и «прочитано» — по желанию,
  как в мессенджере.

Реализовано (спайк 6): `social-feed` — дедуп по
`post_id = SHA-256(canonical_post)`, порядок `ts` по убыванию + `post_id` по
возрастанию (детерминирован между устройствами), локальный read-state;
`restore` перепроверяет подпись и пересчитывает id, поэтому подсунуть чужой id
к валидному посту нельзя. Пост с невалидной подписью в ленту не попадает.
SQLite-адаптер — отдельный слой, ядро ленты от него не зависит.

### 7.3 Офлайн

- Лента и миниатюры читаются без сети.
- Пост можно создать офлайн: он лежит в outbox, шифрование и загрузка медиа
  начнутся при появлении сети; UI честно показывает состояние.

### 7.4 Репозиторий автора (зарезервировано, не MVP)

Личные посты, сферы и профиль складываются в **зашифрованный append-only
репозиторий** в хранилище пользователя (`social_repo_head` указывает на
последний блок). Это даёт:
- синхронизацию между устройствами без сервера (телефон ↔ десктоп);
- перенос аккаунта: новый клиент читает репозиторий по ключу;
- бэкфилл истории новому получателю, если у него есть ключ аудитории.

MVP может жить без репозитория (только envelopes + локальная БД), но формат
манифеста и `device`-подписи закладываются сразу, чтобы не переделывать.

### 7.5 Заявки, ключи и история

- `social_contact_request` уходит на email владельца. Если публичный ключ
  известен (QR/ссылка) — E2E-конверт; если только email — минимальное
  приглашение без личного содержания.
- `social_contact_accept` — E2E на ключ заявителя: профиль, выданная роль,
  ключи текущих аудиторий. Идемпотентен по `(from, to, nonce)`.
- `social_history_grant` — пакет ключей постов и медиа за период; отправляется
  батчами (например, по 50 постов) с прогрессом в UI. Устройство владельца
  должно быть онлайн; иначе заявка ждёт, а не «одобряется сервером».
- `social_contact_decline` — необязательный: молчание тоже допустимо, чтобы
  отказ не превращался в спам. `social_contact_block` — локальное состояние;
  входящие заявки от заблокированного игнорируются.
- Все заявки и выдачи — в outbox с ретраями; повторная доставка не создаёт
  второй контакт и не выдаёт ключ дважды.

### 7.6 Профиль

Профиль — имя, био, аватар и ссылки. Идентичность — отпечаток публичного ключа
(§8), email в профиле нет. Подпись живёт в **отдельном домене**
`sfera-profile:v1\0`, не в общем с постом: один ключ не должен создавать
взаимозаменяемые подписи поста и профиля. Само правило подписи не дублируется —
оба типа вызывают `social_model::post`; JS повторяет только проверку wire-формы
(гейт `profile-contract`).

Реализовано (спайк 8): `social-profile` — `ProfileV1` + `SignedProfile` с
валидацией (имя 1..80, био до 500, до 8 ссылок только `https`/`http`/`mailto`,
аватар — `BlobId`, mime и size > 0, ключ едет отдельно в E2E), `compose` и
`verify_profile`; `ProfileBook` с идемпотентной вставкой и правилом «новее
побеждает» (равный `ts` разрешается детерминированным сравнением канонического
JCS — два устройства выбирают один профиль без переговоров); `restore`
перепроверяет подпись. Кто видит профиль, решает `social-rights` (§4.2).

Реализовано (24.11, адресная публикация): `profile_id` стабилен по публичному
ключу автора; `publication_id` включает каноническую версию и получателя, поэтому
обновление профиля не считается дубликатом в outbox. `social-delivery`
сериализует `SealedEnvelope {v,to,from_x25519,address,wire,header}`: публичный
X25519 отправителя нужен получателю для hybrid KDF, приватный ключ в конверт не
входит. `social-bridge` запечатывает `{profile,avatar_manifest?}` отдельно для
каждого контакта с X25519+ML-KEM; неполный/битый контакт попадает в `skipped`,
не срывая остальную рассылку. `social-app` ставит конверты через
`enqueue_envelope`; без получателей остаётся прежний локальный маркер, который
транспорт честно отклоняет. Композиция публикации вынесена в
`social-app/profile_publish.rs`, корень остаётся делегатом.

Своя пара Sfera (`social-keys`, `encryption.json` 0600) загружается оболочкой
при старте; контакты берутся из проверенного `sfera_link.json` и обновляются при
повторном связывании без перезапуска. `social_upload_avatar` запоминает манифест
и возвращает только `AvatarRef` — ни file key, ни локального пути в JS нет.

Реализовано (24.11, приём и SMTP): `social_receive_profile` открывает конверт
приватными ключами из app data, проверяет подпись профиля, тип и соответствие
манифеста аватара, затем применяет правила `ProfileBook`. Манифест сохраняется
внутри `SferaState`; `social_open_received_avatar` принимает от JS только
`profile_id`, поэтому `file_key_hex` и локатор не покидают Rust. Чужой аватар не
добавляется в собственный каталог и открывается непосредственно по манифесту.

`src-tauri/smtp.rs` подключает delivery-порт только при полном наборе отдельных
`SFERA_SMTP_EMAIL`, `SFERA_SMTP_PASSWORD`, `SFERA_SMTP_SERVER` (и необязательного
`SFERA_SMTP_PORT`, по умолчанию 465). Креды мессенджера не используются.
`social_sync_outbox` запускается явно: только ответ SMTP-сервера переводит запись
в отправленные, ошибка оставляет штатный ретрай. Тестовый plaintext допускается
лишь с `SFERA_SMTP_ALLOW_INSECURE=1` на loopback; production-путь требует TLS.
**IMAP-монитор ещё не реализован**: получение письма и вызов приёма конверта —
следующий шаг; локальный SMTP end-to-end не заменяет живую двустороннюю приёмку.

Реализовано (24.11, явный IMAP-цикл): `social_receive_inbox` по отдельным
`SFERA_IMAP_*` читает INBOX один раз по вызову, без фонового монитора. Сначала
получаются только `BODY.PEEK[HEADER.FIELDS (SUBJECT)]`; полное тело запрашивается
только для темы `sfera-profile:*` через `BODY.PEEK[TEXT]`. Обычные письма телом
не читаются, `STORE`, `RFC822` и установка `\\Seen` не используются. После разбора
IMAP-literal тот же `SferaState::receive_profile_envelope` проверяет и принимает
профиль. Локальный cursor `imap-received.json` (0600, атомарная запись) не даёт
повторно принимать уже успешный UID; отклонённый остаётся кандидатом на ретрай.
Локальный end-to-end прошёл реальный E2E-конверт и подтвердил отсутствие чтения
чужого тела и изменения флагов; внешний IMAP-провайдер пока не проверялся.

UI (25.11): в «Контактах» кнопка «Проверить почту» вызывает этот цикл явно.
После отчёта UI читает профили по fingerprint и показывает имя/аватар; DTO
`social_profile` добавляет `profile_id` из проверенного ключа автора. Манифест
и file key в JS не передаются; удалённое удаление аватара очищает превью.
Принятые профили пока живут в памяти приложения: persistence — следующий шаг,
не следует обещать их наличие после перезапуска.

Persistence (25.11): `keys/received_profiles.json` хранит подписанные профили
и манифесты аватаров (0600, tmp+sync+rename). Запуск повторно проверяет подписи
и связь манифеста с профилем; книга ищется по `author.fp`, а аватар — по
`profile_id`. После нового `SferaState` UI получает их без повторной выдачи
писем. Повреждённый файл даёт ошибку и не затирается пустой книгой.

## 8. Идентичность и связь с мессенджером

Код раздельный, поэтому «тот же аккаунт» — это не общий файл и не вкладка, а
явное связывание двух приложений.

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Отдельный аккаунт в соцсети | Полная независимость | Второй граф контактов, второй ключ, пользователь не поймёт, кому он пишет |
| B. Копия ключей мессенджера | Ноль дублирования | Копия приватного ключа — худший класс утечки; код и данные смешиваются |
| C. **Отдельное приложение + связанное устройство** | Один граф, один аккаунт, ноль копий ключа, код не смешивается | Нужен протокол связывания и аккуратный доступ к ящику |

**Рекомендация C — с первого дня, а не «потом».**

1. **Sfera — отдельное приложение** (`sfera/`), не вкладка мессенджера:
   вкладка неизбежно затащит социальный код в `vault-desktop` и разрушит
   границу, ради которой всё разделяется.
2. **Связывание**: мессенджер показывает QR/файл `vault://link-sfera?…` с
   подписанным bundle: публичный ключ аккаунта, **сертификат устройства**
   Sfera (`social_device_cert`), контакты с ключами, сферы. Приватный ключ
   аккаунта между приложениями **не копируется**.
3. **Подпись постов**: ключ устройства + сертификат; получатель проверяет
   цепочку до ключа аккаунта. Отзыв устройства — новый bundle без него.
4. **Почта**: Sfera входит в тот же ящик своим паролем приложения и читает
   только социальные конверты (`BODY.PEEK[]`, без `\Seen` на чужой почте);
   если провайдер умеет фильтры — отдельная папка. Это снимает главный риск
   «двух клиентов на одном ящике».
5. **Без мессенджера**: «начать с нуля» — новый ключ и ящик, контакты по QR.
   Sfera остаётся самостоятельным продуктом, а не приложением-придатком.
6. Android-обмен между пакетами (content provider/Intent) не строим: связывание
   идёт по QR/E2E, данные — только экспортом/импортом.

Почему не «просто два APK на одном ящике» без правил: два IMAP-клиента
конфликтуют по `\Seen`, монитору и push. Поэтому у Sfera нет монитора всего
ящика: только классифицированные социальные конверты, PEEK и своя папка, где
это возможно.

## 9. Архитектура кода

### 9.1 Два workspace и одно общее ядро

Соцсеть — **отдельный workspace**, не каталог внутри мессенджера. Общий код —
только уже существующий `vault-core` с версией; всё остальное раздельно.
Нового `vault-kernel` не создаём (был бы дубликат рабочего ядра, §9.1.1).

```
whisper/
  vault-core/            # общий: crypto_pq, identity, key_store, relay, settings, transport
  vault-client/          # мессенджер: CLI + ядро обмена (своё workspace)
  vault-desktop/         # мессенджер: Tauri (desktop + Android)
  sfera/                 # соцсеть: своё workspace
    crates/
      social-model/      # типы, схемы, канонический JSON, версии, контракты портов
      social-rights/     # чистые правила: роли, права, матрица ACL (без состояния)
      social-contacts/   # отношения, заявки, роли контактов, блокировки
      social-audience/   # сферы, членство, ключи эпох, правила доступа
      social-post/       # сборка/подпись/валидация поста
      social-media/      # формат блоба, чанкованный AEAD, миниатюры, манифест
      storage-api/       # BlobStore, Locator, BlobId, StorageError
      storage-conformance/ # единый набор проверок семантики для любого адаптера
      storage-local/     # папка устройства (desktop) / SAF (Android)
      storage-webdav/    # Nextcloud/ownCloud
      storage-s3/        # Selectel/VK/MinIO
      storage-yandex/    # Яндекс Диск
      storage-gdrive/    # Google Drive
      storage-vault/     # будущее хранилище Vault
      social-delivery/   # outbox, сборка конвертов, порты email/relay
      social-feed/       # локальная агрегация, порядок, read-state
      social-profile/    # профиль, аватар, ссылки
      social-sync/       # фоновая синхронизация, квоты, ретраи
      social-app/        # композиционный корень: только сборка портов (реализовано, спайк 9)
      social-ffi/        # тонкий слой Tauri-команд (social_*)
    src-tauri/           # оболочка Sfera: Windows/Linux/macOS + Android
    src/                 # Vue UI
    package.json
```

`vault-core` не входит ни в один workspace: оба приложения зависят от него
как от библиотеки (path/версия). Это и есть «из одной части можно обращаться
в другую»: обращение идёт через публичный API ядра, а не через исходники
чужого приложения.

Пока Sfera — отдельный workspace в том же репозитории; вынос в отдельный
репозиторий позже не потребует правок, потому что общий только
версионированный `vault-core`.

Правило стрелок: `feature → vault-core | storage-api | social-model |
social-rights`; `feature ↛ feature`; `social-app → все`; `social-ffi →
social-app`. Композиционный корень — единственное место, где фичи видят друг
друга.

Реализовано (спайк 9): `social-app` держит `Feed`, `ProfileBook`, `ContactBook`,
`Outbox`, ключи аудиторий и `Arc<dyn BlobStore>`; facade-методы только делегируют
(`publish_post` → `social-post` + outbox, `receive_posts` → `ingest`,
`access` → `social-contacts` + `social-rights`, `sync_outbox` → ретраи с
замыканием-транспортом). Ни одного правила внутри, время приходит аргументом.
Бюджет корня **305 строк** (было 295/300; +6 — читающий итератор аудиторий
для UI, §19). 24.11 публикация профиля вынесена в `profile_publish.rs`; фактический
размер `lib.rs` — 310 строк (порог 300 не превышать новыми правилами, следующий
инкремент — вынос, а не рост). Гейт `crate-boundary` (`npm run test:boundary`)
фиксирует четыре унаследованных ребра «фича → фича» в baseline и запрещает
новые; проверен негативом.

Пересечение данных между фичами — только через порты, объявленные в
`social-model`: `ContactDirectory` (реализует `social-contacts`),
`AudienceMembership` (реализует `social-audience`), `PermissionPolicy`
(реализует `social-rights`). Композиционный корень связывает реализации;
фичи не импортируют друг друга.

Импорт общего кода разрешён и ожидаем: обе стороны берут `vault-core` (и
другие явно общие крейты). Запрещён импорт **прикладного** кода чужого
приложения: `sfera ↛ vault-desktop`, `vault-desktop ↛ sfera`. Если функция
нужна обоим — она сначала выносится в общий крейт, а не подключается «как
есть». Общая разметка — только токены темы, без компонентов с логикой.

**Извлечение ядра — отдельная партия, а не «заодно».** Ядро уже существует и
рабочее: `vault-core/` (PQ-hybrid `crypto_pq`, `identity`, `key_store`, `relay`,
`settings`, `transport`) — единый источник истины, от которого desktop уже
зависит (`vault-desktop/src-tauri/Cargo.toml`, `vault_core::*` в `key_store.rs`,
`letter_keys.rs`, `groups.rs`, `lib.rs`). Новый `vault-kernel` **не создаётся**:
это был бы дубликат рабочего ядра. Вместо этого роль `vault-kernel` в схемах ниже
выполняет `vault-core`, при необходимости расширенный аддитивно.

Чтобы соцсеть не зависела от мессенджера, остальные примитивы, которые всё ещё
лежат в `vault-client`/мосте, переезжают в `vault-core` с реэкспортом, чтобы
существующие импорты не менялись. Поведение мессенджера не меняется;
доказательство — те же тесты до и после. Партия идёт в отдельной ветке, не
смешивается с продуктовыми правками и проходит чек-лист §9.1.1.

#### 9.1.1 Чек-лист безопасной партии ядра

Извлечение меняет работающий мессенджер — поэтому каждый пункт обязателен,
пропуск означает откат партии. Порядок фиксирован (проверено осенними партиями
ADR-005, 201 модуль / 2340 мутаций / 0 дыр).

1. **Реэкспорт, не разрыв.** `vault-core` оборачивает существующие пути; старые
   `use`-импорты продолжают работать. Ни одного удалённого публичного имени.
2. **Diff публичного API = 0.** Аддитивные изменения — ok; ломающие — только
   мажорная версия и отдельный коммит. Гейт `kernel-api-diff`.
3. **Паттерны мутаций до прогона.** `npm run gate:mutation-patterns` — любой
   «паттерн не найден» означает, что перенос сдвинул якорь; чинить паттерны,
   а не считать зелёным. `cargo fmt` по репозиторию — ЗАПРЕЩЁН (см. AGENTS.md).
4. **Полный прогон затронутого набора** мутаций и `./scripts/test-all.sh`.
   Тесты мессенджера до и после — одинаковые; разница = поведение изменилось.
5. **Качество фронта:** `npm run quality` и `npm run audit:arch` (протокольных
   решений в JS — 0).
6. **JNI/DEX:** если тронут мост — `gate:jni-keep` + `dex-jni-check.mjs` на
   реальном APK/AAB (R8 молча вырезает мост — 28.10 потеряли гудок звонка).
7. **Вход на телефоне НЕ трогать** (правило AGENTS.md); приёмку на X50 гонять
   только по наименее разрушительному пути и не волной повторов входа.
8. **CI `kernel-consumers`:** изменение под `vault-core/**` прогоняет тесты и
   мессенджера, и Sfera; красный хотя бы у одной стороны — правка не принимается.
9. **Отдельный коммит/ветка**, без примеси продуктовых правок; в том же коммите
   — ADR, документация, graphify, OpenViking.

### 9.2 Почему это переживёт вынос в сервисы

Каждая фича уже общается через порт и события, а не через чужую таблицу.
Когда появится видеохостинг или стриминг, это будет ещё один крейт-адаптер
(или процесс), а не правка ленты. Это то же правило, что в
`feature-service-map.md` §4: решения — в Rust, состояние — у владельца,
зависимости — явные.

### 9.3 Изоляция фич: четыре механизма

1. **Контракт, а не вызов.** У фичи есть публичный trait + DTO с версией; чужая
   фича может вызвать только его. Внутренние типы не экспортируются.
2. **Свои данные.** У каждой фичи свой namespace в SQLite и свой каталог; нет
   общих таблиц. Чужое — только через query-порт с устойчивым DTO.
3. **События вместо синхронных цепочек.** `PostPublished`, `BlobStored`,
   `AudienceRotated` — версионированные, идемпотентные (ключ идемпотентности),
   доставка at-least-once. Подписчик не может уронить издателя.
4. **Изоляция отказов.** Команда на границе FFI ловит панику (`catch_unwind`,
   `panic = "unwind"` для социального ядра) и возвращает типизированную ошибку;
   упавший адаптер хранилища показывает «провайдер недоступен», а не роняет
   приложение. Парсеры медиа (видео/аудио) — в отдельном потоке/процессе,
   потому что это недоверенный вход.

### 9.4 Гейты (измеримо, как в мессенджере)

| Гейт | Что запрещает |
|---|---|
| `crate-boundary` | ребро «фича → фича» в Cargo-графе; исключения — только в baseline (гейт реализован: `npm run test:boundary`) |
| `social-logic-ratchet` | решения о формате/правах/ключах/ретраях в TS/JS |
| `schema-version` | изменение поля без повышения `v` и без теста обратной совместимости |
| `blob-contract` | расхождение формата блоба с фикстурой (общая для Rust и JS) |
| `provider-conformance` | адаптер хранилища не проходит единый набор put/get/range/stat/delete/public-link |
| `ui-import` | экран импортирует чужую фичу или лезет в SQLite напрямую |
| `secret-hygiene` | токены провайдеров в логах, JSON или git |

Гейты — не «на будущее»: `crate-boundary` и `blob-contract` пишутся вместе с
первым крейтом, иначе архитектура останется на бумаге.

### 9.5 Почему это не повторит монолит мессенджера

Монолит мессенджера вырос не из злого умысла, а из трёх привычек: god-компонент,
общее состояние и «потом вынесем». Здесь они запрещены конструкцией, а не
дисциплиной.

| Привычка | Запрет | Чем измеряется |
|---|---|---|
| God-компонент | экран не хранит состояние и не принимает решений; только вызовы `social_*` | `ui-logic-ratchet`: 0 решений в `.vue/.ts` |
| Общее состояние | у фичи свои таблицы и каталог; чужое — только через порт | `schema-owner`: таблица с двумя владельцами — ошибка сборки |
| Синхронные цепочки | фича не вызывает фичу; события идемпотентны | `crate-boundary`: ребро «фича → фича» — ошибка |
| «Потом вынесем» | композиционный корень — только сборка, бюджет 300 строк | `root-budget` |
| «Один крейт на всё» | новый домен = новый крейт; публичная поверхность крейта ограничена | `crate-surface` |
| «Тесты потом» | у фичи свой smoke и conformance до появления UI | `feature-dod` |

**Definition of Done для каждой фичи** (без него PR не принимается):
1. публичный trait + DTO с версией;
2. свои миграции и таблицы, ни одной чужой;
3. smoke на контракт + негативный кейс;
4. событие (если фича меняет мир) идемпотентно;
5. ноль импортов других фич;
6. экран вызывает только команды, без логики.

**Бюджеты — ратчет**: могут только уменьшаться. Именно этого не хватило
мессенджеру: метрики появились после того, как монолит уже вырос, и
разбирать пришлось 198 методов в `App.vue`.

**Первая вертикальная срезка** (проверка, что конструкция работает):
`storage-local` + `social-media` + `social-post` + `social-audience` +
`social-feed` + один экран. Если эта срезка проходит без единого импорта
«фича → фича», архитектура доказана до того, как появится второй экран.

### 9.6 Граница с мессенджером: общий код отдельно, прикладной — нет

«Можно обращаться, нельзя смешивать» относится к **прикладному** коду.
Общий код живёт в отдельном крейте и импортируется обеими сторонами — это
нормальный путь, а не нарушение.

1. **Разные workspace, приложения и данные.** У Sfera свой `Cargo.toml`,
   `package.json`, app id, каталог данных, keychain, SQLite и релизный
   конвейер. Она не читает файлы мессенджера и не пишет в них.
2. **Общий код — только в общих крейтах.** `vault-core` и, при
   необходимости, `vault-shared-*`: сюда выносится всё, что нужно обоим.
   Импорт из общего крейта разрешён и ожидаем. Копия одного и того же кода в
   двух приложениях запрещена: копии расходятся.
3. **Прикладной код чужого приложения не импортируется.** Нужна функция из
   мессенджера? Решение до кода: (а) она общая — вынести в `vault-core`
   с тестами и версией; (б) она специфична — написать свою в Sfera. Прямой
   `use` прикладного крейта — ошибка.
4. **Правка общего кода — правка двух продуктов.** Перед коммитом в общий
   крейт: прогнать тесты обоих приложений; посмотреть diff публичного API;
   держать изменения аддитивными и не менять семантику существующих функций.
   Если одной стороне нужно другое поведение — **не менять общий код**, а
   добавить новую функцию/параметр или реализовать локально.
5. **Совместимость — версией, а не синхронной правкой.** `vault-core`
   версионируется; изменения аддитивные, ломающие — мажорные, и оба
   приложения обновляются отдельными коммитами. Одно приложение не может
   «сломать» другое, потому что не собирается с его исходниками.
6. **Обращение — через объявленный контракт.** Разрешено: публичный API
   общего крейта; deep link (`vault://…`); подписанный bundle
   контактов/идентичности (QR/файл); позже — версионированный JSON-мост.
   Запрещено: общий процесс, общая БД, чтение чужих файлов.

**Протокол «нужна функция из другой части».**

1. Проверить, нет ли её в общем крейте.
2. Если нет — решить, общая она или специфичная.
3. Общая → вынести в общий крейт, добавить контрактный тест, оба приложения
   зелёные.
4. Специфичная → написать свою, не трогая чужой код.
5. Если правка общего кода меняет поведение для другой стороны — остановиться:
   добавить новую функцию/параметр или локальную реализацию. Общий код не
   ломается ради одной части.

**Гейты границы.**

| Гейт | Что ловит |
|---|---|
| `app-boundary` | импорт **прикладного** кода между `sfera/` и `vault-*` |
| `kernel-api` | использование внутренностей ядра вместо публичного API |
| `kernel-api-diff` | ломающее изменение публичного API без мажорной версии |
| `kernel-consumers` | изменение общего крейта без тестов обоих приложений (CI) |
| `no-shared-db` | один файл SQLite/каталог на два приложения |
| `release-separation` | общий app id, ключ подписи или релизный скрипт |

`kernel-consumers` — не пожелание, а CI-джоба: любое изменение под
`vault-core/**` запускает тесты и мессенджера, и Sfera; красный хотя
бы у одной стороны — правка не принимается.

Это не бюрократия: именно отсутствие такой границы превращает два продукта
в один монолит, который нельзя менять по частям.

### 9.7 Хранилище: когда выносить в общий крейт

`BlobStore`, `Locator`, `BlobId`, `StorageError` и адаптеры пока живут в
`storage-api`/`storage-*` внутри workspace Sfera. Это **осознанное решение,
а не забывчивость**: по состоянию на 20.11.2026 единственный потребитель
порта — Sfera (9 крейтов), а мессенджер вообще не использует `BlobStore`
(0 упоминаний в `vault-client`, `vault-desktop`, `vault-core`). Выносить порт
сейчас значит менять работающий мессенджер ради будущего потребителя, которого
ещё нет.

Правило выноса (триггер, а не дата):

1. **Второй реальный потребитель.** Как только распределённый видеохостинг,
   видеостриминг или мессенджер начнут писать/читать блобы через этот порт,
   `storage-api` + `storage-conformance` переносятся в общий крейт
   `vault-shared-storage` с реэкспортом из старых путей: ломать 9 импортов
   Sfera в одной партии нельзя.
2. **Адаптеры остаются в Sfera до появления второго потребителя.** Провайдеры (local/WebDAV/S3/…)
   подключаются по пресетам; общим делается только порт и контракт
   conformance. Если видеохостинг захочет тот же WebDAV, он подключает тот же
   адаптер через общий крейт, а не копирует его.
3. **Партия выноса идёт по чек-листу §9.1.1 целиком**: реэкспорт, diff
   публичного API = 0, `gate:mutation-patterns` до прогона, полный прогон
   мутаций и `./scripts/test-all.sh`, `npm run quality` + `audit:arch`,
   `kernel-consumers` зелёный для обеих сторон, отдельный коммит без
   продуктовых правок. Плюс `storage-conformance` обязателен для каждого
   адаптера: новый провайдер = пресет + адаптер + зелёный conformance.
4. **Токены — в OS keychain** (§6), не в SQLite и не в логах; при выносе
   OAuth-адаптеров (Яндекс, Google) это единственное место хранения refresh-
   токенов, общее для всех приложений.

Так архитектура остаётся современной (общий контракт, изолированные
адаптеры, измеримая совместимость), но не ломает запущенный мессенджер
заранее.

## 10. Интерфейс: мобильный и десктопный

Пять вкладок; на десктопе — три колонки с теми же модулями.

```
[ Лента ] [ Контакты ] [ + ] [ Хранилище ] [ Профиль ]
```

1. **Лента** — посты контактов, хронология, фильтры «Все / Сферы / Избранное»,
   сетка медиа, состояние синхронизации, «N новых». Тап — полноэкранный
   просмотрщик (свайп, зум, видео с Range).
2. **Контакты** — входящие и исходящие заявки, принятые контакты с ролями
   (Близкий/Друг/Знакомый/Ограниченный), сферы, «добавить контакт» (QR,
   ссылка, email, из мессенджера). Внутри контакта — права, сферы, история,
   блокировка.
3. **Создать** — текст, медиа (камера/галерея/файл), выбор аудитории чипами,
   предпросмотр «Кто увидит: Сфера „Семья“ · 6 человек», прогресс
   «шифрую → загружаю → отправляю», черновик.
4. **Хранилище** — карточки провайдеров (статус, квота, здоровье), мастер
   подключения (WebDAV: URL/логин; S3: ключи; Яндекс/Google: OAuth), провайдер
   по умолчанию, «Vault Storage — скоро», перенос блобов.
5. **Профиль** — имя, аватар, био, стена, отпечаток ключа и QR, связанные
   устройства, приватность, экспорт.

### 10.1 Десктоп — обязателен, а не «потом»

Десктоп — тот же продукт и те же модули, а не урезанная версия:

- **Раскладка**: левая навигация, центральная лента, правая колонка деталей;
  минимум 1024×700, нормально на 1366×768.
- **Ввод**: drag-and-drop файлов в композер, вставка из буфера, мультивыбор,
  горячие клавиши (j/k, space, Esc), контекстное меню.
- **Хранилище**: локальная папка как полноценный провайдер (нативный путь);
  на Android тот же адаптер работает через SAF/app-private каталог — разница
  только в выборе пути.
- **Системная интеграция**: трей со статусом синхронизации, нативные
  уведомления, открытие медиа в системном просмотрщике по желанию.
- **Сборка**: один Tauri-shell даёт Windows/Linux/macOS и Android; релизный
  конвейер собирает все цели. Терминального клиента нет ни у соцсети, ни в
  планах.
- **Приёмка**: desktop и Android в одном чек-листе; фича не считается готовой,
  пока не проверена на обеих платформах.

**Правила UI.**
- Аудитория видна до публикации, а не после.
- Никаких публичных счётчиков «лайков» как рейтинга; реакции — приватный жест.
- Состояние хранилища видно всегда: «медиа недоступно, провайдер не отвечает»
  лучше, чем пустая сетка.
- Ни один экран не содержит решений: только вызовы `social_*` и отрисовка.

Подробная карта экранов и потоков — `docs/design/social-app-product.md`.

## 11. Совместимость с горизонтом

| Будущая часть | Что переиспользует | Что добавляется |
|---|---|---|
| **Видеохостинг** | `social-media` (чанки, Range), `storage-*`, манифест | Каталог видео, постеры, транскодинг на устройстве/сервисе |

Ключевое: **медиа-слой один**. Видео в соцсети, видео в видеохостинге и
запись стрима — один формат блоба и один порт хранилища. Это и есть
«совместимость частей» на уровне контракта, а не обещание.

## 12. Безопасность, приватность, право

- **E2E**: X25519 + XChaCha20-Poly1305, как в мессенджере; ключи медиа — внутри
  конверта. Сервер и провайдер хранилища не видят ни текста, ни ключей.
- **Метаданные**: провайдер видит размер, время и IP; почта/релей — уже
  существующая модель zero-metadata. IP можно скрывать релеем (premium).
- **Удаление**: удаление поста у автора не отзывает копии у получателей —
  честно пишем в UI; ключ аудитории ротируется, но старые копии остаются
  расшифровываемыми у тех, кто их получил. Это свойство E2E, а не дефект.
- **152-ФЗ / РКН**: уведомление об обработке и трансграничное уведомление уже
  поданы и зарегистрированы (№ 100494543, реестр 168588/77; № 100494565,
  регистрация 18.11.2026). Хранение медиа у зарубежного провайдера по выбору
  пользователя — отдельная трансграничная передача; её надо раскрыть в
  политике и брать согласие. Это не отменяет уведомления, но требует честного
  текста.
- **ОРИ**: соцсеть с UGC может попасть под ст. 10.1 149-ФЗ (организатор
  распространения информации). Контактный граф снижает риск, но не отменяет
  его; до публичного запуска — юридическая проверка. В приложении обязательны
  жалоба на контент и блокировка (механика §3.5 уже есть в мессенджере).
- **Магазины**: RuStore/Google Play требуют модерацию UGC и контакт поддержки;
  E2E не освобождает. Переиспользуем `report-content` и экран правил.

ADR-005 исправлял в мессенджере.

## 14. Открытые вопросы

1. **Комментарии** — отдельный тип (`social_comment`) или реакции + 1:1 чат в
   MVP? Предложение: реакции в MVP, комментарии — фаза 2.
2. **Сферы и «Мой круг» мессенджера**: импортировать состав «Моего круга» в
   сферу или хранить отдельно? Предложение: отдельная сущность с импортом
   состава; слово «круг» в интерфейсе Sfera не используется.
3. **Ротация ключа аудитории** при удалении контакта: перевыпуск всех постов
   или только новых? Предложение: только новых, старые честно помечаем.
4. **Google Drive** — нужен ли в первой публичной версии, учитывая верификацию
   OAuth? Предложение: после Яндекс Диска и S3.
5. **Бренд**: решено 19.11.2026 — официально **Vault Sfera**, коротко Sfera,
   логотип **VS**, цвета — фиолетовый и золотой. В листинге — Vault Sfera,
   на иконке — логотип VS. Проверка ТМ по классам 9/38/42 — до подачи.
   Слово «круг» не используется (в мессенджере есть «Мой круг»): наборы
   контактов называются сферами.
6. **ОРИ** — нужна ли юридическая проверка до запуска или после пилота на
   контактах? Предложение: до публичного запуска, пилот — закрытый.
7. **Доступ Sfera к ящику**: отдельная папка через фильтр провайдера или
   PEEK-классификация без отметок? Предложение: фильтр там, где есть; иначе
   PEEK и строгое правило «не отмечать чужую почту».
8. **Односторонняя подписка** (смотреть без взаимности) — нужна ли в MVP или
   только взаимные контакты? Предложение: MVP — взаимные, подписка — фаза 2.
9. **История для нового контакта**: по умолчанию `none` или `all_contacts`?
   Предложение: `all_contacts` с предпросмотром «сколько постов откроется» и

10. **Роль по умолчанию** для одобренной заявки: «Знакомый» или
    «Ограниченный»? Предложение: «Знакомый» (видит медиа), владелец меняет
    в один тап.
11. **Кто может отправлять заявки** по умолчанию: `link_only` или `everyone`?
    Предложение: `link_only`; «все» — осознанное включение в настройках.

## 15. Что измеряем (а не обещаем)

- **Доставка**: доля постов, дошедших до всех получателей; медиана времени.
- **Медиа**: время до миниатюры, время до первого кадра видео, ошибки Range.
- **Хранилище**: доля успешных put/get по провайдеру, квоты, отзывы ссылок.
- **Приватность**: ноль ключей и текста в логах/сети (тест-перехват), ноль
  чужих получателей в аудитории (тест на пересечение).
- **Изоляция**: ноль рёбер «фича → фича», ноль решений в JS, ноль падений
  приложения при отказе одного адаптера.
- **Граница с мессенджером**: ноль импортов прикладного кода, ноль копий
  общего кода, правка `vault-core` — тесты обоих приложений зелёные.
- **Контакты и права**: заявка → решение без потери; ноль случаев, когда
  пост или медиа получил не входящий в аудиторию; «Ограниченный» не получает
  ключи медиа (тест на перехват).

## 16. UI: языки и темы (решение владельца 20.11.2026)

Языки интерфейса: **русский, английский, китайский** с возможностью добавить
другие. Добавление языка = один файл `src/locales/<code>.js` + одна строка в
реестре `BUILTIN`; пропущенный ключ ловит гейт `tests/ui/locales-themes.mjs`,
а не молчаливый fallback в проде.

Стили оформления — те же, что в мессенджере: **фиолетовый** акцент
(`#6366f1` / `#818cf8`) и **янтарный** вторичный (`#f59e0b` / `#fbbf24`,
подписка/квоты/предупреждения). Три темы: `dark`, `light`, `amber`; базовые
токены (`--font-sans`, `--radius-*`, `--shadow-sm`) объявлены в каждой теме,
чтобы не повторить дефект мессенджера с несуществующим `--accent`.

UI — только строки и CSS-переменные. Протокол, подписи, права, ключи и
форматы остаются в Rust: гейт запрещает соответствующие имена в
`src/locales` и `src/themes`. Клиенты: мобильный и десктоп; CLI, в отличие от
мессенджера, не планируется.

## 17. Организации и монетизация (решение PM 20.11.2026)

Требование владельца: интерфейс не нагруженный, но с возможностями современной
соцсети; в горизонте — аккаунты организаций для монетизации. Выбранный вариант:

1. **Один граф на аккаунт.** Организация — не второй тип ленты и не «страница»
   внутри пользователя, а **аккаунт с другим типом** (`AccountKind::Person |
   Organization`). У неё те же примитивы: ключ, отпечаток, сертификат
   устройства, репозиторий, лента. Это устраняет дублирование логики и позволяет
   подключить organization-аккаунт как обычный контакт.
2. **Права и роли — в Rust, в `social-rights`.** Организация получает роли
   `Owner`/`Admin`/`Editor`/`Viewer` не как новую систему прав, а как
   `RoleOverrides` поверх существующей матрицы. Никакой отдельной модели
   доступа в UI.
3. **Монетизация через существующие примитивы, а не через новый биллинг в UI.**
   Платные возможности: (а) каналы/аудитории свыше лимита, (б) premium-релей
   (быстрая доставка), (в) расширенное хранение блобов. Все три уже имеют
   Rust-порты (`social-sync::Quota`, `social-transport`, `BlobStore`); UI только
   показывает состояние и цену, полученную с сервера (как в мессенджере:
   `GET /relay/plans`). Никаких цен и правил в JS.
4. **Лёгкий интерфейс.** Пять вкладок, без левой колонки «ещё 20 функций».
   Организации и платные возможности появляются контекстно (в профиле и в
   хранилище), а не отдельными вкладками. Современность = быстрые действия,
   ясные состояния, а не число кнопок.
5. **Порядок работ.** Сначала каркас UI на существующих Tauri-командах и
   локалях, затем organization-тип в Rust с тестами, затем монетизация как
   контракт сервера. Не начинать с биллинга: нечем платить, пока нет продукта.

Этот выбор фиксирует, чтобы UI не разросся и не пришлось переделывать модель
аккаунта при добавлении организаций.

## 18. Мессенджер из Sfera и медиа в хранилище (решение PM 20.11.2026)

**Переключение.** Мессенджер уже регистрирует deep link `vault://open`
(AndroidManifest, M2.3-b). Sfera не гадает по именам пакетов: ОС-адаптер
проверяет, обрабатывается ли ссылка, и передаёт факт в Rust как
`sfera_companion::CompanionProbe`. Единственное решение в Rust: установлен →
`OpenMessenger` (`vault://open`), не установлен → `InstallMessenger`
(`https://vault-msg.ru/`). В UI **одна контекстная кнопка в профиле**, не
отдельная вкладка. Приватный ключ не копируется: связывание по §8.

**Медиа.** Пользователь хранит фото, аудио, видео и файлы. Классификация
(`social_media_kind::classify`) живёт в Rust: UI получает готовый `MediaKind`
и не делает `mime.startsWith`. Неизвестный MIME → `Document` (честный
дефолт). `inline_preview` разрешён для image/audio/video; `needs_range` для
audio/video — это требует поддержки Range от провайдера (§5.1). Содержимое
шифруется в `social-media`; хранилище видит только шифротекст.

**Границы.** Никакого импорта прикладного кода мессенджера, никаких правил в
JS. Новые крейты: `sfera-companion`, `social-media-kind`.

## 19. Каркас интерфейса: Vue-слой и два читающих контракта (решение PM 21.11.2026)

Логика MVP в Rust готова, поэтому следующим шагом собран реальный интерфейс,
а не ещё один слой адаптеров. Решения:

1. **Vue 3 + Vite, пять экранов.** `src/App.vue` только выбирает экран и
   переключает вкладку; `src/views/*.vue` — отрисовка; состояние экранов
   живёт в `src/ui/app.js` и не трогает DOM. Правил протокола, прав, цен и
   форматов в JS нет: всё приходит из Rust.
2. **Два читающих контракта, которых не хватало вкладкам.** `social_contacts`
   отдаёт записи `social-contacts` как есть; `social_audiences` отдаёт
   адресатов уже в форме `PostAudience` (`id`, `epoch`, `spec`). Экран
   «Создать» передаёт выбранный объект обратно без пересборки — UI не
   изобретает эпоху и спецификацию аудитории.
3. **Версия wire и время — не из JS.** Версия берётся из
   `social_api_version`, время поста приходит аргументом; в тесте часы
   подменяются, поэтому сценарий детерминирован.
4. **Языки и темы — данные, а не компоненты.** Три новых ключа
   (`contacts_empty`, `create_no_audience`, `storage_none`) добавлены во все
   три локали; гейт `locales-themes` требует совпадения наборов.
5. **Сборка.** `npm run build` (Vue + Vite) и `npm run test:contract`
   (включая новый гейт `tests/ui/app.mjs`). `node_modules` и `dist` в git не
   попадают.
6. **Бюджет корня.** `social-app` вырос с 299 до 305 строк: добавлен только
   читающий итератор аудиторий, без правил. Потолок 300 поднят осознанно;
   следующая правка корня требует выноса, а не нового роста.

**Что осталось до запускаемого приложения.** Оболочка Tauri (`sfera/src-tauri`),
OS-адаптер deep link `vault://open` для кнопки мессенджера и приёмка на
телефоне. До неё UI собирается и проверяется гейтами, но не запускается как
приложение.

## 20. Оболочка Tauri: ключ устройства, один handler (решение PM 21.11.2026)

Каркас UI собирался без приложения; теперь появилась оболочка `sfera/src-tauri`.

1. **Свой ключ устройства, не копия ключа аккаунта.** Первая версия оболочки
   читала приватный ключ из key store мессенджера — это нарушало §8 (вариант B
   отвергнут: копия приватного ключа — худший класс утечки). Исправлено:
   Sfera создаёт свой Ed25519-ключ при первом запуске, хранит его в app data
   (`identity.json`, права 0600, атомарная запись) и показывает в профиле как
   **ключ устройства**. Аккаунт отображается отдельно как «не связан», пока
   не выполнен протокол `vault://link-sfera` с сертификатом устройства (§8).
   Для разработки seed можно передать `SFERA_SEED`; в логи он не попадает.
   Проверка GUI это и поймала: отпечаток не совпадал с аккаунтом, потому что
   X25519-секрет мессенджера использовался как seed Ed25519.
2. **Один `invoke_handler`.** Tauri допускает только один, а команд три
   крейта. Каждый крейт объявляет `handles(command)` рядом со своими
   командами; оболочка маршрутизирует вызов в нужный handler. Список имён не
   дублируется в оболочке.
3. **Хранилище по умолчанию — локальная папка** в app data Sfera (`blobs/`).
   Выбор провайдера (WebDAV/S3/Яндекс) — следующий шаг; порт `BlobStore` уже
   готов, оболочка его не подменяет.
4. **Квота outbox — MVP-константа** (60 с, 10 МБ, 60 элементов) в оболочке,
   а не в UI. Серверные лимиты придут отдельным контрактом.
5. **Оболочка не входит в workspace ядра.** `src-tauri` исключён из
   `sfera/Cargo.toml`: `cargo test --workspace` проверяет логику без GUI-стека,
   оболочка собирается отдельно (`npm run tauri dev|build`).

**Осталось:** `tauri android init` и сборка APK, OS-адаптер deep link
`vault://open` для кнопки мессенджера, экран связывания устройства (§8) и
команда статуса связывания вместо текущего честного `linked: false`.
