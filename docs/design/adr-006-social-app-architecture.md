# ADR-006: Vault Social (Sfera) — распределённая соцсеть на тех же ключах и транспорте

**Дата**: 19.11.2026
**Статус**: предложение к ревью (до начала кода)
**Основание**: указание владельца 19.11.2026 — следующая часть проекта,
отдельное приложение; медиа у пользователя (свой диск / Google Drive / Яндекс
Диск / API-хранилище), видимость только для контактов и кругов, E2E как в
мессенджере; вся логика — Rust, Vue/JS — только UI; горизонт — видеохостинг,
стриминг и собственное хранилище.
**Связанные документы**: ADR-005 (логика в Rust, границы фич = границы
сервисов), ADR-004 (модульная независимость), `docs/design/channels-protocol.md`
(каналы), `docs/research/social-network-architecture.md` (анализ чужого опыта),
`docs/design/feature-service-map.md` (карта «фича → будущий сервис»).

---

## 1. Решение в одном абзаце

Vault Social — **не новая платформа, а новый тип контента в уже существующем
E2E-конверте**. Пост — это типизированное сообщение (как пост канала), медиа —
зашифрованные блобы в хранилище, которое выбрал пользователь, а лента —
локальная агрегация на устройстве. Аудитория — граф контактов мессенджера и
круги (как группы), поэтому «соцсеть» не требует ни центрального сервера, ни
нового аккаунта, ни отказа от приватности. Приложение — тонкая оболочка Tauri 2
над общим Rust-ядром; мобильная версия первична, десктоп вторичен, терминала
нет.

## 2. На кого похожа и на кого ориентируемся

| Что берём | У кого | Почему |
|---|---|---|
| Закрытый граф, «только свои» | **Path** (лимит друзей), **BeReal** (friends-only) | Аудитория — контакты, а не весь интернет; нет публичных счётчиков и вирусности |
| Круги и адресность | **Google+ Circles** (идея), **Telegram-группы** (механика) | Один пост — разным наборам людей; привычная модель «круг = группа» |
| Медийная лента | **Instagram** (только UX ленты и просмотрщика) | Сетка, полноэкранный просмотр, свайп; без алгоритма и рекламы |
| Broadcast-канал | **Telegram-каналы**, **Delta Chat Channels** | Один вещает — многие читают; у Delta Chat это уже работает поверх email |
| Типизированные события | **Nostr** (NIP-99 и др.) | Пост/объявление/реакция — типы, а не отдельные подсистемы |
| Переносимый аккаунт и репозиторий | **Bluesky AT Protocol** (PDS) | Личные данные и история — в репозитории пользователя, а не на платформе |
| Медиа у пользователя | **Immich**, **Nextcloud** | Файлы лежат там, где решил владелец; приложение — клиент |
| E2E и группы | **Signal** | Шифрование на устройстве, ключи не уходят на сервер |

**На кого НЕ похожа и почему**: Mastodon/ActivityPub — каждый узел это сервер
с чужим хранилищем и точкой блокировки; Facebook/VK — централизованный профиль,
алгоритм и реклама; Telegram — центральный сервер и отсутствие E2E по
умолчанию. Наш продукт — «закрытая соцсеть, которую нельзя выключить целиком:
контакты, лента и медиа остаются у людей».

**Формулировка для пользователя**: «Лента для своих. Фото и видео лежат в
вашем облаке, провайдер видит только зашифрованные файлы. Кто видит пост,
решаете вы — контакты, круг или никто».

## 3. Инварианты (не регрессировать)

1. **Нет нового аккаунта.** Идентичность — та же, что в мессенджере: почтовый
   адрес + ключи X25519/Ed25519. Соцсеть не просит регистрацию.
2. **Нет нового транспорта.** Доставка — те же E2E-конверты, почта и релей;
   stealth (пустые темы, классификация по содержанию) сохраняется.
3. **Провайдер хранилища не видит контент.** Только шифротекст, размер и время.
4. **Лента хронологическая и локальная.** Нет серверного ранжирования, рекламы
   и рекомендаций; нет публичных метрик (лайки не являются рейтингом).
5. **Аудитория явная.** Перед публикацией пользователь видит, кто получит пост
   («Круг „Семья“ · 6 человек»). Молчаливой публикации «всем» нет.
6. **Логика — в Rust, UI — в Vue.** JS не принимает решений о формате, правах,
   ключах, ретраях и порядке доставки (ADR-005).
7. **Фича не знает про фичу.** Только порты ядра и композиционный корень.
8. **Ключи не покидают устройство.** Никакого серверного сканирования,
   восстановление — только явный эскроу пользователя (как в мессенджере).

## 4. Модель данных: пост = типизированный конверт + манифест медиа

Продолжаем модель исследования 22.08: «всё — типизированное сообщение».
Новые типы (версия 1):

```json
{
  "v": 1,
  "type": "social_post",
  "id": "pst_<hex>",
  "author": { "email": "...", "fpr": "<ed25519>" },
  "device": "dev_<hex>",
  "ts": 1795000000,
  "audience": { "id": "aud_<hex>", "kind": "contacts|circle|selected", "epoch": 3 },
  "body": "текст или markdown",
  "media": [
    {
      "blob": "blb_<sha256(ciphertext)>",
      "key": "<32B, base64url>",
      "size": 1048576,
      "mime": "image/jpeg",
      "width": 2048, "height": 1536,
      "thumb": "blb_<...>",
      "chunks": 1,
      "locators": [
        { "provider": "webdav", "url": "https://.../vault/blobs/blb_..." },
        { "provider": "vault",  "url": "https://storage.vault-msg.ru/b/..." }
      ]
    }
  ],
  "sig": "<ed25519 над каноническим JSON>"
}
```

Другие типы: `social_profile`, `social_circle`, `social_reaction`,
`social_comment` (фаза 2), `social_audience_key` (ротация ключа аудитории),
`social_device_cert` (связанное устройство), `social_repo_head` (репозиторий
автора, §7.4).

**Правила схемы.**
- `v` — версия конверта; неизвестные поля игнорируются, неизвестные типы
  сохраняются как «неподдерживаемое» и не ломают ленту.
- Подпись — Ed25519 по каноническому JSON (JCS), а не по строке: иначе
  перестановка полей ломает проверку.
- `id` детерминирован от автора, `ts` и nonce; повторная отправка не создаёт
  дубль (дедуп как у сообщений).
- Тело и медиа-ключи лежат **внутри** E2E-конверта; провайдер хранилища их не
  получает.

**Аудитории.**
- `audience.kind = contacts` — все контакты, у которых есть публичный ключ.
- `circle` — именованный набор (круг), членство хранится у автора и
  синхронизируется между его устройствами; получателю уходит только факт
  «вы входят в аудиторию» и ключ эпохи.
- `selected` — явный список на один пост.
- **Ключ аудитории** — 32B, эпоха `epoch`; ротация при удалении участника.
  В режиме группы ключ приходит адресно; в режиме канала (broadcast) —
  выводится из broadcast-секрета, как в `channels-protocol.md` §3.1.

## 5. Медиа: шифрование, чанки, провайдеры

### 5.1 Формат блоба

```
VAULTBLOB1 | ver=1 | chunk_size=4MiB | blob_id(32) | nonce_prefix(16) | chunks...
chunk i: XChaCha20-Poly1305(file_key, nonce = nonce_prefix || i, aad = blob_id || i || total)
```

- `file_key` — случайные 32 байта на файл; в пост попадает в завёрнутом виде
  (ключом аудитории или ключом получателя).
- Чанки независимы → **Range-запросы и стриминг**: плеер запрашивает нужный
  кусок, не скачивая файл целиком. Это же — фундамент будущего видеохостинга и
  стриминга.
- Миниатюра — отдельный маленький блоб, ключ = `HKDF(file_key, "thumb")`.
- `blob_id` — SHA-256 **шифротекста**: провайдер не может сопоставить одинаковые
  файлы, дедупликация сознательно принесена в жертву приватности.

### 5.2 Доступ: capability URL + ключ в конверте

Провайдеры (Google Drive, Яндекс Диск, WebDAV, S3) не умеют «доступ для
контактов». Работает простая и переносимая схема:

1. Автор публикует блоб по **неугадываемому пути** (`/vault/blobs/blb_<hash>`)
   и делает ссылку доступной по ссылке (Google Drive «anyone with link»,
   Яндекс «поделиться по ссылке», Nextcloud public share, S3 public-read
   bucket).
2. Ссылка и ключ уходят **только внутри E2E-конверта** получателям.
3. Утечка ссылки бесполезна без ключа; утечка ключа возможна только вместе с
   конвертом (компрометация устройства получателя).

Для будущего **Vault Storage** тот же порт, но доступ строже: подписанные
per-recipient токены и отзыв. Фичи от этого не меняются — меняется адаптер.

### 5.3 Несколько локаций (locators)

У блоба может быть несколько локаций: исходный провайдер + зеркало в Vault
Storage. Это даёт:
- миграцию между провайдерами без перевыпуска постов (добавили локацию —
  старые ссылки живы);
- устойчивость к отзыву ссылки у одного провайдера;
- будущий «переезд в наше хранилище» одной кнопкой.

Порядок локаций — предпочтение, а не истина: клиент пробует по очереди и
запоминает рабочую.

## 6. Хранилище: порт и адаптеры

```rust
pub trait BlobStore: Send + Sync {
    fn caps(&self) -> StoreCaps;                    // public_link, range, quota, auth
    async fn put(&self, id: &BlobId, r: Box<dyn AsyncRead>, size: u64) -> Result<Locator>;
    async fn get(&self, loc: &Locator, range: Option<Range>) -> Result<Box<dyn AsyncRead>>;
    async fn stat(&self, loc: &Locator) -> Result<BlobStat>;
    async fn delete(&self, loc: &Locator) -> Result<()>;
}
```

**Правила.**
- Фичи видят только `BlobStore`, `Locator`, `BlobId`; ни один доменный крейт не
  импортирует HTTP-клиент провайдера.
- Адаптер отвечает за OAuth/ключи, ретраи, лимиты, квоты и преобразование
  ошибок в общий `StorageError`.
- Токены доступа — в OS keychain, не в SQLite и не в логах.

**Порядок подключения (по стоимости входа, а не по популярности).**

| Очередь | Провайдер | Почему так |
|---|---|---|
| 1 | **Устройство** (папка) | Ноль настройки, работает офлайн, честный дефолт |
| 2 | **WebDAV** (Nextcloud/ownCloud) | Простейший протокол, логин/пароль, без OAuth-ревью |
| 3 | **S3-совместимое** (Selectel, VK Cloud, MinIO) | Ключи, public-read, РФ-локализация, дёшево |
| 4 | **Яндекс Диск** | OAuth без долгой верификации, привычен в РФ |
| 5 | **Google Drive** | OAuth-верификация и ограничения `drive.file`; подключать последним |
| 6 | **Vault Storage** | Наш адаптер; тот же порт, плюс токены и отзыв |

Google Drive важен для охвата, но дорог в запуске: экран согласия, верификация,
лимиты. Поэтому он не должен быть единственным путём MVP.

### 6.1 Пресеты провайдеров и ручной ввод (как в почте)

Механизм повторяет `mailProviders.js` мессенджера, но каталог и решение —
в Rust (`storage-providers`), UI только рисует список и поля:

```rust
pub struct StoragePreset {
    pub id: &'static str,          // "nextcloud", "selectel", "custom"…
    pub label: &'static str,
    pub kind: StoreKind,           // WebDav | S3 | OAuth | Local
    pub endpoint: Option<&'static str>,
    pub region: Option<&'static str>,
    pub bucket_template: Option<&'static str>,
    pub auth: AuthKind,            // Password | Token | OAuth | Keys
    pub public_link: bool,
    pub range: bool,
    pub max_file_mb: u32,
    pub hint: &'static str,
}
```

- `detect_by_url(url)` — пользователь вставил ссылку/endpoint, пресет
  подсветился; `preset_fields(id)` — какие поля показать и что предзаполнить.
- `custom` («Другое») — все поля вручную: URL, логин, пароль/токен, bucket,
  регион. Это ровно тот же путь, что «свой IMAP/SMTP» в мессенджере.
- OAuth-провайдеры (Яндекс, Google) полей не показывают — только кнопку входа.
- MVP-каталог: **Устройство**, **Nextcloud/ownCloud** (WebDAV), **Generic
  WebDAV**, **Selectel / VK Cloud / MinIO** (S3), **Яндекс Диск**. Google
  Drive — позже; `kind = OAuth` и пресет закладываются сразу, чтобы добавление
  было данными, а не правкой фичи.
- Новый провайдер = один пресет + адаптер, прошедший `provider-conformance`.
  Лента, пост и медиа не меняются.

## 7. Доставка, лента и репозиторий автора

### 7.1 Доставка

- **Малые аудитории (контакты, круг)** — адресные E2E-конверты, как групповое
  сообщение: письмо на каждого получателя + релей-дубль.
- **Большие аудитории (канал)** — broadcast-модель `channels-protocol.md`:
  пост в релей с channel-token, подписчики поллят; email-дубль известным.
- Конверт несёт манифест: локации блобов и ключи. Медиа не в письме — только
  ссылки, поэтому лимиты почтового провайдера не мешают.
- Исходящая очередь (outbox) — в Rust, с ретраями и идемпотентностью; UI
  показывает «отправлено N из M», а не врёт «опубликовано».

### 7.2 Лента

- Локальная SQLite-таблица `social_feed` (своя у фичи, не общая с чатами).
- Сортировка хронологическая; фильтры — круг/контакт/тип медиа; «непрочитанное»
  считается локально.
- Медиа подгружается лениво: сначала миниатюры, полный файл — по тапу.
- Нет серверного счётчика просмотров; «доставлено» и «прочитано» — по желанию,
  как в мессенджере.

### 7.3 Офлайн

- Лента и миниатюры читаются без сети.
- Пост можно создать офлайн: он лежит в outbox, шифрование и загрузка медиа
  начнутся при появлении сети; UI честно показывает состояние.

### 7.4 Репозиторий автора (зарезервировано, не MVP)

Личные посты, круги и профиль складываются в **зашифрованный append-only
репозиторий** в хранилище пользователя (`social_repo_head` указывает на
последний блок). Это даёт:
- синхронизацию между устройствами без сервера (телефон ↔ десктоп);
- перенос аккаунта: новый клиент читает репозиторий по ключу;
- бэкфилл истории новому получателю, если у него есть ключ аудитории.

MVP может жить без репозитория (только envelopes + локальная БД), но формат
манифеста и `device`-подписи закладываются сразу, чтобы не переделывать.

## 8. Идентичность и связь с мессенджером

Три варианта, recommendation — третий.

| Вариант | Плюсы | Минусы |
|---|---|---|
| A. Отдельный аккаунт в соцсети | Полная независимость | Второй граф контактов, второй ключ, пользователь не поймёт, кому он пишет |
| B. Копия ключей мессенджера | Ноль дублирования | Копия приватного ключа — худший класс утечки; два приложения на одном ящике конфликтуют |
| C. **Одно приложение, раздел «Соцсеть»; позже отдельное приложение со связанным устройством** | Один граф, один ключ, быстрый MVP; позже — отдельный APK без форка ядра | Требует экрана-раздела и позже — протокола связывания |

**Рекомендация C.**
1. **MVP**: соцсеть — раздел в существующем приложении (новая вкладка). Контакты,
   ключи, круги — те же; ноль дублирования.
2. **Отдельное приложение** («Vault Social») — только после стабилизации MVP:
   тот же Rust-крейт, отдельная оболочка. Связывание — как у Signal linked
   devices: мастер-устройство выдаёт социальному устройству **сертификат
   устройства** (`social_device_cert`), подписанный ключом аккаунта; посты
   подписываются ключом устройства + сертификатом. Приватный ключ аккаунта
   между приложениями не копируется.
3. Android-обмен между пакетами (content provider/Intent) не строим: это
   хрупко и не нужно, если связывание идёт по QR/E2E.

Почему не «просто два APK на одном ящике»: два IMAP-клиента на одном ящике
конфликтуют по `\Seen`, монитору и push; это уже проверено на практике.

## 9. Архитектура кода

### 9.1 Workspace

```
crates/
  vault-kernel/          # примитивы, выделенные из vault-client (crypto, envelope,
                         # identity, transport ports); не форк и не копия
  social-model/          # типы, схемы, канонический JSON, версии, валидация
  social-audience/       # круги, членство, ключи эпох, правила доступа
  social-post/           # сборка/подпись/валидация поста
  social-media/          # формат блоба, чанкованный AEAD, миниатюры, манифест
  storage-api/           # BlobStore, Locator, BlobId, StorageError
  storage-local/         # папка устройства
  storage-webdav/        # Nextcloud/ownCloud
  storage-s3/            # Selectel/VK/MinIO
  storage-yandex/        # Яндекс Диск
  storage-gdrive/        # Google Drive
  storage-vault/         # будущее хранилище Vault
  social-delivery/       # outbox, сборка конвертов, порты email/relay
  social-feed/           # локальная агрегация, порядок, read-state
  social-profile/        # профиль, аватар, ссылки
  social-sync/           # фоновая синхронизация, квоты, ретраи
  social-app/            # композиционный корень: только сборка портов
  social-ffi/            # тонкий слой Tauri-команд (social_*)
```

Правило стрелок: `feature → vault-kernel | storage-api`; `feature ↛ feature`;
`social-app → все`; `social-ffi → social-app`. Композиционный корень —
единственное место, где фичи видят друг друга.

### 9.2 Почему это переживёт вынос в сервисы

Каждая фича уже общается через порт и события, а не через чужую таблицу.
Когда появится видеохостинг или стриминг, это будет ещё один крейт-адаптер
(или процесс), а не правка ленты. Это то же правило, что в
`feature-service-map.md` §4: решения — в Rust, состояние — у владельца,
зависимости — явные.

### 9.3 Изоляция фич: четыре механизма

1. **Контракт, а не вызов.** У фичи есть публичный trait + DTO с версией; чужая
   фича может вызвать только его. Внутренние типы не экспортируются.
2. **Свои данные.** У каждой фичи свой namespace в SQLite и свой каталог; нет
   общих таблиц. Чужое — только через query-порт с устойчивым DTO.
3. **События вместо синхронных цепочек.** `PostPublished`, `BlobStored`,
   `AudienceRotated` — версионированные, идемпотентные (ключ идемпотентности),
   доставка at-least-once. Подписчик не может уронить издателя.
4. **Изоляция отказов.** Команда на границе FFI ловит панику (`catch_unwind`,
   `panic = "unwind"` для социального ядра) и возвращает типизированную ошибку;
   упавший адаптер хранилища показывает «провайдер недоступен», а не роняет
   приложение. Парсеры медиа (видео/аудио) — в отдельном потоке/процессе,
   потому что это недоверенный вход.

### 9.4 Гейты (измеримо, как в мессенджере)

| Гейт | Что запрещает |
|---|---|
| `crate-boundary` | ребро «фича → фича» в Cargo-графе; исключения — только в baseline |
| `social-logic-ratchet` | решения о формате/правах/ключах/ретраях в TS/JS |
| `schema-version` | изменение поля без повышения `v` и без теста обратной совместимости |
| `blob-contract` | расхождение формата блоба с фикстурой (общая для Rust и JS) |
| `provider-conformance` | адаптер хранилища не проходит единый набор put/get/range/stat/delete/public-link |
| `ui-import` | экран импортирует чужую фичу или лезет в SQLite напрямую |
| `secret-hygiene` | токены провайдеров в логах, JSON или git |

Гейты — не «на будущее»: `crate-boundary` и `blob-contract` пишутся вместе с
первым крейтом, иначе архитектура останется на бумаге.

### 9.5 Почему это не повторит монолит мессенджера

Монолит мессенджера вырос не из злого умысла, а из трёх привычек: god-компонент,
общее состояние и «потом вынесем». Здесь они запрещены конструкцией, а не
дисциплиной.

| Привычка | Запрет | Чем измеряется |
|---|---|---|
| God-компонент | экран не хранит состояние и не принимает решений; только вызовы `social_*` | `ui-logic-ratchet`: 0 решений в `.vue/.ts` |
| Общее состояние | у фичи свои таблицы и каталог; чужое — только через порт | `schema-owner`: таблица с двумя владельцами — ошибка сборки |
| Синхронные цепочки | фича не вызывает фичу; события идемпотентны | `crate-boundary`: ребро «фича → фича» — ошибка |
| «Потом вынесем» | композиционный корень — только сборка, бюджет 300 строк | `root-budget` |
| «Один крейт на всё» | новый домен = новый крейт; публичная поверхность крейта ограничена | `crate-surface` |
| «Тесты потом» | у фичи свой smoke и conformance до появления UI | `feature-dod` |

**Definition of Done для каждой фичи** (без него PR не принимается):
1. публичный trait + DTO с версией;
2. свои миграции и таблицы, ни одной чужой;
3. smoke на контракт + негативный кейс;
4. событие (если фича меняет мир) идемпотентно;
5. ноль импортов других фич;
6. экран вызывает только команды, без логики.

**Бюджеты — ратчет**: могут только уменьшаться. Именно этого не хватило
мессенджеру: метрики появились после того, как монолит уже вырос, и
разбирать пришлось 198 методов в `App.vue`.

**Первая вертикальная срезка** (проверка, что конструкция работает):
`storage-local` + `social-media` + `social-post` + `social-audience` +
`social-feed` + один экран. Если эта срезка проходит без единого импорта
«фича → фича», архитектура доказана до того, как появится второй экран.

## 10. Интерфейс (mobile-first)

Пять вкладок; на десктопе — три колонки с теми же модулями.

```
[ Лента ] [ Круги ] [ + ] [ Хранилище ] [ Профиль ]
```

1. **Лента** — посты контактов, хронология, фильтры «Все / Круги / Избранное»,
   сетка медиа, состояние синхронизации, «N новых». Тап — полноэкранный
   просмотрщик (свайп, зум, видео с Range).
2. **Круги** — список кругов, состав, «кто что видит», круг по умолчанию,
   создание/редактирование. Внутри — контакты с ключами и статусом.
3. **Создать** — текст, медиа (камера/галерея/файл), выбор аудитории чипами,
   предпросмотр «Кто увидит: Круг „Семья“ · 6 человек», прогресс
   «шифрую → загружаю → отправляю», черновик.
4. **Хранилище** — карточки провайдеров (статус, квота, здоровье), мастер
   подключения (WebDAV: URL/логин; S3: ключи; Яндекс/Google: OAuth), провайдер
   по умолчанию, «Vault Storage — скоро», перенос блобов.
5. **Профиль** — имя, аватар, био, стена, отпечаток ключа и QR, связанные
   устройства, приватность, экспорт.

**Правила UI.**
- Аудитория видна до публикации, а не после.
- Никаких публичных счётчиков «лайков» как рейтинга; реакции — приватный жест.
- Состояние хранилища видно всегда: «медиа недоступно, провайдер не отвечает»
  лучше, чем пустая сетка.
- Ни один экран не содержит решений: только вызовы `social_*` и отрисовка.

Подробная карта экранов и потоков — `docs/design/social-app-product.md`.

## 11. Совместимость с горизонтом

| Будущая часть | Что переиспользует | Что добавляется |
|---|---|---|
| **Видеохостинг** | `social-media` (чанки, Range), `storage-*`, манифест | Каталог видео, постеры, транскодинг на устройстве/сервисе |
| **Стриминг** | `social-media` Range + WebRTC-стек звонков | Сигналинг «смотрю», live-манифест, запись в блоб |
| **Своё хранилище** | `storage-api` | `storage-vault`: токены, отзыв, квоты, биллинг |
| **Монетизация** | Профиль/каналы | Платные каналы через релей (как в исследовании §4) |
| **Мессенджер** | `vault-kernel`, конверты, контакты | Ничего: социальные типы для него — «неизвестный тип, сохранить» |

Ключевое: **медиа-слой один**. Видео в соцсети, видео в видеохостинге и
запись стрима — один формат блоба и один порт хранилища. Это и есть
«совместимость частей» на уровне контракта, а не обещание.

## 12. Безопасность, приватность, право

- **E2E**: X25519 + XChaCha20-Poly1305, как в мессенджере; ключи медиа — внутри
  конверта. Сервер и провайдер хранилища не видят ни текста, ни ключей.
- **Метаданные**: провайдер видит размер, время и IP; почта/релей — уже
  существующая модель zero-metadata. IP можно скрывать релеем (premium).
- **Удаление**: удаление поста у автора не отзывает копии у получателей —
  честно пишем в UI; ключ аудитории ротируется, но старые копии остаются
  расшифровываемыми у тех, кто их получил. Это свойство E2E, а не дефект.
- **152-ФЗ / РКН**: уведомление об обработке и трансграничное уведомление уже
  поданы и зарегистрированы (№ 100494543, реестр 168588/77; № 100494565,
  регистрация 18.11.2026). Хранение медиа у зарубежного провайдера по выбору
  пользователя — отдельная трансграничная передача; её надо раскрыть в
  политике и брать согласие. Это не отменяет уведомления, но требует честного
  текста.
- **ОРИ**: соцсеть с UGC может попасть под ст. 10.1 149-ФЗ (организатор
  распространения информации). Контактный граф снижает риск, но не отменяет
  его; до публичного запуска — юридическая проверка. В приложении обязательны
  жалоба на контент и блокировка (механика §3.5 уже есть в мессенджере).
- **Магазины**: RuStore/Google Play требуют модерацию UGC и контакт поддержки;
  E2E не освобождает. Переиспользуем `report-content` и экран правил.

## 13. Этапы

| Этап | Объём | Критерий готовности |
|---|---|---|
| **0. Спайки** | формат блоба + conformance-набор хранилищ; канонический JSON и подпись; связанное устройство (прототип) | Фикстура блоба читается Rust и JS; два адаптера (local, WebDAV) проходят один набор тестов |
| **1. MVP в приложении** | круги, текстовые и фото-посты, аудитория, лента, локальное хранилище + WebDAV, жалоба/блокировка | Два аккаунта: пост с фото доходит, фото расшифровывается, чужой контакт не видит; гейты зелёные |
| **2. Отдельное приложение** | оболочка Vault Social, связанное устройство, Яндекс Диск, S3, десктоп | Пост с телефона виден на десктопе через репозиторий; ключ аккаунта не копируется |
| **3. Медиа-расширение** | видео с Range, аудио, альбомы, миниатюры, квоты | Видео играет с середины, не скачивая файл целиком |
| **4. Vault Storage** | адаптер, миграция, тарифы | Блоб переезжает одной кнопкой, старые ссылки живы |

Порядок неслучаен: сначала контракт медиа и порт хранилища, потом UI. Если
начать с UI, формат блоба и права застынут в JS — ровно та ошибка, которую
ADR-005 исправлял в мессенджере.

## 14. Открытые вопросы

1. **Комментарии** — отдельный тип (`social_comment`) или реакции + 1:1 чат в
   MVP? Предложение: реакции в MVP, комментарии — фаза 2.
2. **Круги и мессенджер**: круг = группа мессенджера или отдельная сущность,
   синхронизируемая с группой? Предложение: отдельная, с импортом состава.
3. **Ротация ключа аудитории** при удалении контакта: перевыпуск всех постов
   или только новых? Предложение: только новых, старые честно помечаем.
4. **Google Drive** — нужен ли в первой публичной версии, учитывая верификацию
   OAuth? Предложение: после Яндекс Диска и S3.
5. **Имя продукта**: решено 19.11.2026 — официально Vault Social, коротко
   Sfera; в листинге магазина Vault Social, на иконке и в лаунчере Sfera.
   Проверка ТМ по классам 9/38/42 — до подачи в магазины.
6. **ОРИ** — нужна ли юридическая проверка до запуска или после пилота на
   контактах? Предложение: до публичного запуска, пилот — закрытый.

## 15. Что измеряем (а не обещаем)

- **Доставка**: доля постов, дошедших до всех получателей; медиана времени.
- **Медиа**: время до миниатюры, время до первого кадра видео, ошибки Range.
- **Хранилище**: доля успешных put/get по провайдеру, квоты, отзывы ссылок.
- **Приватность**: ноль ключей и текста в логах/сети (тест-перехват), ноль
  чужих получателей в аудитории (тест на пересечение).
- **Изоляция**: ноль рёбер «фича → фича», ноль решений в JS, ноль падений
  приложения при отказе одного адаптера.
