# Локальная история + инкрементальная синхронизация с email (M1)

Статус: дизайн, реализация после демо M0 (20.08). Вехи: ROADMAP-2026-08-16.md, M1.

## 1. Проблема

Сейчас Desktop при каждом открытии чата заново:
1. фетчит последние 100 писем All Mail + 50 Junk (заголовки),
2. фильтрует по email собеседника, берёт последние 30,
3. фетчит тела (батчем по папкам), расшифровывает, рендерит.

Последствия:
- история ограничена окном 100 писем — старые сообщения недоступны;
- каждое открытие чата = IMAP-трафик и задержка (кэш тел `emailBodyCache`
  живёт только в памяти, после перезапуска всё заново);
- поиск/редактирование/удаление (M1) негде делать — нет локального хранилища.

В CLI та же картина: `MessageIndex` (~/.vault/message_index.json) написан,
но в приём/отправку не подключён.

## 2. Целевая модель

**Локальная БД — источник правды для UI; email — только транспорт.**
Это модель Delta Chat (наш ориентир паритета): письмо скачано один раз,
расшифровано, положено в SQLite — дальше UI читает только БД.

- Храним **расшифрованный текст**: устройство и так является границей
  доверия (на нём приватные ключи), Delta Chat хранит plaintext локально
  по той же причине. Шифровать локальную БД — отдельная задача (SQLCipher),
  в M1 не входит.
- Пересборка `messages = []` при переключении чатов (фикс гонки, коммит
  0530740) остаётся — но данные берутся из БД мгновенно, IMAP не ждём.

## 3. Синхронизация: закладки НЕ по чатам, а по папкам

Идея «закладка на чат» (метка последней синхронизации, искать после неё) —
верная по духу, но **не отображается на IMAP**: у нас нет папки на чат.
Все чаты лежат вперемешку в INBOX/All Mail/Junk, темы пустые (stealth),
принадлежность письму чата определяется только ПОСЛЕ расшифровки
(по конверту {vault:1,...}). Поэтому:

**Закладка = (folder, uidvalidity, last_uid)** — одна на папку, не на чат.

```
sync_state: folder TEXT, uidvalidity INTEGER, last_uid INTEGER
```

Цикл синка (каждые 30 сек поллинг + при входе):
1. Для каждой папки (INBOX, [Gmail]/All Mail, [Gmail]/Junk, Sent):
   - SELECT → проверить UIDVALIDITY. Изменился — папка пересоздана,
     закладка сбрасывается, рефетч окна (см. §6).
   - `SEARCH UID last_uid+1:*` → только новые письма с прошлого синка.
2. Фетч заголовков + тел новых писем (батчем, как уже умеем).
3. Расшифровка, классификация (сообщение/реакция/инвайт/чужое).
4. Upsert в БД по стабильному id (§4). Чужие/не-VAULT письма в БД
   сообщений не попадают (можно хранить факт «есть такое письмо» для
   stealth-картины, но не содержимое).
5. Обновить last_uid = max(UID обработанных).

**Почему не по дате:** в M1 запланирован рандомный Date-заголовок
(zero-metadata, Header Protection) — дата письма перестаёт быть правдой,
закладка по дате сломается собственным же stealth. UID в рамках
UIDVALIDITY монотонен и от дат не зависит.

## 4. Стабильная идентичность сообщения (дедупликация)

Письмо может лежать в INBOX и в All Mail (разные UID!) — без дедупликации
сообщение появится дважды. Ключ записи, по приоритету:
1. `env.id` — id из конверта {vault:1,id,...} (стабилен, уже используется
   для реакций);
2. для legacy-писем без конверта — заголовок `Message-ID` письма;
3. крайний случай — `folder:uid` (тогда дедупликация между папками не
   работает, приемлемо для legacy).

В таблице messages: `id TEXT PRIMARY KEY` (env.id) +
`UNIQUE(folder, uid)` как второй индекс для синка.

## 5. Удаление сообщений — tombstones

Ключевой момент, который поднял вопрос: если сообщение удалено в Vault,
а синк продолжит выгребать его из email — оно **вернётся** в чат.
Решение — могилы:

```
deleted_messages: message_id TEXT PRIMARY KEY, deleted_at TEXT
```

- «Удалить в Vault» = удалить из messages + вставить tombstone.
  Синк при upsert проверяет tombstone и пропускает письмо.
- «Удалить и из почты» (опционально, M1): сверх tombstone — IMAP-удаление
  письма (COPY в Trash + EXPUNGE Trash — см. грабли Gmail в скилле
  vault-e2e-messenger: Deleted+EXPUNGE в All Mail только архивирует).
  У собеседника копия остаётся — полное удаление у обоих это протокольная
  задача (конверт-команда delete, как edit в EditManager), не IMAP.
- Tombstones живут вечно (они крошечные) — иначе отложенный синк воскресит
  сообщение.

## 6. Первый запуск / новый девайс / смена UIDVALIDITY

Полной истории в email может не быть (провайдер чистит, письма удалялись).
Правила:
- первый синк: ограниченное окно (последние N=500 писем на папку), дальше —
  инкрементально. N настраивается; «поднять всю историю» — отдельная
  долгая операция с прогресс-баром;
- новый девайс видит только то, что ещё живо в ящике (local-first, как
  Delta Chat без multi-device-рассылки); синхронизация истории между
  своими устройствами — не цель M1 (достаточно BCC-self для исходящих);
- сброс UIDVALIDITY: рефетч окна N, дедупликация по §4 не даёт дублей.

## 7. Схема (переиспользуем storage/sqlite.rs)

Desktop: скелет `Storage` уже есть (WAL, FK) — оживить, выкинуть мёртвые
таблицы от REST-эры (users/chats в нынешнем виде), добавить:

```sql
CREATE TABLE messages (
    id TEXT PRIMARY KEY,          -- env.id / Message-ID
    chat_peer TEXT,               -- email собеседника или group:<id>
    folder TEXT, uid INTEGER,     -- где лежит письмо (для удаления из почты)
    sender TEXT, direction TEXT,  -- 'in' | 'out'
    body TEXT,                    -- расшифрованный текст
    envelope_json TEXT,           -- имя/аватар/вложения (метаданные)
    sent_at TEXT, received_at TEXT DEFAULT (datetime('now')),
    is_read INTEGER DEFAULT 0,
    UNIQUE(folder, uid)
);
CREATE TABLE sync_state (
    folder TEXT PRIMARY KEY,
    uidvalidity INTEGER, last_uid INTEGER, synced_at TEXT
);
CREATE TABLE deleted_messages (
    message_id TEXT PRIMARY KEY, deleted_at TEXT
);
CREATE INDEX idx_messages_chat ON messages(chat_peer, sent_at);
```

CLI: тот же SQLite вместо JSON-индекса (общий формат ~/.vault/vault.db —
CLI и Desktop смогут читать одну историю; Desktop уже читает
~/.vault/groups.json CLI — прецедент есть).

## 8. Этапы M1

1. **D1**: Storage в Desktop — миграция/инициализация, upsert/select по чату.
2. **D2**: инкрементальный синк (sync_state + SEARCH UID n+1:*) вместо
   «последние 100»; UI читает БД, IMAP-фетч тел — только для новых.
3. **D3**: tombstones + удаление из UI (+ опц. удаление письма из почты).
4. **D4**: поиск по локальной истории (MessageIndex-подобный, но по БД),
   подгрузка старины по скроллу (on-demand фетч тел писем до закладки).
5. **D5**: CLI на ту же БД (общая история CLI/Desktop).

## 9. Не входит

- Шифрование локальной БД (SQLCipher) — отдельная задача безопасности.
- Синхронизация истории между устройствами пользователя.
- Протокольное удаление у собеседника (конверт delete) — вместе с
  редактированием/удалением в M1, но отдельным пунктом.
