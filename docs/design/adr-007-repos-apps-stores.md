# ADR-007: Репозитории, приложения и магазины

**Дата**: 21.11.2026
**Статус**: принято (решение PM)
**Основание**: указание владельца 21.11.2026 — проект будет расширяться;
нужно решить, выносить ли Sfera в отдельный репозиторий, как организовать
взаимодействие частей и будущие публикации в магазины.
**Связанные документы**: ADR-004 (модульная независимость), ADR-005 (граница
Rust/JS), ADR-006 (архитектура Sfera), `docs/design/feature-service-map.md`.

---

## 1. Решение в одном абзаце

Остаёмся в **monorepo**, но каждый продукт — **отдельное приложение** со своим
workspace, версией, тегом, подписью и листингом в магазине. Общий код —
только `vault-core` как версионируемая библиотека. Sfera не импортирует
прикладной код мессенджера и наоборот; взаимодействие — через протокол
(E2E-конверты, deep link, общий key store на устройстве), а не через исходники.
Вынос Sfera в отдельный репозиторий — не «когда-нибудь», а по конкретным
триггерам (§5); до них monorepo дешевле и безопаснее.

---

## 2. Почему не отдельный репозиторий сейчас

| Аргумент за split | Что происходит на практике сейчас |
|---|---|
| Независимые релизы | Релизы уже независимы по тегам и артефактам; репозиторий этому не мешает |
| Права доступа | Владелец один; отдельная команда/подрядчик появятся — тогда и split |
| Размер репозитория | Основной вес — `target/`, он не в git; исходники Sfera малы |
| CI-время | Sfera-джобы кэшируются; общий `vault-core` всё равно требует прогона обоих |
| Открытый код одной части | Пока обе части закрытые; откроем — вынесем именно её |

Главный риск split сейчас — **рассинхрон общего ядра**: правка `vault-core`
требует двух PR, двух версий и ручной синхронизации. В monorepo это один
коммит и гейт `kernel-consumers`, который уже прогоняет мессенджер и Sfera
вместе. Пока ядро меняется чаще, чем раз в неделю, split увеличивает риск
регресса, а не уменьшает.

## 3. Как устроены части проекта

```
whisper/                      # monorepo, один git
  vault-core/                 # общая библиотека: crypto, identity, key_store,
                              # relay, settings, transport. Версионируется.
  vault-client/               # мессенджер: CLI + ядро обмена (свой workspace)
  vault-desktop/              # мессенджер: Tauri (desktop + Android)
  vault-relay/                # сервер доставки
  sfera/                      # соцсеть: свой workspace (38 крейтов + UI + shell)
    crates/
    src/
    src-tauri/
```

Правила, которые уже действуют и не меняются при росте:

1. **Приложение ≠ крейт ≠ сервис.** Крейт — единица логики; приложение —
   установочный пакет; сервис — процесс с сетевым контрактом. Видеохостинг и
   стриминг сначала появляются как крейты Sfera, затем могут стать сервисами
   (ADR-006 §9.2), но не «второй вкладкой».
2. **Стрелки зависимостей.** `feature → vault-core | social-model |
   social-rights`; `feature ↛ feature`; `social-app → все`; `social-ffi →
   social-app`. Между приложениями — **ноль** импортов прикладного кода.
3. **Общее — только в `vault-core`.** Если функция нужна обоим приложениям,
   она сначала переезжает в ядро (аддитивно, с реэкспортом), а не подключается
   «как есть» из чужого приложения.
4. **Идентичность одна на уровне аккаунта, но не через копию ключа.** У Sfera
   свой ключ устройства и сертификат, выданный аккаунтом; приватный ключ
   мессенджера между приложениями не передаётся (ADR-006 §8). Связывание — по
   QR/`vault://link-sfera`; до него Sfera честно показывает «не связан».

## 4. Приложения, магазины и релизы

**Каждый продукт — отдельное приложение.** Не «Vault с режимом соцсети»:
разные package id, разные листинги, разные подписи, разные циклы ревью.

| | Vault (мессенджер) | Sfera (соцсеть) |
|---|---|---|
| Package / bundle id | `com.vault.vault` | `com.vault.sfera` |
| Desktop | Tauri, `vault-desktop/` | Tauri, `sfera/src-tauri/` |
| Android | APK/AAB из `vault-desktop/src` | APK/AAB из `sfera/src` |
| Версия | `vault-desktop/src-tauri/tauri.conf.json` | `sfera/src-tauri/tauri.conf.json` |
| Тег | `vX.Y.Z` | `sfera-vX.Y.Z` |
| Артефакты | `/home/maksim/vault-releases/<версия>/` | `/home/maksim/vault-releases/sfera/<версия>/` |
| Подпись Android | свой keystore | **свой** keystore (не переиспользовать) |

Правила релиза:

1. **Один магазин — один листинг на продукт.** Магазины не любят «два
   приложения в одном»; пользователь ставит то, что ему нужно.
2. **Общий keystore запрещён.** Компрометация одного приложения не должна
   позволять обновлять второе. Ключи — в `~/.hermes/secrets` (вне git).
3. **Версии не синхронизируются искусственно.** Общая версия нужна только
   `vault-core`; у приложений свои.
4. **Тег — на коммит, а не на «хвост».** Проверка `release-tag-check.mjs`
   расширяется на префикс `sfera-`.
5. **Изменение `vault-core` требует зелёных обоих приложений.** Гейт
   `kernel-consumers` в CI уже это делает; при split он станет двумя
   пайплайнами с общим артефактом ядра.

---

## 5. Триггеры выноса Sfera в отдельный репозиторий

Split делается, когда выполнено **хотя бы одно**:

1. Появляется отдельная команда/подрядчик, которым нельзя давать доступ ко
   всему monorepo.
2. Релизный цикл Sfera и мессенджера расходится настолько, что общий CI
   становится узким местом (стабильно > 15 минут на изменение одной части).
3. Нужно открыть исходники только одной части.
4. Магазин/аудит требует раздельного доступа к репозиторию продукта.
5. Размер истории/сборки начинает мешать разработке (не «кажется большим»,
   а измерено: checkout/CI).

До первого триггера split — преждевременная оптимизация. После — переносится
**целиком workspace `sfera/`** (он уже самодостаточен) и подключается к
`vault-core` как к версионируемой зависимости; это и есть проверка, что
граница была настоящей.

---

## 6. Что делаем прямо сейчас

- CI: отдельная проверка Sfera (контракты, workspace, оболочка Tauri) и
  сохранение гейта `kernel-consumers`.
- Релизный документ Sfera: `sfera/RELEASE.md` (десктоп, Android, теги,
  артефакты, листинги).
- Скрипт сборки десктопа: `sfera/scripts/build-desktop.sh`.
- Никаких переносов каталогов и «подготовительных» репозиториев: граница уже
  проверяется гейтами, а не структурой папок.
