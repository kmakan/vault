# Relay-протокол — дизайн-док (M2.1)

Статус: черновик для ревью · Дата: 04.09.2026 · Автор: Vault team
Задача: t_dbb97708 · Веха: M2 (t_m2_channels)

## 1. Цели и нецели

### Цели
1. **Доставка <1с** вместо 30–60с поллинга / ~1–2с IDLE (и то только когда
   IMAP-сессия жива и провайдер не троттлит).
2. **Push при закрытом приложении** на Android без FCM и без постоянного
   foreground-процесса — главный аргумент Premium.
3. **Устойчивость**: конверт идёт двумя путями (email + relay), кто первый —
   тот и доставил. Падение релея = деградация к email-режиму, не к простою.
4. **Приватность не хуже почты**: релей — «труба, не читатель». Он не должен
   узнавать ничего, чего не знает уже почтовый провайдер, а в идеале — и того
   меньше (не видит адресатов вообще).

### Нецели (осознанно вне MVP)
- Анонимность метаданных от релея (follow-up: cover-traffic, см. §9).
- Доставка больших вложений через релей (лимит тела, см. §5.4).
- Децентрализация/ротация релеев (M6; MVP — один сервер на VPS).
- Web Push (browser push) для desktop — только Android/desktop-WS.

## 2. Модель угроз и приватности

Что знает релей о каждом конверте:

| Факт | Email-провайдер | Relay |
|---|---|---|
| Содержание | нет (E2E) | нет (тот же конверт, E2E) |
| Отправитель/получатель | **да** (From/To) | **нет** — только токен получателя (opaque id) |
| Факт переписки A↔B | да | нет (A и B используют разные токены, связь не видна без корреляции времени) |
| Метаданные времени | да | да (минимально необходимые) |

Итого релей по приватности **строже** почты: он не видит адресов вообще.
Это ключевой аргумент Premium («быстрее И приватнее»), и требование к протоколу:
**в relay-конверте не должно быть email-адресов в открытом виде**.

AAD `VAULT` и stealth-свойства почтового пути сохраняются: relay-дубль — тот же
зашифрованный blob, что и в письме.

## 3. Архитектура: дублирование, а не замена

```
Отправитель                          Получатель
    │                                    ▲
    ├─► SMTP (письмо, как сейчас) ───► ящик ─┤ IMAP IDLE (FGS, как сейчас)
    │                                    ▲   │
    └─► POST /relay (тот же конверт) ─► Relay ┘ WS /relay/ws?token=<tok>
                              (хранит ≤N ч, дёргает подписчика)
```

- Отправка: `email_send` + `relay_publish` параллельно (relay — best effort,
  таймаут 3с, ошибка релея НЕ отменяет отправку письма).
- Приём: оба канала дают один и тот же конверт с одним `env.id` → дедуп по
  нему (уже есть: `processedUnreadIds`/envelope id в App.vue).
- Получатель без валидного токена релея просто живёт на email-режиме —
  протокол не ломается, релей опционален по дизайну.

Почему не «relay вместо email»: serverless-принцип. Email — базовый транспорт,
который нельзя выключить; relay — ускоритель. Это же снимает вопрос доступности
(MVP-релей может лежать — переписка не страдает).

## 4. Идентификация: токен подписки

```
token = base64url( key_id(8) ‖ scope(1) ‖ expiry(4) ‖ HMAC-SHA256(server_key, ...) (32) )
```
- `key_id` — ротация server_key без инвалидации всех токенов;
- `scope` — read|write (write = publish, read = только приём);
- `expiry` — unix-секунды, подписка «истекла» = сервер отвечает 402, клиент
  деградирует на email и показывает баннер продления;
- HMAC — stateless-валидация (MVP без БД токенов; выдача — CLI-скрипт на сервере,
  первые 10 токенов ручные, M2.4).
- Привязка к email — на уровне выдачи (журнал), в самом токене email нет.
- Хранение у клиента: kv_store (`relay-token`), экран Настройки→Relay (M2.4).

Токен — секрет. По WS передаётся в первом кадре auth, по HTTP — заголовок
`Authorization: VaultRelay <token>`. TLS обязателен (443).

## 5. Проволочный формат

### 5.1 Публикация (отправитель → релей)

```
POST /relay/pub
Authorization: VaultRelay <write-token>   # опционально: анонимный publish разрешён (см. §9.1)
Content-Type: application/json

{
  "v": 1,
  "to": "<read-token-получателя>",        # релей знает только токен, не email
  "id": "<envelope id, тот же, что в письме>",
  "exp": 1725500000,                       # ttl конверта на релее (unix)
  "body": "<PQ1:... | legacy base64>"      # байт-в-байт как тело письма
}
→ 200 {"ok":true,"mid":"..."} | 402 (подписка истекла) | 413 (перелимит) | 429
```

### 5.2 Получение (получатель → релей)

WebSocket (основной канал, «push»):
```
GET /relay/ws
Authorization: VaultRelay <read-token>
→ сервер шлёт: {"t":"hello","pending":N}
→ каждый новый конверт: {"t":"msg","id":...,"body":...}
→ клиент подтверждает: {"t":"ack","id":...}   (не ack'нутый вернётся при реконнекте)
```
Long-poll fallback (корпоративные прокси, desktop-эконом):
```
GET /relay/poll?wait=25   → 200 [конверты] | 204 таймаут цикла
```

### 5.3 Дедупликация и порядок
- `id` конверта — глобальный (уже генерируется как envelope id); приёмник
  идемпотентен: повтор с тем же id = no-op.
- Порядок не гарантируется (как в почте); клиент сортирует по `ts` конверта.

### 5.4 Лимиты MVP
- тело ≤ 64 KiB (текстовые сообщения и сигнальные конверты звонков проходят;
  вложения — всегда email-путём, релей их не хранит);
- ≤ 200 непрочитанных на токен, ttl ≤ 24ч, дальше FIFO-вытеснение;
- rate-limit: 10 rps publish, 5 rps poll на токен.

## 6. Клиентское поведение

### 6.1 Android
- Есть валидный relay-токен → флаг kv `relay-active=1` → **VaultForegroundService
  не стартует** (главная батарея-прода); WS держит WebView-сессию приложения,
  при уходе в фон — короткий «дотяг» и сон; новые конверты приходят как
  wake-уведомление через… — ВНИМАНИЕ: без FCM разбуждения нет (см. §9.2),
  MVP-формулировка честная: «мгновенно при открытом/недавно закрытом приложении,
  при полном убийстве процесса — доставка при следующем запуске + email-копия
  всё равно лежит в ящике».
- Нет токена / релей недоступен → текущее поведение (FGS+IDLE), без изменений.

### 6.2 Desktop
- WS в service_monitor-подобной Rust-задаче; событие `mail-changed` с тем же
  payload — фронт не различает каналы.

### 6.3 Отправка
- `api.js`: после успешного SMTP — fire-and-forget `relay_publish` (3с таймаут).
- Ошибки релея: лог, без UI-шума; 402 → один баннер «подписка истекла».

## 7. Сервер MVP (M2.2)

- Rust **axum** (общий стек с клиентом, переиспользование типов конвертов),
  systemd на существующем VPS, nginx TLS termination (443), домен
  `relay.vault-msg.ru` (A → .136 или отдельный IP — см. заметку инцидента).
- Хранилище: in-memory HashMap<token_hash, VecDeque<Envelope>> + sqlite-WAL
  персист (переживает рестарт; TTL-очистка cron'ом задачи).
- Никаких БД пользователей, email-адресов, логов тел конвертов (только метрики:
  счётчики pub/recv, размеры, latency).
- Auth: HMAC stateless (§4); server_key в /etc/vault-relay/ (вне git, 600).
- Наблюдаемость: /metrics (counters), journald.

## 8. Совместимость и миграция

- Клиенты без relay-кода: не затронуты (email-путь не меняется).
- Сервер без клиентов: тихо пустой.
- Формат конверта НЕ меняется — relay несёт байты письма как есть; значит
  совместимость desktop↔CLI↔Android сохраняется автоматически (общий wire).
- Версионирование: поле `v` в envelope запроса; сервер принимает v=1.

## 9. Открытые вопросы (решить до M2.3)

1. **Анонимный publish**: разрешить write без токена (антиспам = captcha/PoW)?
   Иначе отправителю нужен токен → «отправь быстрее» продаём обеим сторонам,
   что удваивает трение. Текущий черновик: publish анонимный, read по токену.
2. **Полное убийство процесса на Android**: без FCM разбудить нельзя —
   честная формулировка в продающих текстах (см. §6.1) или unified-push позже.
3. **Корреляция метаданных**: publish и read с одного IP (оба — один юзер) —
   релей может связать пару. Осознанное ограничение MVP; в SECURITY.md добавить.
4. **Формат токена для QR-расшаривания** подписки (дарить Premium?).
5. Лимит 64 KiB: проверить максимальный текстовый конверт с PQ1 (ek 1184B →
   ~1.6 KiB base64) — с запасом, ок; групповые meta-конверты — ок.

## 10. MVP scope (что делаем в M2.2/M2.3)

Сервер: /relay/pub, /relay/ws, /relay/poll, HMAC-auth, in-memory+sqlite, TTL,
лимиты §5.4, /metrics. Клиент: relay_publish в api.js, WS-приёмник в
service_monitor (desktop) и отдельная Rust-задача (Android), дедуп по id,
флаг relay-active → не запускать FGS. Экран/токены — M2.4.

Тесты: roundtrip pub→ws→ack; дедуп двойной доставки (email+relay); 402-деградация;
лимиты 413/429; офлайн-релей = нулевой регресс email-пути (главный тест).
