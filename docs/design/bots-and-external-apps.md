# Боты и внешние приложения в Vault — дизайн-док (M2+)

Статус: черновик для ревью · Дата: 15.09.2026 · Задача: t_m2_channels (follow-up)
Триггер: директива юзера 15.09 — «подключение других приложений, например
Hermes (общаться с ассистентом с телефона как в Telegram) и боты».

## 1. Что уже есть (факты, не планы)

| Компонент | Состояние | Роль для задачи |
|---|---|---|
| Hermes gateway `api_server` | живёт (OpenAI-совместимый HTTP: /v1/chat/completions, /v1/runs, sessions) | любой клиент может общаться с агентом как с чат-моделью |
| Hermes gateway plugin-система | plugin.yaml + adapter.py (BasePlatformAdapter), 0 изменений ядра | путь добавить Vault как платформу Hermes |
| vault-client (Rust) | CLI + библиотека: wire-формат (XChaCha20-Poly1305 + ML-KEM-768), IMAP/SMTP, relay | переиспользуемый крипто/транспорт-слой для бота |
| relay-сервер | VPS, pub/poll/ws, не видит содержимого | мгновенный канал для бота без IMAP-поллинга |

## 2. Два сценария

### 2.1 Сценарий A: «общаться с Hermes с телефона» (юзер ↔ ассистент через Vault)

Пользователь пишет в Vault-чат → ассистент отвечает. Vault = приватный
транспорт до LLM-агента, Telegram-подобный UX, но E2E.

**Архитектура: VaultBot-мост (headless-клиент Vault рядом с Hermes)**

```
Телефон (Vault-приложение) ⇄ email/relay ⇄ [VaultBot-процесс на VPS/десктопе]
                                                │ расшифровывает конверт
                                                │ (ключи бота = «контакт» юзера)
                                                ▼
                                    Hermes gateway api_server
                                    POST /v1/chat/completions
                                    (сессия на юзера, ключ API_SERVER_KEY)
                                                │ ответ
                                                ▼
                                    VaultBot шифрует ответ на ключ юзера
                                    → email/relay → телефон
```

Почему мост, а не «плагин Vault-платформы в Hermes»: плагин Hermes всё
равно должен был бы содержать ВЕСЬ Vault-стек (IMAP, PQ-крипто, конверты)
— это Python-реализация wire-формата, дублирующая vault-client. Мост на
Rust переиспользует готовую библиотеку vault-client (crypto, protocol,
relay-модули), а Hermes-сторона остаётся тонким HTTP-клиентом.

Состав VaultBot (MVP):
1. `vault-client --listen` headless-режим: поллинг/relay-подписка ящика
   бота, расшифровка, очередь входящих (библиотечные модули уже есть).
2. Мостовой слой: входящее сообщение юзера → POST /v1/chat/completions
   (api_server, X-Hermes-Session-Id для непрерывной сессии на юзера) →
   ответ ассистента → encryptVault на pubkey юзера → отправка.
3. Онбординг юзера: у бота обычный Vault-контакт (QR-инвайт как у людей);
   бот отвечает accept-письмом — готово, никаких серверов регистрации.

Приватность: переписка юзер↔бот E2E на участке телефон↔мост; на мосту
расшифровывается по необходимости (как у любого LLM-чата — модель всё
равно видит текст); мост и Hermes живут на своём VPS юзера, не у нас.

Ограничение честно: LLM-провайдер видит текст запроса (это свойство
любого AI-чата, не транспорта). Vault-часть даёт: приватный канал,
stealth-письма, отсутствие третьих messenger-посредников, свои ключи.

### 2.2 Сценарий B: боты вообще (третьи)

Бот = обычный Vault-аккаунт с программным клиентом. Всё уже сходится:
- контакт бота добавляется как обычный контакт (QR/id);
- бот на базе vault-client headless + свой обработчик;
- Relay-канал даёт мгновенность без FGS;
- Мини-приложения (M3, webxdc) — те же боты с UI.

Ничего нового в протоколе НЕ нужно: бот и человек неотличимы на wire
(это свойство E2E — сервер не может классифицировать). Разница только в
кто держит приватные ключи: у бота — процесс, у человека — телефон.

**Bot-API слой (опционально, для экосистемы)**: тонкая Rust-обёртка
`vault-bot-sdk` поверх vault-client: listener + handler-колбэки +
стандартные ответы (typing, read-receipt). ~2-3 дня. НЕ нужен для MVP
сценария A (мост сам себе SDK).

## 3. Что НЕ делаем (и почему)

- **Не встраиваем LLM-клиент в Vault-приложение** (API-ключ в приложении =
  утечка; провайдер видит всё; нарушение «ключи не покидают устройство»
  для контента — отличие: это осознанная опция бота, не дефолт).
- **Не делаем Hermes-платформу внутри Vault-приложения** (двойная
  реализация, нет).
- **Не даём ботам доступ к группам/каналам в MVP** (спам-вектор; сначала
  приватные 1:1-боты, групповые боты — M3+ с ролями).

## 4. Порядок работ (вписывается в текущий M2)

| # | Шаг | Оценка | Зависимость |
|---|---|---|---|
| 1 | `vault-client --listen` (headless poll + relay-sub, очередь) | 1.5д | нет (библиотека готова) |
| 2 | VaultBot-мост → api_server `/v1/chat/completions` | 1д | #1 |
| 3 | Смоук: телефон Максима ↔ бот-аккаунт (vault_msg@bk.ru) ↔ Hermes | 0.5д | #2 |
| 4 | Дока «Боты» на сайты (гайд: как добавить бота, что видит бот) | 0.5д | #3 |
| 5 | (позже) vault-bot-sdk, каталог ботов в каналах | M3 | каналы |

После этого «общаться с Hermes с телефона» = добавить контакт бота и
писать как в Telegram. Vault получает первый «killer-фичей-демо»:
собственный приватный AI-мессенджер без серверов.

## 5. Открытые вопросы

1. Где живёт мост юзера: его VPS/десктоп (self-hosted, наш теперешний
   случай) — ок; «облачный бот Vault» (наш VPS для всех) = отдельный
   продукт-решение (монетизация №7?), НЕ MVP.
2. Сессии Hermes: один агент-профиль на юзера (X-Hermes-Session-Id per
   Vault-контакт) — подтвердить при смоуке.
3. Голосовые юзера боту: STT в мосте (whisper) — M3, MVP текст.
4. Медиа от бота (картинки/графики от ассистента): вложения как у людей —
   уже работает конвертами, просто проверить в смоуке.

## 6. Решения, которые нельзя регрессить

- Бот = обычный аккаунт: никаких «бот-флагов» в wire (E2E-нейтральность).
- Мост не в приложении: ключи бота — на стороне бота, ключи юзера — у юзера.
- api_server-ключ Hermes — секрет моста, не Vault (разные домены доверия).
