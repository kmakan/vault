# ADR-005: Логика в Rust, JS — фронт. Границы фич = границы сервисов

**Дата**: 19.10.2026
**Основание**: прямое указание владельца (19.10.2026) + ADR-004 (независимость как
инвариант), ADR-003 (слои фронтенда), ADR-001 (разрыв ctx).
**Статус**: принят, исполняется. Это план текущего этапа.

---

## 1. Решение владельца (19.10.2026)

> «Язык логики — Rust, JS — только фронт и прослойка. JS стараться избегать в
> логике. Главная цель данного этапа — модульная независимость фич: правка одной
> фичи не должна сказываться на поведении других фич либо всего приложения. Это
> подразумевает минимизацию `ctx` (а лучше полное неиспользование), минимизацию
> JS в логике (а лучше полное неиспользование), минимизацию `App.vue` (только
> вызовы). После добавления в магазины и начала монетизации займёмся расширением
> по архитектуре микросервисов: мессенджер — сервис, распределённая соцсеть —
> сервис, частные видеохостинги пользователей для своих контактов — сервис,
> частный видеостриминг для контактов (возможно, по частной подписке на аккаунт
> стримера)».

Три нормативных следствия: **ноль `ctx`**, **ноль JS в логике**, **`App.vue`
только вызывает**. Четвёртое следствие — горизонт: границы, которые мы проводим
сейчас между фичами, станут границами сервисов.

## 2. Что это меняет в уже принятых решениях

**2.1. Отменяется моя прежняя рекомендация по `t_99f22059`.** Я предлагал удалить
неиспользуемую Tauri-команду `vault_classify_incoming` как «мёртвый код». По новой
рамке Rust-классификатор — не мёртвый код, а **будущий единственный источник
правды**: удалять его означало бы двигаться против решения владельца. Правильная
задача — **подключить** его, а JS превратить в адаптер (решение принимает Rust,
эффекты исполняет JS, пока JS — фронт). Формулировка задач исправлена в
`t_857ee662` и `t_99f22059`.

**2.2. ADR-004 не отменяется, а продолжается.** Его этап A закрыт (0 полей с
несколькими писателями), гейты (циклы, правило слоёв, владельцы ссылок) держат.
Незакрытая часть ровно та, которую называет владелец: `ctx` (686 ссылок, см. исправление в §3) и монолит
`App.vue` (198 методов с собственной логикой).

**2.3. Крипто-граница уже чистая — и это измерено, а не предположено.**
Изначально `audit:arch` показывал «ПЛОХО: крипто-логика в JS» со ссылкой на
`features/invites.js`. Это было **ложное срабатывание инструмента**: шаблон
`/pbkdf2|scrypt|argon2/i` без границ слова находил `scrypt` внутри имени
`isCryptoReady` («i-sCrypt-o»), а отсутствие флага `g` занижало счёт. Исправлено
19.10.2026 (`scripts/audit-arch.mjs`), самопроверка в обе стороны:

* файл с одним `isCryptoReady` — чисто (ложное срабатывание вылечено);
* файл с настоящим вызовом `pbkdf2(...)` — красный (`✗ __audit_fp_probe.js: pbkdf ×1 — KDF в JS`).

После починки вердикт: **крипто-логики в JS нет**, вся криптография идёт в Rust
через 121 команду. Значит «логика в Rust» на этом этапе — про **протокольные
решения, состояние и формат**, а не про крипту. Это меняет порядок работ: начинать
с решений и `ctx`, а не с крипто-«долга», которого нет.

Урок ADR-004 («цифра инструмента верна настолько, насколько проверен инструмент»)
подтвердился во второй раз. Поэтому в плане ниже **W0 (инструменты) идёт первым**.

## 4. Нормативные правила этапа (обязательны для новых правок и ревью)

* **R1. Новая логика — только в Rust.** Ветвление по формату, протоколу, времени
  жизни, состоянию сессии/звонка/группы в JS — это дефект размещения, а не стиль.
* **R2. JS-модуль — либо адаптер к Rust, либо UI.** В шапке модуля написано, что
  он из себя представляет; «адаптер с ветвлениями» запрещён.
* **R3. Ноль `ctx`.** Модуль не берёт состояние из компонента. Данные — у
  владельца (store) или из Rust; зависимость объявляется явным узким списком.
* **R4. `App.vue` — композиционный корень.** Его задача — вызвать и передать;
  методов с собственной логикой должно быть 0.
* **R5. Фича не знает про фичу.** Обмен — через Rust-core (wire-конверты) или
  через store с единственным владельцем. Правило слоёв из ADR-004 в силе.
* **R6. Граница фичи = будущая граница сервиса.** Если часть нельзя вынести в
  отдельный процесс (мессенджер / соцсеть / видеохостинг / стриминг), граница
  проведена неверно.
* **R7. Каждая веха закрывается ратчетом.** Инструмент обязан быть проверен на
  заведомо известном нарушении (подставленном), иначе он измеряет мнение.
* **R8. Контракт границы «фича ↔ композиционный корень» типизирован формой
  данных, а не договорённостью.** Корень отдаёт фиче две вещи — владельца
  состояния и замыкания-зависимости; обе стороны обязаны сходиться:
  (а) поле владельца читается только как `param.state.<поле>` (или как метод из
  фабрики) — `param.<поле>` даёт `undefined` и молча пишет пустоту;
  (б) замыкание принимает РОВНО столько аргументов, сколько ему передаёт фича, и
  в том же порядке — `(k, m) => this.f(k, m)`, без захвата переменной вместо
  аргумента и без подстановки своего контекста вместо присланного.
  Держится `owner-contract-gate` (самопроверка на подставленном нарушении;
  слепота = падение, а не «зелёно»). Оба нарушения lived молча и уронили
  продукт 22.10: архив чатов не наполнялся НИГДЕ, а бакет pending стал строкой и
  поллинг подмешал в чат символы вместо переписки.

UI-состояние (открыт ли попап, позиция меню) остаётся в компоненте — правило
ADR-003 §2; на него R1–R4 не распространяются.

## 6. Порядок работ

Порядок выведен из измерения и риска, а не из удобства.

### W0. Инструменты и ратчеты — ПЕРВЫМ

Без измерения план — мнение; инструмент обязан сначала поймать подставленное
нарушение.

* расширить `audit:arch`: детект протокольных решений в JS (сборка/разбор
  конвертов, `JSON.parse` конвертов, переходы состояний) — с самопроверкой;
* новый ратчет «JS-логика» (ctx + методы с логикой в `App.vue` + файлы с
  протокольными решениями) в `npm run build`, потолок только затягивается;
* подключить `audit:arch` к сборке (сейчас — только вручную).

**Acceptance**: каждое из трёх нарушений (новая `ctx`-ссылка, новый метод с
логикой, разбор конверта в JS), подставленное в код, валит сборку с точным
сообщением; самопроверка зафиксирована в комментарии гейта.

**Статус W0 — ВЫПОЛНЕНО 19.10.2026** (`t_8a422c38`). Три инструмента:
`scripts/lib/arch-metrics.mjs` (единственный код измерения),
`scripts/audit-arch.mjs` (отчёт, код выхода 1 на крипто-логику и провал
самопроверки), `scripts/js-logic-ratchet-gate.mjs` (потолок по трём величинам,
только затягивается). Оба подключены к `npm run build`. Подстановка трёх
нарушений: `1 / 1 / 1 → 0` по коду выхода, тексты в комментарии гейта.
Побочно исправлен **дефект измерения**: `ctx` считался двумя правилами (735
сырых против 686 по гейту) — теперь правило одно, и обе цифры согласованы
(`docs/testing/js-logic-gate.md`).

**Правка инструмента 19.10.2026 (партия `send`).** В `ctx-ratchet-gate`
проверка «рабочая копия эталона не слабее закоммиченной» для
`sharedWriteFields` и «писателей у поля» была записана с обратным знаком:
падало уменьшение. Партия, которая снимает `ctx` с модуля целиком, обязана
уменьшать общие поля — гейт наказывал саму работу. Направление приведено к
`--write`: ослабление — рост ссылок/полей и появление писателя; проверено
подстановкой (рост ссылок, новый писатель, рост `sharedWriteFields` → код 1;
уменьшение → 0).

### W1. Классификация входящих: решение → в Rust

`t_857ee662` + `t_99f22059`. Шаги:

1. расширить Rust `incoming::classify` до паритета по всем ветвям (profile,
   presence, call, poll, channel, group) под общей фикстурой, тот же принцип
   «сколько объявлено — столько проверено»;
2. в `features/incoming.js` вызвать Rust-классификатор; в JS оставить только
   **эффекты** (обработчики звонка, применение профиля, тосты, обновление

3. удалить JS-дубль решений о типе конверта.

**Acceptance**: гейт паритета по всем типам конвертов; в `incoming.js` нет
ветвлений «какой это конверт»; `ctx` модуля 65 → ≤15.

### W2. `ctx` → 0 по батчам (`t_bcb8927a`)

Партия = один модуль, порядок по числу взятых полей: `send` (100),
`messages` (72), `invites` (48), `groups` (45), `recovery` (44),
`calls` (39), `profiles` (37), `duress` (26). Внутри партии: заменить
`ctx.*` на явные `deps` / метод владельца / вызов Rust. После партии — затянуть
потолок `ctx-ratchet` (механика уже есть, повышения не допускает).

**Статус: партия 1 (`attachments`) закрыта 19.10.2026 — модуль 103 → 0.**

- Замена шла **по владельцам состояния** (ADR-004), а не «всё в deps»:
  `activeChat`/`activeChatType`/`currentGroup` — `chatStore` (session-store),
  `peerKeys`/`peerPqKeys` — `identityStore`, `emails` — `mailboxStore`,
  `email` — `sessionStore`, `parseEnvelope`/`isTextMime`/`senderEmail` —
  `message-format.js`, `mediaQuality` — `message-store.js`. Это 62 из 103
  ссылок, и они перестали быть «полями компонента» вовсе.
- В `deps` осталось только то, что принадлежит компоненту: `notes`/`chat`
  (per-app экземпляры владельцев), `groupKeys`, `cryptoReady`, `dodCache` и
  ЭФФЕКТЫ (`buildEnvelope`, `markPending`, `saveCurrentHistory`, `compressImage`,

**W4, десятый срез: последние три решения о состоянии звонка — в ядро. Протокольный долг JS: 3 → 0.**

Это был последний кусок W4, и он потребовал отдельного механизма: **таблицы
ответов ядра**, а не «ещё одного вызова моста».

- **Почему нельзя было просто добавить `await`.** Три оставшихся сравнения
  состояния жили в местах, где ожидание недопустимо или бессмысленно:
  `canCallBack` вызывается из ШАБЛОНА компонента (шаблон не умеет ждать
  промис), а `hangup` — fire-and-forget: `await` внутри сдвинул бы сброс
  состояния на микротаск, и новая машина состояний успела бы начаться, пока
  старая ещё не сброшена (гонка, уже ловившаяся в этом модуле 12.10.2026).
- **Решение — кэш решений ядра.** Ответ «можно ли» зависит ТОЛЬКО от
  состояния, а состояний четыре. Значит, ядро может отдать всю таблицу
  ОДНИМ вызовом (`vault_call_can_table` → `call_state::can_table`), а JS
  закешировать её и читать синхронно. Решение по-прежнему принимает ядро;
  кэш не протухает (таблица выводится из кода ядра и не меняется в рантайме).
  Таблица прогревается один раз при старте приложения (`App.vue::mounted`).
- **Новые вопросы ядра:** `call_idle`, `call_incoming_ringing`,
  `call_outgoing_ringing` — «какое сейчас состояние» (рядом с `call_active`).
  Они же покрывают `wasActive`/`wasIncoming`/`wasOutgoing` в `hangup` — там
  сравнения строк weren't even counted by the meter (the states weren't in its
  list), но по правилу ADR-005 они — решения о протоколе, и они уехали в ядро
  вместе с остальными.
- **Безопасная деградация:** при отказе моста кэш пуст → `canCached` отвечает
  «нельзя». Для «нельзя» безопасный ответ есть всегда (не гасить таймер, не
  отвечать «занято», не начинать звонок); обратное означало бы действие,
  которого мы не проверили.
- **Метрика:** протокольных решений в JS **3 → 0**. **Цель ADR-005 §5
  достигнута: решений о протоколе/формате в JS не осталось.**

**ОСТАЛОСЬ 3 РЕШЕНИЯ В `features/calls.js` — и вот почему они ещё в JS.**
Все три — сравнения состояния звонка, но живут в **синхронных** контекстах,
где мост (асинхронный) недоступен:

- `canCallBack` — вызывается из ШАБЛОНА компонента (`v-if`), шаблон не умеет
  ждать промис;
- `hangup` — по условию fire-and-forget: `await` внутри сдвинул бы сброс
  состояния на микротаск, и новая машина состояний успела бы начаться, пока
  старое ещё не сброшено (гонка, уже ловившаяся в этом модуле);
- обработка терминального сигнала звонка — сравнение идёт в ветке, где
  состояние уже сброшено предыдущим шагом.

Закрыть их можно не «ещё одним вызовом», а **кешем ответов ядра**: ответ
`can(state, question)` зависит только от состояния, состояний конечное число,
значит ответы можно кэшировать и обновлять при смене состояния — тогда
синхронные места читают кэш, а решение по-прежнему принимает ядро. Это отдельная
партия с изменением жизненного цикла состояния звонка, поэтому вынесена из
этих срезов и зафиксирована здесь, а не сделана «на бегу».

функции-адаптера. Теперь он ловит АРИФМЕТИКУ (`ttl * 1000`) и не считает
комментарии (как ctx-счётчик). Добавлены четыре пробы в самопроверку (18/18).
Побочный эффект — честная величина: протокольных решений в JS **67 → 49**
(в 12 файлах вместо 13): ушли ложные срабатывания.

### W4. Протокол и формат — в Rust

`message-format.js` (`parseEnvelope`/`buildEnvelope`), редакции, TTL, реакции,
конверты вложений, состояние звонка (`calls.js`, 1094 строки — сюда же
`t_64e7241a` про Rust-сигнализацию). JS остаётся транспортом доставки.

**Где именно в Rust (прецедент 23.10, `vault::body_absence`).** «В Rust» — это
не «в `src-tauri`». Правило: **протокольное решение живёт в `vault-client`
(общий крейт CLI и десктопа), в мосту остаётся только ввод-вывод** — сессия,
`UID SEARCH`, `UID FETCH`. Причина не эстетическая: `rust-mutation-gate`
меряет покрытие только по `vault-client`, поэтому решение, написанное в мосте,
непроверяемо по построению (так и вышло с «пустой FETCH ≠ рассинхрон» — он
лежал в `email.rs`, и 28 наборов его не видели). Второй доход — переиспользование:
правило, живущее в мосте, недоступно слушателю CLI, и тот со временем пишет свою
версию того же решения. Проверка правила — набор `rust-body-absence` (6 мутаций,
все пойманы): каждая мутация — тот самый дефект, который уже случался (негатив не
помечен → перепрос каждым поллингом; помечен живой uid → письмо потеряно
навсегда; desync при живых телах → reconnect-шторм).

Оставшийся во мосту ввод-вывод (`UID SEARCH`/`UID FETCH`, порядок обращений) тоже
больше не «непроверяем по построению»: с 23.10 есть протокольный стенд —
loopback TLS + настоящий `imap`-клиент в `email/full_scan_tests.rs`, шесть проб
по сценариям правила, negative-контроль проверен (две внесённые регрессии ломают
ровно ожидающие пробы и не задевают остальные).

3. **В CLI ветки «письма себе» не было вовсе** — переписка `From == To` (Key

через 15-45 минут ожидания — то есть дефект протокола мог жить в APK месяцами.

что он и есть безопасность: терминальные сигналы (`call_cancel`/`call_end`/
`call_reject`) проверяются **до** фильтра свежести — просроченный `call_end`
обязан погасить зависший `ringing`, иначе телефон гудит навсегда; граница окна
исключительная; `ts <= 0` не звонит никогда (часы до NTP).

Дыру нашёл гейт, а не устройство: мутация `env_ts <= 0` → `env_ts < 0` **выжила**
— при `ts = 0` письмо отсекалось и так окном свежести, и про «часы не выставлены»
не говорило ничего. Добавлена проба
`request_without_ts_never_rings_even_before_the_clock_is_set` (now=500, ts=0 →
`Silent`), набор стал 10/10 — и 12/12 после того, как во мосту осталось
`matches!(mapped, "accepted" | "rejected")`: это тоже решение о протоколе, оно
переехало как `dismisses_ring`. Ровно этот класс «правильно, но непроверяемо» ратчет
и должен ловить до телефона.

написаны во мосту заново (события — дважды). Теперь ядро само печатает имена

**Почему это было невидимо, а не просто неудобно.** `monitor_invariants.rs` был
вынесен из монитора «чтобы тестировался на хосте» — и тестировался: 13 проб
обычным `cargo test`. Но `rust-mutation-gate` перебирает наборы
`scripts/rust-mutations/sets/*.mjs`, каждый из которых указывает файл внутри
`vault-client`, — то есть предикаты были покрыты тестами и полностью вне
мутационной мерки. Разница существенна: тест проверяет, что поведение
*соответствует намерению автора теста*, мутация проверяет, что поведение
*зависит от числа*. Пока `FRESH_SECS = 15 * 60` лежал во мосту, никто не мог
подложить «14 минут» и посмотреть, заметит ли это проверка; все тесты окон
считают возраст **от самого порога**, поэтому сдвиг числа им невиден в
принципе. Отсюда отдельная проба `thresholds_are_the_numbers_their_names_claim`
— она пинит литералы, и шесть мутаций констант ловятся именно ею.

требовал бы сети, а без теста лексикографическая регрессия («0.1.9» новее
«0.1.255») осталась бы незамеченной до того момента, как клиент перестал бы
получать обновления ровно на переходе минора за девятку. Теперь арифметика

знака, «равные = есть обновление»).

**Что вскрывается такой меркой (не фантазия, а найденное).** Четыре дефекта
вышли наружу вместе с переносом:

1. **Регистр ASCII.** `backup_import` отбраковывал дубли участников по
   `to_ascii_lowercase()`: два адреса одного человека, отличающиеся
   не-ASCII-регистром, проходили как разные — архив с дублем принимался, а
   дальше расходился с нормализованными ключами. Тот же класс, что 23.10
   нашёл в именах папок (`vault::mailbox_names`): кириллица при
   `to_ascii_lowercase()` не понижается, поэтому сравнение не срабатывает
   никогда.
2. **Ключ реестра без нормализации.** `presence.rs` клал heartbeat под
   `email.to_string()`, а читал по `store.get(email)` — `Bob@X` и `bob@x`
   заводили два разных реестра, и «был онлайн N мин назад» терялось в
   зависимости от того, в каком регистре адрес пришёл из письма. Плюс
   пустой адрес заводил запись «ни от кого».
3. **Пустое значение совпадает с пустым.** В слушателе CLI self-копия
   отсекалась условием `m.from.eq_ignore_ascii_case(me)`: при пустом `me`
   (сбой загрузки аккаунта) письмо без `From` молча выбрасывалось, а адрес
   с обрамляющим пробелом не узнавался — то есть бот отвечал сам себе,
   ровно та петля, от которой фильтр защищал.
4. **Одиннадцать сравнений «тот же ли участник» в мосту.** `add_member`,
   `group_invite`, `accept_invite`, `remove_member`, `set_member_role`,
   `merge_members`, `rename_member` искали запись то точным `==`, то
   `to_lowercase()` без обрезки, то `eq_ignore_ascii_case`. Итог: адрес из
   письма в другом регистре или с обрамляющим пробелом заводил ВТОРУЮ запись об
   том же человеке (тот же класс, что группа «Четыре» 06.10.2026, только
   источник — регистр, а не смена почты), а создателя, написанного в другом
   регистре, можно было удалить и понизить с Admin. Сейчас в мосте не осталось
   ни одного собственного сравнения адресов — все идут через
   `identity::same_address` (проба:

**Форма предикатов.** `owns_group` принимает `(created_by, итератор пар

зависеть от того, что у десктопа `groups::Group`, а у CLI

`fingerprint`**, поэтому CLI может отвечать на `owns_group` только адресами —

«вынести предикат» означало бы незаметно врать про CLI-паритет.

2. **Журнал звонков жил в двух пространствах.** Ключ аккаунта строился

   «зашифрован моим ключом» и молча помечался доставленным. `same_fingerprint`
   пустое значение не совпадает ни с чем.

   сравнение с уже записанными было точным `==`: строка `Боб@Почта.ру` в

   стороны в нормальной форме, поэтому и старые, сырые записи списка

**Что вскрывается такой меркой.**

1. **Попап по уже принятой группе возвращался.** Участник, записанный старым
   адресом (смена почты) или в другом регистре, не совпадал ни с создателем, ни
   с составом — и фронт показывал инвайт заново каждый поллинг. Теперь
   `is_mine` решает отпечаток, а адрес и алиасы — fallback; `null` (группа не
   сохранена локально) инвайт НЕ скрывает, и отказ моста тоже не теряет попап.
2. **Создатель в другом написании не считался админом.** `App.vue` сравнивал
   `created_by` точно: кнопки управления составом и ролями не появлялись.
   Обратная сторона того же сравнения: строка создателя, записанная иначе,
   получала кнопку «удалить» и активный выбор роли — действие, которое мост
   затем отказывал. Теперь и видимость, и отказ — из одного ответа
   (`may_remove`/`may_set_role_of`), поэтому UI не предлагает запрещённого.
3. **Один человек добавлялся в группу дважды.** `addManualEmail` сравнивал
   введённый адрес с сырыми записями состава: `Боб@X` и `боб@x` проходили как
   разные, и инвайт уходил «второму». Вопрос формы адреса — `groups_has_member`.
4. **Создатель с другим написанием адреса не мог клонировать группу.**
   `groups-clone.js` сравнивал `src.created_by !== email` — кнопка не
   срабатывала. Теперь право — `is_creator`; если мост не ответил, клона нет
   (не «разрешаем по умолчанию»).
5. **Смена почты не переименовывала группу с адресом в обрамлении.**
   `migrations.js` нормализовал только `toLowerCase()`: строка ` me@old.com `
   под переименование не попадала. Перебор переехал в мост
   (`groups_rename_address` — проход по всем группам один раз, идемпотентно),
   а форма адреса — `identity`.
6. **У детектора не было вида «владение».** ADR-005 показывал 0 решений в JS
   честно только для известных видов: сравнение `created_by` им не ловилось.
   Добавлен вид `identity` (сравнение в любую сторону и через приведение к
   нижнему регистру) с пятью парами самопроверки — «поймано» на трёх формах,
   «не решение» на чтении поля и на переносе адреса.

**Форма ответа и почему одна команда.** «Чья группа», «что мне можно» и «что
можно с каждой строкой» — один и тот же вопрос идентичности, и разными
командами фронт мог бы получить несогласованные ответы (состав перечитан,
права — нет). Поэтому `groups_access` отдаёт всё сразу, а фронт хранит ответ в
`features/group-access.js`: смена группы перезапрашивает права, ответ от
прошлой группы отбрасывается по `groupId` и номеру запроса (иначе медленный
ответ на A включал бы кнопки в только что открытой B), `refreshGroupMembers`
перечитывает и состав, и права. Позиционный `members` — не удобство, а запрет:
сопоставлять адреса во фронте значило бы держать вторую копию их формы.
`groups_has_member` и `groups_rename_address` — отдельные команды, потому что
это точечные вопросы вне открытой группы.

**Партия 3b: окно свежести опроса и снапшот окон — в ядре (23.10, `t_ee90c534`).**
В `features/incoming.js` жили две вещи, принадлежащие протоколу: число
`FRESH_WINDOW_MS = 15 * 60 * 1000` (копия `timings::FRESH_SECS`) и сам предикат
`Date.now() - new Date(m.date).getTime() < FRESH_WINDOW_MS`. Копию числа ещё
можно было бы заменить снапшотом, но предикат — нет: у опроса политика ДРУГАЯ,
чем у монитора. В JS нераспарсенный `Date` давал `NaN < window` → `false`
(не будить), а ядровой `timings::date_fresh_at` осознанно трактует
«неизвестно = свежее», потому что у монитора есть второй рубеж — `ts`
расшифрованного конверта. Просто подставить ядровой предикат значило бы начать
будить телефон по письмам с мусорным `Date` (в т.ч. перехваченным).

| Решение | Где жило | Куда переехало | Мера |
|---|---|---|---|
| окно свежести 15 мин | литерал `FRESH_WINDOW_MS` в `incoming.js` | `timings::FRESH_SECS` + команда `vault_timings_snapshot` | `rust-timings`, `incoming-smoke` |
| «письмо свежее для пуша» | сравнение дат во фронте | `timings::poll_fresh_at` → поле `fresh` ответа `vault_classify_incoming` | `rust-timings` 21/21, `incoming-mut` 7/7 |
| «неизвестный `Date`» в опросе | неявно (NaN-сравнение) | явная политика ядра: `false` для опроса (у монитора — `true`) | `rust-timings` (мутация «опрос будит по неизвестному Date») |
| форматы `Date` | `new Date(...)` во фронте | `timings::parse_date_ms`: RFC 2822 (email) + RFC 3339 (relay-копия) | `rust-timings` (мутация «ISO не разбирается») |

Снапшот окон (`{freshSecs, callStaleMs, ringTimeoutMs, callTombstoneMs,
seenCap}`, camelCase закреплён тестом сериализации) фронт читает лениво, один
раз на сессию, и использует только для диагностики порога. Само решение о
свежести приходит готовым полем `fresh` в том же ответе классификатора — без
второго IPC на письмо. Формат ISO добавлен не «на всякий случай»: relay-копия
собирается на фронте из `env.ts` и приходит ISO, а парсер, знающий только
RFC 2822, объявил бы «неизвестной» каждую мгновенную доставку.

Поведение сохранено: граница окна миллисекундная (как в прежнем JS-предикате),
письмо ровно на пороге не будит, будущее время проходит, неизвестный `Date`

**Отклонение PBKDF2, закреплённое как формат.** При написании KAT выяснилось,

wrap→unwrap внутри одной версии остался бы зелёным. Поэтому KAT
(`kek_matches_archive_vector`) фиксирует ФАКТИЧЕСКИЕ seed и KEK, отклонение
явно описано в `pbkdf2_sha512`, а мутация «исправлено на 4 байта» обязана
падать. Это тот же класс, что и `rust-call-names`: round-trip не видит дрейфа
формата.

**Партия 5c: гибрид PQ-V1 под мутационной меркой (23.10, `t_a2da57c0`).**
`vault-core/src/crypto_pq.rs` был единственным модулем ядра с пробами (10
тестов), но без мутационного набора: плотность держала его в исключениях,
чтобы партия 4e не смешивалась с криптографией. Класс риска тот же, что у
эскроу-архива: соль, домен `info`, порядок `ikm` и каноническая сортировка
pub-ключей — это ПРОТОКОЛ. Обе стороны считают одной константой, поэтому
round-trip остаётся зелёным при любом дрейфе домена, а уже отправленные
конверты молча перестают открываться.

| Решение | Где жило | Мера |
|---|---|---|
| соль и домен чатового KDF | `PQ_SALT`, `b"VAULT-PQ-V1-hybrid"` | KAT `hybrid_key_matches_known_vector` (вектор посчитан независимым HKDF-SHA256) |
| домен медиа-ключа | `b"VAULT-PQ-V1-media"` | KAT `media_kdf_matches_known_vector` |
| порядок ног гибрида | `ikm = x25519_ss ‖ mlkem_ss` | тот же KAT (перестановка ног меняет вектор) |
| канонический порядок pub-ключей | `if my_pub <= peer_pub` | `hybrid_key_is_symmetric_in_peer_order` |
| wire-форма ek/seed | `PQ_EK_LEN = 1184`, `PQ_SEED_LEN = 64` | KAT `pq_ek_from_seed_matches_known_vector` (SHA-256 от 1184 байт) + `pq_sizes_match_wire_format` |
| SMTP-fold в base64 | три whitespace-фильтра | fold-пробы ek, медиа-kemct и всего конверта |

**Почему отпечаток, а не строка целиком.** Wire-ek — 1184 байта (1580
символов base64); держать их в тесте нечитаемо. KAT фиксирует SHA-256 от
байтов ek, восстановленного из канонического seed `00..3f`, и отдельно
проверяет длину — дрейф сериализации крейта (`ml-kem 0.3`) ловится так же,
как дрейф домена.

**Почему не round-trip.** `test_hybrid_roundtrip` и `test_media_hybrid_key_symmetry`
остаются обязательными, но они проверяют согласованность двух концов ОДНОЙ
версии. Набор из 19 мутаций бьёт именно в протокол: соль, оба домена,
порядок ног, сортировка, AAD, длины, whitespace-фильтры, источник `pq` в
конверте и X25519-ногу шифрования. 18 ловятся пробами, одна (`PQ_SEED_LEN`
как длина массива) отбракована компилятором — это тоже доказательство, что
константа связана с типом, а не декоративна.

### W5. Карта «фича → будущий сервис» и требования к границам — ВЫПОЛНЕНО (22.10.2026)

**Результат:** `docs/design/feature-service-map.md` (человекочитаемая карта) +
`docs/design/feature-service-map.json` (машиночитаемая) + гейт
`vault-desktop/scripts/service-boundary-gate.mjs` (в `npm run quality` и CI).

88 фич разложены по пяти сервисам горизонта: messenger (44), streaming (9),
app (16), social (5), videohost (2). Гейт проверяет машинно: полноту карты
(нет сирот и призраков), контракт примитивов сервиса (фича не импортирует
корневой модуль, не объявленный её сервису — это и есть список того, что
уезжает в процесс) и долг границы «фича → чужой владелец состояния» (сейчас
31; в партии 4d сократился с 32) под ратчетом — расти не может.

Что осталось за рамками гейта (и почему): готовность выноса в отдельный
процесс зависит от наличия у сервиса своего хранилища, IPC и схемы
развёртывания — это свойство решения и вехи, а не файла. Порядок выноса и
условия зафиксированы в карте (§4): social → videohost → streaming →
messenger (последним и, возможно, никогда — это смена транспорта, а не
вынос сервиса).


| сервис (горизонт) | что в нём | сегодня в коде | готовность границы |
|---|---|---|---|
| **Мессенджер** | ядро обмена: конверты, крипто, классификация, хранилища | `vault-client` (Rust) + `messages`/`send`/`incoming`/`attachments` | частично |
| **Соцсеть (local-first)** | профили, каналы/лента, подписки, релей | `profiles`, `channels`, `relay` | нет — живёт в JS |
| **Видеохостинг (частный)** | видео, поиск по доступным у контактов | `video.js` | нет — живёт в JS |
| **Стриминг (частный)** | поток для контактов, подписка на стримера | `calls.js`/медиа-слой | нет |

Требование к границе: сервис не вызывает сервис напрямую в JS; обмен — через
Rust-core и wire-конверты. Предусловие выноса — W1–W4: иначе «сервис» будет
переносом монолита в другой процесс.

### W4 (партия 5d). Захват камеры десктопа — в Rust: WebKitGTK не отдаёт кадры в JS (24.10.2026)

**Симптом.** Звонок «телефон → десктоп» показывал видео, «десктоп → телефон» —
нет: Rust-writer звонка завершался с `RTP writer finished (frames=0)`, то есть
в трек не пришёл ни один кадр.

**Причина (измерено, а не предположено).** На десктопе кадры камеры брались в
JS через `<video srcObject=stream>` + `new VideoFrame(videoEl)` +
`requestVideoFrameCallback`. WebKitGTK 2.54.1 при этом:

* `getUserMedia({video})` отдаёт живой `MediaStream` (трек `live`, без ошибки);
* но `<video>` с этим потоком остаётся `readyState = 0`, `videoWidth = 0` —
  кадров в элемент не приходит вообще;
* `new VideoFrame(videoEl)` падает `InvalidStateError: Video element has no data`;
* `MediaStreamTrackProcessor` в движке отсутствует (а это единственный
  путь «MediaStream → VideoFrame» без `<video>`).

То есть JS-путь камеры на десктопе не «сломан кодом» — он физически
недоступен в этом движке. Проверено отдельно от звонка: `ffmpeg` снимает с
`/dev/video0` 30 кадров `yuyv422 640x480`, значит камера и драйвер в порядке.

**Размещение (ADR-005 §4).** Захват и кодирование — это решения о формате и
протоколе (пиксельный формат, размер, битрейт, интервал ключевых кадров,
таймстемпы RTP), поэтому они уехали в Rust, а не остались «обходным путём» в
JS. Android сохраняет WebCodecs-путь: там `MediaStreamTrackProcessor` есть, и
кадры берутся в WebView без нового кода в Rust.

**Что сделано.**

* `src-tauri/src/video.rs`, `mod capture` (Linux): V4L2 через `v4l` —
  `/dev/video0`, `YUYV 640x480@30`, mmap-поток, `yuyv_to_i420` (переупаковка
  планарного YUV без усреднения — драйвер уже даёт 4:2:2), очередь
  `CameraFrame` глубины 4 с `try_send` (перегрузка → дроп кадра, а не рост
  задержки). `start` возвращает настоящую ошибку, если камера не открылась или
  драйвер не дал YUYV, — «Ok, но кадров нет» запрещён.
* `src-tauri/src/vp8_encoder.rs` + `src-tauri/src/vp8_enc_shim.c`: VP8-энкодер
  поверх системной libvpx. Раскладка `vpx_codec_enc_cfg_t` НЕ описана в Rust —
  она версионнозависима; C-шим (собирается `cc` из `build.rs`) включает
  системные заголовки и отдаёт три функции. Кодирование: CBR 500 кбит/с,
  `cpu-used 8`, `VPX_DL_REALTIME`, `lag_in_frames 0`, ключевой кадр каждые
  150 кадров (5 с) — NACK/PLI не реализованы, ключевой кадр закрывает потери.
* `src/features/video.js`: desktop-ветка больше не изобретает кадры — только
  `api.mediaCameraStart(callId)` (открыть writer звонка) и
  `mediaCameraStop` на стопе. Ветка выбрана по факту движка
  (`typeof MediaStreamTrackProcessor === 'undefined'`), а не по
  `navigator.platform`. Поколение захвата (`captureGen`) осталось: старт,
  завершившийся после отбоя, не трогает уже освобождённые ресурсы.
* `build.rs`, `Cargo.toml`: `cc` в build-dependencies, `v4l = "0.14"` под
  `cfg(target_os = "linux")`, линковка `vpx` только для линуксового хоста
  (Android-таргет не затрагивается).

**Ловушка, которую стоит помнить.** `vpx_img_wrap` пятым аргументом принимает
`stride_align` (выравнивание), а не саму длину строки: наивное `w` = 640
возвращает `NULL` (640 — не степень двойки), и энкодер отвечает
`libvpx encode failed (code -2)`. Правильно — 32 (строки I420 остаются
упакованными: 640/320).

**Проверки.**

* `cargo test --lib` — 163 passed, 0 failed.
* Живой тест камеры отдельно от звонка (не для CI, нужен `/dev/video0`):
  `cargo test --lib capture_live -- --ignored --nocapture` — 3 VP8-кадра,
  первый ключевой, 22154 байта. Он же ловит «камера не открылась» и «кадры не
  кодируются» раздельно, чтобы не путать отказ захвата с отказом
  сигнализации.
* Живой звонок: `[video] camera frames=1 bytes=20264`, `[video] 150/300/450
  frames sent`, `[video] RTP writer finished (frames=539)` — видео с десктопа
  пришло на телефон (подтверждено владельцем).

**Остаток.** NACK/PLI и адаптивный битрейт не реализованы (восстановление —
ключевым кадром раз в 5 с); macOS/Windows получают честную ошибку
«capture is not implemented on this platform yet» вместо тихой заглушки.

### W4 (партия 5e, `t_fd23d678`). «Чей это адрес?» после смены почты — одно правило в ядре (24.10.2026)

**Симптом (живые данные телефона, три случая одного класса).**

1. Собственная почта стояла в списке контактов строкой; тап по ней открывал
   попап «Добавить контакт» вместо чата.
2. После ренейма тап по известному (старому) адресу собеседника тоже открывал
   «Добавить контакт» — ключ лежал под свежим адресом.
3. Broadcast своего профиля уходил письмом самому себе, потому что «получатели»
   строились из того же списка контактов, где была наша же строка.

**Причина.** Вопрос «эта запись — мы / этот адрес и тот адрес — один пир» в
каждом месте решался своей строкой сравнения: `contacts-load` сравнивал
`e.email !== email`, гейт чата — голую строку адреса, `key_store` (ядро) —
`k.public_key == key.public_key` без нормализации, а словарь переименований
`email-aliases` (kv, `{старый: новый}`) не спрашивал вообще никто. Нормальная
форма `normalize` существовала, но вызывалась не везде, поэтому ключ в ВЕРХНЕМ
регистре проходил стража своего ключа, а ` Old@X → New@X` не находился.
Три места — три копии одного факта, расходятся молча (ADR-005 §2).

**Размещение.** Правило — про форму адреса и принадлежность записи, значит Rust:

| Решение | Куда легло | Команда моста | JS-адаптер |
|---|---|---|---|
| «какими формами адреса это один пир» (сам адрес → конец цепочки `old→new` → адреса, которые резолвятся в него; цикл `A→B→A` обрывается) | `vault_core::identity::address_variants` | `identity_address_variants` (читает `email-aliases` из kv, мусор = пустой словарь) | `identity.js::addressVariants`, fail-open: `[bare]` |
| «какой адрес у пира сейчас» (тот же обход цепочки, ответ — один адрес) | `vault_core::identity::resolve_alias` + `alias_resolutions` (словарь уже разрешённых строк) | `identity_alias_resolutions` (один ответ на весь словарь аккаунта) | `identity.js::resolveAlias` на кэше, fail-open: адрес как есть |
| «как запомнить смену почты» (заменить запись старого ключа, убрать обратную `A→B→A`, нормализовать словарь) | `vault_core::identity::alias_pairs_after_remember` | `identity_alias_remember` (читает словарь аккаунта, пишет новый, отвечает разрешённым) | `api.js::rememberAlias` → `identity.js::rememberAlias`, кэш обновляется ответом |
| «есть ли у этого адреса ключ» | — | — | `identity.js::peerContactFor` = варианты × нормализованный `peer_keys` |
| «эта запись — мы?» | `vault_core::identity::peer_is_self` (адрес ∪ публичный ключ) | `contacts_drop_own` | `identity.js::dropOwnEntries`, fail-open: прежнее сравнение строк |
| «не клади НАШ ключ как пирский» | `key_store::add_peer_key_at` (SELF-KEY GUARD, мера — `same_public_key`) | — | — |
| «не клади чужой ключ под НАШЕЙ почтой» | `Identity::has_address` в мосте (`add_peer_key_as`) | `save_peer_key` (+`own_email`) | — |

Потребители адаптера — `chat-navigation.js::selectChat`, `messages.js` (гейт
открытия чата), `profiles.js::broadcastProfile`, `contacts-load.js`: все четыре
спрашивают теперь одну меру, а не каждый свою.

**Почему на записи ДВА стража, а не один предикат.** У отказа разные причины и
разные сообщения, и знание разное: мост знает нашу почту (и обязан отвергнуть
чужой ключ, подписанный нашим адресом), ядро хранилища знает наш ключ (и обязано
отвергнуть его же, записанный под любым адресом — `peer_store` общий на машину).
`peer_is_self` объединяет оба для ЧТЕНИЯ, где и адрес, и ключ приходят парой из
записи. Сведение к одному «универсальному» стражу дало бы общее сообщение об
ошибке и слепую зону: первый пропущенный случай в истории был именно «наш ключ
под чужим адресом».

**Дыра, которую нашли по ходу, — не в правиле, а в проводе.** Аргумент
`own_email` в `save_peer_key` — `Option`: мост обязан получить нашу почту, но
`gate:tauri-args` отсутствие `Option` прощает (он сверяет имена и арность, а не
значимость). Значит страж адреса жил бы в собранном APK и не сработал бы НИ
РАЗУ: ни `crypto.js::savePeerKey`, ни `keys.js`, ни `contacts.js`, ни запись
accept-письма в `api.js` аргумент не передавали. Проведён через все четыре точки
записи (`savePeerKey(email, key, label, pq, ownEmail)`), а форма вызова команды
меряется смоуками — опция перестаёт быть невидимой только тогда, когда её
проверяют как данные, а не как подпись функции.

**Мера (мутации на новое правило, а не только тесты).**

* `rust-identity` — 49/49 поймано (+9: нормализация входа, пустой адрес,
  сырое сравнение ключа словаря в обе стороны, обратный ход без фильтра «пара
  этого пира» — он подставляет чужой ключ, дедуп варианта, и по одной ветки
  `peer_is_self`);
* `rust-key-store` — 10/10 (+2: страж своего ключа выключен / сравнивает
  строкой — второй ловит именно `"ABCD1234"`);
* тесты ядра дополнены: `address_variants` использует только пары этого пира,
  читает грязный словарь, `peer_is_self` узнаёт наш ключ под чужим адресом;
  `vault-core --lib` 78/0, `src-tauri --lib` 170/0
  (`test_add_peer_key_rejects_our_own_address`);
* JS-смоуки: `identity` 27/0, `profiles` 64/0, `chat-navigation` 36/0,
  `contacts-load` 16/0, `messages` 31/0; их наборы мутаций — 9/9, 11/11, 15/15.
  Смоук `contacts-load` теперь копирует НАСТОЯЩИЙ `src/identity.js`, а не
  локальную копию правила: иначе проверка адаптилась на саму себя.
* Провод `own_email` тоже под меркой: `crypto` 29/0 (+4 на форму вызова
  `save_peer_key`), `keys` 40/0 (+2), `contacts` 44/0 (+6 — путь
  `acceptContactInvite` до этого не проверялся вообще), `pending-invites` 18/0
  (+5: запись ключа из accept-письма и отсеивание СВОЕГО письма по резолву
  алиаса). Наборы мутаций — `crypto` 6/6, `keys` 22/22, `contacts` 10/10,
  `pending-invites` 9/9; снятый аргумент `ownEmail` ловится смоуком, а не
  компилятором.

**Что осталось незакрытым (осознанно, задачи заведены).** CLI пишет контакт до
фильтра «это я» (`listen.rs`), а восстановление из резервной копии
(`import_keys_at`) заносят записи с нашим же ключом — там страж нужен на другом
входе; сиротские строки `chat_history` по старым адресам из словаря
(`t_b16e4c11`). Четыре копии гейта «это моё письмо» в `api.js` закрыты партией
5h (`t_53a3027c`): теперь один предикат ядра `identity::is_own_address` вместо
четырёх сравнений строк. Ни одно из этого не меняет поведения телефона, поэтому
не входит в сборку 0.1.268.

**Что изменится для пользователя.** Свой аккаунт исчезает из контактов и больше
не получает писем от самого себя; тап по любому известному адресу (старому,
новому, в любом написании) открывает чат, а не попап «Добавить контакт»;
попытка сохранить свой ключ как пирский отвергается с внятной причиной.

### W4 (партия 5f). Тумблеры возможностей и выбор транспорта — дефолт и план в ядре (24.10.2026)

**Симптом 1 (дефолт возможности).** Требование владельца — звонки по умолчанию
включены, видеозвонки по умолчанию выключены. До переноса «включена ли
возможность, если пользователь не выбирал» было записано во фронте дважды:
стартовая строка компонента (`expCalls: false`) и перечитывание kv при старте.
Компилятор про расхождение молчал: кнопка появлялась и гасла через секунду, и
узнать об этом можно было только тапом по телефону.

**Симптом 2 (выбора транспорта не было).** Сообщение и сигнал звонка всегда
ехали обоими каналами, поэтому настройка «только почта» (требование (d)) была
невыразима, а суточный лимит релея расходовался даже когда пользователь просил
его не трогать. Обратная сторона — требование (e): если релей не доставил,
почта обязана догнать. Это ветвление, а не вёрстка, значит место ему в ядре.

**Размещение.**

| Решение | Куда легло | Команда моста | JS-адаптер |
|---|---|---|---|
| «включена ли возможность, если не выбирал» + форма хранения воли | `vault_core::settings::flag_enabled` / `flag_stored` (таблица `default_enabled`, всё вне неё — fail-closed) | `settings_flag`, `settings_flag_set` | `features/settings-ui.js`: `loadExperimentFlags`, `onExperimentsCalls`, `onExperimentsVideo` |
| «каким транспортом везёт это сообщение/сигнал» | `vault_core::transport::plan(preference, relay_available)` → `Plan { mail, relay, mail_fallback }` | `transport_plan` | `api.transportPlan` (деградация в «авто»), исполнение — `features/send.js`, `features/calls.js` |
| «следующий выбор после клика» (порядок `auto → relay → mail`) | `vault_core::transport::CYCLE` / `next` | `transport_preference_next` (читает, считает, пишет, возвращает НОВОЕ имя) | `features/transport.js::cycleTransportPreference` |
| показ выбора (иконка, ключ подписи) | — это презентация, не решение | — | `features/transport.js::transportView` |

Цикл переключения держится у ядра потому, что имена транспорта — тоже его:
список строк во фронте был бы второй копией тех же литералов и разошёлся бы при
первой переименовании (тот же класс ошибки, что две копии дефолта). Фронт не
пересчитывает цикл по своей копии — он рисует то имя, которое вернул мост.

**Гарант доставки — инвариант, а не надежда.** У любого плана остаётся
почтовый путь: `mail == true` или `mail_fallback == true`; выбор «только
почта» никогда не публикует в релей (лимит не расходуется); при недоступном
релее план всегда почтовый. Инвариант меряется в трёх местах, а не в одном:
тесты ядра, 11 мутаций `rust-transport`, цикл пробы `flags` на живом
устройстве (все 6 комбинаций «выбор × доступность»).

**Мера.**

* ядро: `settings` — 8 тестов (в т.ч. форма хранения закреплена ЛИТЕРАЛОМ, а
  не круговой проверкой, и имена флагов = ключи kv), `transport` — 10 тестов;
  `cargo test -p vault-core --lib` = 95/0;
* наборы мутаций на новое правило: `rust-settings` 9/9, `rust-transport` 11/11,
  `transport-mut` 10/10, `send-mut` 11/11, `calls-mut` 8/8, `settings-ui-mut` 9/9;
* смоуки: новый `transport-smoke` (чтение/сдвиг/тост/провод аккаунта),
  `send-smoke` 33/0 (блок 5d: «только почта» не трогает релей, релей+успех не
  пишет письмо, отказ релея догоняет почтой, релей выключен → degraded-план,
  «авто» → оба; блок 5e: своя история записана ДО первого шага доставки),
  `calls-smoke` 99/0 (сигнал не публикуется при «только почта» и при выключенном
  релее, но письмо уходит всегда);
* один мутант оказался ЭКВИВАЛЕНТНЫМ и выжил: `parse(stored.unwrap_or(""))` —
  `parse('')` даёт `auto`, подмена ненаблюдаема. Заменён наблюдаемым
  (`unwrap_or(PREFERENCE_MAIL)`), а не прощён: выживший мутант значит, что
  проверка отсутствует, а не что код плохой (ADR-005 §2.3);
* тот же урок вскрыл дыру в проводе тестов: `relayAvailable` нельзя переопределять
  внутри мока плана — иначе мутация «доступность релея не передаётся в план»
  невидима. Доступность выключают живым `relayState.enableRelay(false)`.

**Живая проводка.** В `scripts/device-accept.mjs` добавлена проба `flags`
(дефолты, раунд-трип тумблера видео и его независимость от звонков, сдвиг
выбора и чтение обратно, restores выбор, инвариант плана, чип в рядку фич) и

found` — установленный APK старше этого правила, значит мера будет считаться
только со сборки, сделанной из этого дерева.

(отдельная вкладка «Экспериментальные функции» с единственной парой строк
убрана — звонки ищут в разделе «Звонки»): «Звонки» включены по умолчанию,

интерфейс.

### W4 (партия 5g). Порог релея — на сервере, значение 429 — в ядре (24.10.2026)

**Симптом (постановка владельца + то, что вскрыла живая проверка).**

1. «Порог в 100 сообщений через релей должен быть на сервере, т.к. в коде
   приложения можно поменять что угодно». Порог действительно жил на сервере,
   но был не измеряем: `std::env::var(...).unwrap_or(100)` стоял строкой внутри
   `main()`, и ни один тест не отвечал на вопрос «100 или 0 при опечатке в
   конфиге».
2. Живой прогон (локальный релей, 104 публикации через реальный HTTP) показал
   второе: сервер отвечает **429 в двух несходных случаях** — `daily relay
   limit reached` и `rate limit` (вспышка 10 rps), а клиент имел одну ветку на
   оба и на любой 429 писал в kv «лимит дня». Звонок шлёт сигналы пачкой
   (setup + ICE-кандидаты), т.е. вспышка — штатный случай: «дозвонился —
   потерял ускорение до полуночи UTC». Тот же код был продублирован в CLI
   (`relay.rs`: `429 => state.limit_day = Some(today)`).

**Размещение.** Квота — решение сервера, «чем был 429» — решение о протоколе,
значит Rust; состояние (письмо ушло/не ушло) остаётся фронту.

| Решение | Куда легло | Команда моста | JS-адаптер |
|---|---|---|---|
| «сколько действий релея в сутки бесплатно» (100; `0` = выключатель; мусор в env = дефолт, а не ноль) | `vault_relay::DEFAULT_FREE_DAILY_LIMIT` + `daily_limit_from_env` | — | — |
| «кто потратил сутки» (счётчик на издателя, смена UTC-дня, `retry_after` до полуночи) | `vault_relay::tally_daily` (чистая функция: `day` и `now` — параметры) | — | — |
| «не ограничивать явно платные/тестовые виды токена» | `publisher_key` + `Kind::is_unlimited` (канальные токены — не безлимит) | — | — |
| «какой это 429» | `vault_core::relay::pub_rejection` (`daily` / `rate` / `other`) | `relay_pub_rejection(status, body)` | `relay-client.js::classifyPubRejection` — читает тело, вызывает, fail-open на `rate` |

CLI получает то же ядро (`vault_client::vault::relay` зовёт
`vault_core::relay::pub_rejection`) — одна копия правила на десктоп и CLI,
иначе «телефон молчит, а десктоп нет» вернулся бы с другой стороны.

**Почему счётчик — отдельная чистая функция.** Внутри `relay_pub` он выглядел
«тремя строками», но смена суток там не проверялась ВОВСЕ: тест живёт внутри
одной секунды, ветка `entry.0 != day` не срабатывает никогда, и снятый сброс
дал бы зелёный прогон — лимит превратился бы в пожизненный для каждого, кто
дожил до полуночи. С `day`/`now` как параметрами мутация «сброс снят» ловится
разу. Так же и с env-разбором: `daily_limit_from_env` вынесена, потому что
«мусор = дефолт, а не ноль» иначе не проверить, а ноль — штатный выключатель.

**Почему fail-open в сторону «вспышки».** Ошибка «нераспознанный 429 = лимит
дня» стоит сутки без ускорения у живого пользователя; ошибка «лимит = вспышка»
стоит один лишний запрос, который сервер всё равно отвергнет (квота на
сервере). Поэтому неизвестный текст, пустое тело, отсутствие команды моста —
`rate`.

**Мера (мутации на новое правило, а не только тесты).**

* `rust-relay-limit` — 16/16 (арифметика счётчика, смена суток, `retry_after`
  не от полуночи, «0 не выключает», премиум под лимитом, лимит по адресату
  вместо издателя, анонимный pub без квоты, канал обходит лимит, v2-тариф
  игнорируется, легаси-promo v1 под лимитом, порог 100 → 50, мусор в env = 0,
  пробелы ломают разбор);
* `rust-relay-rejection` — 12/12 (не-429 тоже разбирается, константа порога
  сдвинута, `daily`↔`rate` перепутаны, регистр префикса, fail-open наоборот,
  обе константы имён веток, camelCase провода);
* `vault-relay` 58 → 67 тестов, `vault-core --lib` 95 → 102, `src-tauri --lib`
  170/0, `vault-client --lib` 453/0;
* смоук `relay-client` 28 → 39 проверок (9 — лимит дня пишется и pub до конца
  дня не дёргается; 10 — вспышка НЕ пишет лимит и следующая публикация уходит;
  11 — без команды моста и с пустым телом считаем вспышку), набор
  `relay-client-mut` 7 → 13/13 — каждая ветка со своим утверждением;
* проба `flags` на устройстве сверяет имена веток (`daily`/`rate`/`other`) —
  расхождение имён провода компилятор JS не видит;
* живое подтверждение порога: локальный релей с НЕ заданным env →
  `free_daily_limit=100` в логе старта, 100 принятых публикаций, 101-я —
  `429 {"error":"daily relay limit reached","limit":100,"retry_after":18640}`,
  `limit_hit 4`, в очереди ровно 100 конвертов (отказы ничего не сдвигают);
  на проде `/relay/metrics` отдаёт `limit_hit` и НЕ содержит
  `VAULT_RELAY_FREE_DAILY_LIMIT` в env — значит работает дефолт.

**Что осталось незакрытым (осознанно).** Счётчик in-memory: рестарт релея
обнуляет сутки (в докстринге зафиксировано; при 100/сутки злоупотребление
рестартами дорого серверу, а не пользователю). Второй вектор — регистрация
множества аккаунтов (по 100 на издателя): держится IP-квотой `/register`, а не
суточным лимитом. И расхождение с `paid-tokens-spec.md`: там тарифы 100 / 1000 /
10000 конвертов/сутки, а реализация трактует «любой не-Free» как безлимит —
до начала монетизации надо выбрать (задача не заведена, решение за владельцем).

**Что изменится для пользователя.** Звонок перестанет выключать ускорение на
сутки: после пачки сигналов релей остаётся живым, а бесплатные 100 конвертов в
сутки считаются сервером и не зависят от того, что кто-то пересоберёт
приложение. Почта по-прежнему не ограничивается ничем.

### W4 (партия 5h, `t_53a3027c`). «Это письмо от нас?» — один предикат ядра на все handshake-пути (26.10.2026)

**Симптом.** Письма-инвайты и письма-подтверждения лежат в ящике вечно, и фронт
четыре раза решал «это письмо от НАС?» своей строкой:

* `sweepStaleHandshake` — инвайты (`api.js`, пометки `declined`);
* `sweepStaleHandshake` — accept-письма (пометки `accepted`);
* `fetchPendingContactInvites` — попап «Добавить контакт»;
* `fetchPendingContactAccepts` — запись ключа пира из письма.

Каждая копия резолвила адрес через словарь `email-aliases` и затем сравнивала
строки регистрозависимо: своё письмо с адресом в другом регистре проходило гейт
и возвращало наш ключ в контакты / оставляло попап. Правка одной копии не
ловилась остальными (ADR-005 §2), а смоук `pending-invites` покрывал только
четвёртый путь.

**Размещение.** Правило — форма адреса плюс принадлежность, значит Rust:

| Решение | Куда легло | Команда моста | JS-адаптер |
|---|---|---|---|
| «письмо пришло от нас?» (отправитель → конец цепочки `old→new` → сравнение нормальной формы; пустой адрес — не адрес) | `vault_core::identity::is_own_address` (= `same_address` + `resolve_alias`) | `identity_is_own_address` (читает словарь ЭТОГО аккаунта; ошибка чтения — ошибка, не `false`) | `identity.js::isOwnSender` (кэш по namespace, fail-open: прежнее сравнение нормальных форм), `api.js::isOwnSender` → все четыре точки |

**Почему ошибка чтения, а не `false`.** `false` означает «письмо чужое» и вернул
бы наш ключ в контакты — ровно дефект, ради которого правило переносилось.
Ошибка — честный ответ: адаптер откатывается к прежнему сравнению строк, а не
решает за пользователя.

**Почему кэш сбрасывается при записи смены.** После `rememberAlias(old, new)`
старый адрес может стать нашим (смена почты СОБЕСЕДНИКА не меняет гейт, но
смена нашего адреса — меняет): без сброса кэш держал бы «чужое» до рестарта.

**Мера (мутации на новое правило, а не только тесты).**

* `rust-identity` — 70/70 (+3: гейт без резолва цепочки, сырое сравнение строк,
  пустой отправитель как своё письмо);
* `rust-bridge-identity-alias` — 21/21 (+4: не читает словарь, правило вернулось
  в мост, аргументы перепутаны, ошибку чтения глотает); фикстуры моста — 20
  проб (три новых на команду);
* `identity-mut` — 29/29 (+8: нормализация адреса/своего адреса, пустой
  отправитель, кэш, привязка кэша к namespace, fail-open, неожиданный ответ,
  сброс кэша при записи смены); смоук `identity` 39 → 49 проверок;
* `pending-invites-mut` — 13/13 (+4: обёртка сравнивает строки в JS и три из
  четырёх точек; четвёртая уже была под меркой): смоук поднимает все четыре
  пути — sweep инвайтов/accept и попап контакта, свой адрес в другом регистре и
  старый адрес через alias; смоук 18 → 25 проверок;
* полный JS-гейт — 1069/1069; плотность — 195 модулей / 2068 мутаций / 0 дыр.

**Что осталось незакрытым (осознанно).** Прежний «сырой» быстрый путь
`senderRaw === this.email` перед резолвом оставлен: он не решает, а экономит
вызов моста на точном совпадении, и неверного ответа дать не может. Гейт
`markContactHandshakeDone` (`api.js`, строка пометки) по-прежнему сравнивает
строки — это не «это мы?», а «пометка относится к этой смене», и его форма
привязана к uid письма; отдельной задачи не заводим до живого дефекта.

### W4 (партия 5i). Сборка сигнала звонка — туда же, где разбор (27.10.2026)

**Симптом.** У сигнала звонка было ДВЕ копии формата в двух языках: ядро
собирало конверт `vault::call::build_call_signal` (после переноса из
`service_monitor.rs`, партия 5g), а JS `features/calls.js::sendCallEnvelope`
собирал ровно тот же объект вручную и только потом дописывал `tok`. Разбор
при этом уже год шёл через мост `call_parse_signal`. Копии успели разойтись
ровно на `tok`: пока Rust-парсер его не знал, собеседник терял адрес
relay-очереди отправителя, и мгновенные сигналы падали на почтовый поллинг.
Собрать письмо по одному правилу и разобрать по другому — это и есть ЖИВОЙ
дефект, а не стилистика.

**Размещение.** Сборка переехала к разбору, JS остался транспортом:

| Решение | Куда легло | Команда моста | JS-адаптер |
|---|---|---|---|
| формат конверта сигнала: `vault:1`, имена и порядок ключей, «отсутствующее поле не пишется» | `vault_client::vault::call::build_call_signal` (реэкспорт `vault::build_call_signal`) | `call_build_signal` (`lib.rs`, рядом с `call_parse_signal`) | `wire-signal-rule.js::buildCallSignal`; `calls.js::sendCallEnvelope` передаёт поля и шифрует ГОТОВУЮ строку |

**Отказ ядра — это отказ отправки.** Если мост не собрал конверт, `sendCallEnvelope`
не шлёт НИ релей, НИ почту: локальная сборка вернула бы ровно ту вторую копию
формата, которую убрали. Пустой конверт хуже молчания — получатель принял бы
его за сигнал.

**Идентификатор — один на два канала.** `id` считается один раз и уходит и в
конверт (через ядро), и в релей-публикацию (`{ id }`): иначе дедуп на приёме
сравнивал бы разные ключи, и релей-копия считалась бы новым сигналом.

**Мера (мутации на новое правило).**

* `rust-call` — 12/12 (сборка ядра уже была под меркой; правок в правиле нет);
* `wire-signal-rule-mut` — 22/22 (+5: имя команды, «null» строкой при отказе,
  `sender_ek` в snake_case, отсутствующее поле строкой, тип/время не передаются);
* `calls-mut` — 14/14 (+6: отказ ядра игнорируется, `tok` не доезжает,
  чужой `call_id`, `sdp` не передаётся, `ts` 1970-го, чужой id в релей);
* `calls-smoke` 100 → 103 проверки (camelCase-аргументы ядра, `tok` в конверте,
  id релея = id конверта, отказ ядра → ничего не отправлено); смоук правила —
  49 проверок;
* полный JS-гейт — 1081/1081; `smoke:all`, `audit:arch` (0 протокольных решений
  в JS) зелёные; плотность — 195 модулей / 2080 мутаций / 0 дыр.

**Что осталось (осознанно).** Живой провод звонка меняется — окончательное
доказательство даёт приёмка звонка на X50 (инициировать с телефона, принять на
десктопе, увидеть медиа с обеих сторон), а не смоуки.

### W4 (партия 5j). Вердикт по отказу входа — в ядре; автосжигание кредов убрано (27.10.2026)

**Симптом.** `api.js::restoreSession` на любую ошибку входа ветвился по её
тексту: `msg.includes('login failed') → delete_credentials`. Яндекс отвечает
`AUTHENTICATIONFAILED` и на отозванный app-пароль, и на выключенный IMAP, и на
всплеск логин-попыток. Одна ветка решала три разных случая, и стирание
сохранённого пароля верно только для первого — а стоит оно дней. 27.10 на живом
X50 так и вышло: авто-вход упал, приложение стёрло валидный app-пароль,
восстановление заняло недели.

**Размещение.** Решение «что это за отказ» переехало в ядро, JS остался UI:

| Решение | Куда легло | Команда моста | JS-адаптер |
|---|---|---|---|
| класс отказа входа и его код для объяснения человеку | `vault_client::vault::login_failure::{LoginFailure, classify, code}` | `vault_classify_login_failure` (`vault_bridge.rs`) | `api.js::restoreSession` кладёт код в `lastRestoreError`; тексты — `features/restore-failure.js` + локали `ru/en/zh` |

(«invalid credentials or IMAP is disabled») читается ПЕРВЫМ: он содержит
`AUTHENTICATIONFAILED` и без этого был бы прочитан как отказ пароля. За ним
троттлинг, потом транспорт, и только в самом конце — явный отказ пары
логин/пароль. Это единственная категория, где фронт имеет право сказать
человеку «введите пароль заново».

**Отказ ядра — не отказ входа.** Если мост не ответил (нет команды, упала),
берётся `unknown`, и креды всё равно не трогаются: безопасное по умолчанию —
«не знаю — значит не удаляю». Автосжигания нет ни в одной ветке;
`delete_credentials` вызывают только явные действия человека — `logout` и
удаление ящика.

**Мера (мутации на новое правило).**

* `rust-login-failure` — 16/16 (новый набор: потеря нормализации регистра,

  одного `login failed`, рассинхрон `code()` с классом);
* 8 тестов ядра, в том числе на захваченную с устройства строку ответа Яндекса;

  `lastRestoreError`, `delete_credentials` 0 вызовов, `load_credentials` 1;
  сырой текст доезжает ядро дословно; отсутствие команды → `unknown` без
  стирания; `logout` по-прежнему стирает ровно один раз;
* `restore-failure-smoke` — 45 проверок: у `disabled` и `throttled` свой ключ и
  свой запасной текст, ключ есть во всех трёх локалях;
* полный гейт — JS-мутации 1088/1088, Rust-мутации 1033/1033, `smoke:all`,
  `audit:arch` (0 протокольных решений в JS) и `js-logic-ratchet` зелёные;

**Что осталось (осознанно).** Запрет трогать вход на X50

### W4 (партия 5k). Правило текста SOS — одна копия в ядре, каналы отдают данные (27.10.2026)

**Симптом.** Правило «как из настройки, дефолта и координат получается письмо»
жило в двух местах и разошлось по четырём пунктам:

| Вопрос | Мост (`src-tauri/src/duress.rs`, headless-канал) | Фронт (`features/duress.js`, WebView-канал) |
|---|---|---|
| пустая настройка | текста нет (пустая строка) | подставляется `sos_default`, а за ним — ещё и литеральная заглушка в том же файле (третья копия дефолта) |
| несколько `{coords}` в тексте | меняются все | меняется только первый |
| хвост без плейсхолдера | дописывает через разделитель `" \| "` | дописывает координаты без разделителя |
| фраза координат | её нет (Kotlin форматирует `%.5f, %.5f` сам) | `, мои координаты: …` собиралась в JS, по-русски, независимо от локали |

Это не стилистика: человек задаёт текст в одном месте, а письмо уходит разным —
и в каком именно виде, зависит от того, каким каналом оно поехало. Расхождение
было зафиксировано в самом коде: doc-comment моста называл вторую копию и
откладывал сведение в отдельную задачу, потому что дефолтный текст — это
решение о том, ЧТО пишет человек под принуждением.

**Размещение.** Правило — одно, в ядре; каналы передают только свои данные:

| Решение | Куда легло | Команда моста | JS-адаптер |
|---|---|---|---|
| сборка текста: дефолт, `{coords}`, хвост при гео | `vault_client::vault::duress::{SosText, compose_sos_text}` | `duress_sos_text` (`src-tauri/src/duress.rs`) | `features/duress.js::sendDuressSos` передаёт `sosText`/`defaultText`/`geoOn`/`geo` |
| «какой канал» (headless — `" \| "` и без дефолта, WebView — разделителя нет и дефолт из локали) | данные канала в мосте, не ветвление в правиле | то же | — |
| фраза координат: порядок чисел, пять знаков, ведущая запятая | `vault_client::vault::duress::geo_phrase` | `duress_geo_phrase` | подпись (`sos_coords_label`) приходит из локали, числа — из ядра |

**Проводы обоих каналов сохранены побайтно — кроме одного случая.** Разделитель
`" \| "` и отсутствие дефолта у headless, разделителя и заглушки у WebView
зафиксированы пробами («оба живых канала побайтно»). Единственное расхождение,
которое сведение исправляет арифметически: несколько `{coords}` в тексте.
WebView менял первый, мост — все; правило теперь одно, и оно меняет все
(плейсхолдер — метка, а не часть сообщения). Оба канала — живой провод замка
на том же телефоне, поэтому расхождение снимается как параметры одного правила,
а не как «общий» текст: менять письмо duress без приёмки на X50 (#40) нельзя.

**Отказ ядра — письмо без текста, но не с придуманным.** Если мост не собрал
текст, фронт не собирает его на месте: локальная сборка вернула бы ровно ту
вторую копию, которую убрали. Письмо уходит с меткой `type:"sos"` и пустым
текстом, ошибка пишется громко. С фразой координат так же: без неё уходит текст
без координат, а не выдуманная строка.

**Человеко-читаемая подпись координат — в локалях.** Ключ `sos_coords_label`
(ru/en/zh) добавлен рядом с `sos_default`; в Rust остался только формат чисел.
Русский литерал внутри Rust — это и сломанный i18n, и находка при проверке
готовности к магазинам.

**Мера (мутации на новое правило).**

* `rust-duress` — 14 → 29/29 (дефолт не подставляется, пустота считается без
  `trim`, плейсхолдер не срезается, координаты никогда не встают на своё место,
  подстановка наоборот, хвост теряет координаты/текст/разделитель, флаг гео
  выставляется насильно — в true и в false, число знаков координат, ветка
  пустой подписи, теряется ведущая запятая);
* `rust-bridge-duress` — 15/15: 10 мутаций переехавшего правила убраны, вместо
  них 11 мутаций проводки (headless теряет `default_text`/`separator`/`text`/
  `geo`/`geo_on`, WebView теряет дефолт из локали, получает разделитель,
  инвертирует флаг; `geo_phrase` вызывается с пустой подписью);
* `duress-mut` — 15 → 26/26 (фронт снова собирает текст сам, зовёт другую
  команду, не передаёт `sosText`/`defaultText`/`geoOn`/`geo`, подменяет текст
  локальной сборкой при отказе ядра, пишет подпись литералом вместо локали,
  обнуляет широту, выдумывает фразу при отказе фразы, не опрашивает гео);
* пробы: 6 в ядре (оба живых канала побайтно, дефолт из локали, хвост требует
  флаг, пять знаков), 3 в мосте (headless не передаёт дефолт, WebView-команда
  с дефолтом и без разделителя, фраза из ядра на ru и en подписях), `smoke:duress`
  — 36 проверок (секция 5d: контракт аргументов, подпись и дефолт из локали,
  хвост без плейсхолдера, отказ ядра, отказ фразы);
* плотность — 197 модулей / 2145 мутаций / 0 дыр; `gate:tauri-args` (42 команды),
  `gate:locale-keys`, `audit:arch` (0 протокольных решений в JS) зелёные.

**Что осталось (осознанно).** Живой провод замка — приёмка на X50 (#40): что
SOS доезжает и как он выглядит на устройстве, знает только устройство. Мутациями
здесь измерена формулировка письма, а не его доставка.

### W4 (партия 5l). Мера: поворот кадра в видео и база токенов темы (27.10.2026)

Партия не переносит решение в Rust — она закрывает два места, где решение уже
на месте, а проверить его было нельзя. Очередь — пункт списка качества после
цикла 11 («мутационная плотность видео и настроек»): на весь `features/video.js`
было 6 мутаций, а по базе токенов темы (`:root`, `.vue`) — ни одной.

**Видео: ветка перестройки энкодера была слепой.** В `features/video.js` живёт
правило «размер кадра изменился — перестроить энкодер и отправить ключевой
кадр» (video.js:199-218). Смоук его не видел: мок `VideoEncoder` хранил
ТОЛЬКО последний `config`, поэтому «перестроили один раз на повороте»,
«перестраиваем каждый кадр» и «не перестраиваем никогда» давали один и тот же
наблюдаемый след. Секция 2b меряла портретный конфиг на старте — это другая
ветка (размер берётся из `track.getSettings()`), а не та, что срабатывает в
середине живого разговора.

Сделано: мок ведёт историю (`configs[]` — каждый `configure`, `encodes[]` —
каждый `encode` с флагом ключевой рамки и размером актуального конфига), а
тестовый поток умеет задавать размер на каждый кадр отдельно. Новая секция 2c
крутит шесть кадров: два в 640x480, дальше 480x640, и проверяет 8 фактов —
кадры дошли, ре-конфиг ровно один, новый конфиг следует кадру, кадры до
поворота кодируются со старым размером, первый кадр после поворота ключевой,
следующий обычный (ключевым становится ровно один кадр после перестройки, а не
каждый), при неизменном размере перестройки нет, и перестройка не теряет
codec/bitrate/framerate/keyInterval. Мера: `video-mut` 6 → 19/19 — каждая
мутация ломает один из этих фактов (`if (fw !== encW …)` → `false`/`true`,
`encW = fw` пропускается, конфиг строится от старого размера, `isKey = true` и
`keyFrame` теряются или инвертируются, параметры кодека при перестройке
сбрасываются). Проверок в `video-smoke` 61 → 69.

**Тема: токен без запасного значения и без объявления — невидимый дефект.**
Тема — набор CSS-переменных, которые `applyTheme` пишет в `documentElement`;
остальное оформление берёт значения из глобальных баз `:root` (вторая половина
дизайн-системы живёт в `<style>` файла App.vue). Если токен вызван
`var(--x)` без запасного значения и не объявлен ни в одной базе, ни во всех
темах, браузер считает значение невалидным: элемент наследует чужое или падает
к `initial`. Класс регресса в проекте уже был (`--radius-*`, `--shadow-sm`,
`--font-sans` — элементы теряли скругления, тень и шрифт), поэтому проверка
сделана статическим инвариантом, а не разовым исправлением.

Найденное (четыре настоящих дефекта, все починены):

| Токен | Где звался без запасного значения | Что было | Теперь |
|---|---|---|---|
| `--accent` | App.vue (кнопка отправки), CipherTool (рамка и фон) | не объявлен нигде → фон падал к `initial`, в тёмной теме кнопка прозрачная | `--accent: var(--accent-primary, …)` в базе — цепочкой, чтобы следовать выбранной теме, а не застывать литералом |
| `--border` | ContactList (рамка секции групп) | имени токена не существует | `var(--border-subtle, …)` |
| `--border-color` | LanguageSelector (рамка селекта) | имени токена не существует | `var(--border-subtle, …)` |
| `--accent-hover` | CipherTool (наведение на кнопку) | имени токена не существует | `var(--accent-secondary, …)` |

**Первые два вывода проверки были неверны, и это часть меры.** `--transition-fast`
и `--status-online` проверка тоже посчитала «висящими»: первый вариант читал
только `:root` из `style.css`. По факту оба объявлены в глобальном `:root`
App.vue и работали. Проверка расширена: база собирается из всех `:root`-блоков
без `scoped` (css + глобальные `<style>` в компонентах), и отдельной проверкой
ловится тот же класс ловушки — `:root` внутри `<style scoped>`: Vue дополняет
селектор атрибутом `[data-v-…]`, правило перестаёт матчить документ, и
объявление исчезает молча. Дублировать эти два токена в `style.css` не стали.

Мера: `themes-smoke` 16 → 21 проверка; новый набор `style-tokens-mut` — 12/12
(акцент потерян/застыл литералом/уехал на фон/объявлен пустым, база App.vue
теряет цвет «в сети» и длительность переходов, база уезжает в scoped-блок,
три мёртвых имени возвращаются в компоненты, `--safe-bottom` и `--safe-left`
перестают следить за `env(safe-area-inset-*)`). Мутации бьют по четырём файлам
через `file` у отдельной мутации: набор про правило токенов, а не про один
файл.

**Что ратчет не мерит (осознанно, а не «почти зелёный»).**
`gate:mutation-density` считает мутации по `.js` и `.rs`; `.css` и `.vue` вне
его области по построению. Поэтому в плотность попали +13 (видео: 6 → 19), а
12 мутаций токенов — нет: итог 197 модулей / 2158 мутаций / 0 дыр. Проверка
инварианта живёт в смоуке, и её защищают именно мутации; отдельный учёт для
CSS/Vue не вводится — это был бы ратчет по файлам, которых в списке модулей
нет. Отдельно: `.vue` в этом ADR считаются только данными (ветвления там нет),
за это отвечает `audit:arch`.

**Остаток по обеим частям один и тот же — устройство.** Ни один хостовый гейт
не показывает, как выглядит кнопка в боевой теме и что видит собеседник после
поворота телефона: это приёмка на X50 (#40, #62) и живая приёмка звонка (#63).

## 7. Критерий готовности этапа

1. `ctx` = 0, потолок ратчета равен нулю;
2. в `App.vue` 0 методов с собственной логикой — файл описывает композицию;
3. в JS нет решений о протоколе, формате и крипто — это держит гейт с
   самопроверкой;
4. каждая фича проходит проверку «правка фичи не меняет поведение соседней» —
   на подставленном нарушении, а не на обещании;
5. фикстуры паритета Rust/JS покрывают все типы конвертов по принципу
   «объявлено = выполнено».

## 8. Чего этот ADR не решает

* UI-состояние остаётся в компоненте (ADR-003 §2);
* цена IPC: где вызов Rust на каждое сообщение дорог — решается по измерению
  (батч-команды), а не заранее; язык логики от этого не меняется;
* порядок микросервисов, монетизация, магазины — отдельные ADR/вехи ROADMAP;
* перенос эффектов (обработчиков) в Rust до появления событийной модели
  Rust → JS не делается: порядок «сначала решения, потом события».
