# ADR-005: Логика в Rust, JS — фронт. Границы фич = границы сервисов

**Дата**: 19.10.2026
**Основание**: прямое указание владельца (19.10.2026) + ADR-004 (независимость как
инвариант), ADR-003 (слои фронтенда), ADR-001 (разрыв ctx).
**Статус**: принят, исполняется. Это план текущего этапа.

---

## 1. Решение владельца (19.10.2026)

> «Язык логики — Rust, JS — только фронт и прослойка. JS стараться избегать в
> логике. Главная цель данного этапа — модульная независимость фич: правка одной
> фичи не должна сказываться на поведении других фич либо всего приложения. Это
> подразумевает минимизацию `ctx` (а лучше полное неиспользование), минимизацию
> JS в логике (а лучше полное неиспользование), минимизацию `App.vue` (только
> вызовы). После добавления в магазины и начала монетизации займёмся расширением
> по архитектуре микросервисов: мессенджер — сервис, распределённая соцсеть —
> сервис, частные видеохостинги пользователей для своих контактов — сервис,
> частный видеостриминг для контактов (возможно, по частной подписке на аккаунт
> стримера)».

Три нормативных следствия: **ноль `ctx`**, **ноль JS в логике**, **`App.vue`
только вызывает**. Четвёртое следствие — горизонт: границы, которые мы проводим
сейчас между фичами, станут границами сервисов.

## 2. Что это меняет в уже принятых решениях

**2.1. Отменяется моя прежняя рекомендация по `t_99f22059`.** Я предлагал удалить
неиспользуемую Tauri-команду `vault_classify_incoming` как «мёртвый код». По новой
рамке Rust-классификатор — не мёртвый код, а **будущий единственный источник
правды**: удалять его означало бы двигаться против решения владельца. Правильная
задача — **подключить** его, а JS превратить в адаптер (решение принимает Rust,
эффекты исполняет JS, пока JS — фронт). Формулировка задач исправлена в
`t_857ee662` и `t_99f22059`.

**2.2. ADR-004 не отменяется, а продолжается.** Его этап A закрыт (0 полей с
несколькими писателями), гейты (циклы, правило слоёв, владельцы ссылок) держат.
Незакрытая часть ровно та, которую называет владелец: `ctx` (686 ссылок, см. исправление в §3) и монолит
`App.vue` (198 методов с собственной логикой).

**2.3. Крипто-граница уже чистая — и это измерено, а не предположено.**
Изначально `audit:arch` показывал «ПЛОХО: крипто-логика в JS» со ссылкой на
`features/invites.js`. Это было **ложное срабатывание инструмента**: шаблон
`/pbkdf2|scrypt|argon2/i` без границ слова находил `scrypt` внутри имени
`isCryptoReady` («i-sCrypt-o»), а отсутствие флага `g` занижало счёт. Исправлено
19.10.2026 (`scripts/audit-arch.mjs`), самопроверка в обе стороны:

* файл с одним `isCryptoReady` — чисто (ложное срабатывание вылечено);
* файл с настоящим вызовом `pbkdf2(...)` — красный (`✗ __audit_fp_probe.js: pbkdf ×1 — KDF в JS`).

После починки вердикт: **крипто-логики в JS нет**, вся криптография идёт в Rust
через 121 команду. Значит «логика в Rust» на этом этапе — про **протокольные
решения, состояние и формат**, а не про крипту. Это меняет порядок работ: начинать
с решений и `ctx`, а не с крипто-«долга», которого нет.

Урок ADR-004 («цифра инструмента верна настолько, насколько проверен инструмент»)
подтвердился во второй раз. Поэтому в плане ниже **W0 (инструменты) идёт первым**.

## 4. Нормативные правила этапа (обязательны для новых правок и ревью)

* **R1. Новая логика — только в Rust.** Ветвление по формату, протоколу, времени
  жизни, состоянию сессии/звонка/группы в JS — это дефект размещения, а не стиль.
* **R2. JS-модуль — либо адаптер к Rust, либо UI.** В шапке модуля написано, что
  он из себя представляет; «адаптер с ветвлениями» запрещён.
* **R3. Ноль `ctx`.** Модуль не берёт состояние из компонента. Данные — у
  владельца (store) или из Rust; зависимость объявляется явным узким списком.
* **R4. `App.vue` — композиционный корень.** Его задача — вызвать и передать;
  методов с собственной логикой должно быть 0.
* **R5. Фича не знает про фичу.** Обмен — через Rust-core (wire-конверты) или
  через store с единственным владельцем. Правило слоёв из ADR-004 в силе.
* **R6. Граница фичи = будущая граница сервиса.** Если часть нельзя вынести в
  отдельный процесс (мессенджер / соцсеть / видеохостинг / стриминг), граница
  проведена неверно.
* **R7. Каждая веха закрывается ратчетом.** Инструмент обязан быть проверен на
  заведомо известном нарушении (подставленном), иначе он измеряет мнение.

UI-состояние (открыт ли попап, позиция меню) остаётся в компоненте — правило
ADR-003 §2; на него R1–R4 не распространяются.

## 6. Порядок работ

Порядок выведен из измерения и риска, а не из удобства.

### W0. Инструменты и ратчеты — ПЕРВЫМ

Без измерения план — мнение; инструмент обязан сначала поймать подставленное
нарушение.

* расширить `audit:arch`: детект протокольных решений в JS (сборка/разбор
  конвертов, `JSON.parse` конвертов, переходы состояний) — с самопроверкой;
* новый ратчет «JS-логика» (ctx + методы с логикой в `App.vue` + файлы с
  протокольными решениями) в `npm run build`, потолок только затягивается;
* подключить `audit:arch` к сборке (сейчас — только вручную).

**Acceptance**: каждое из трёх нарушений (новая `ctx`-ссылка, новый метод с
логикой, разбор конверта в JS), подставленное в код, валит сборку с точным
сообщением; самопроверка зафиксирована в комментарии гейта.

**Статус W0 — ВЫПОЛНЕНО 19.10.2026** (`t_8a422c38`). Три инструмента:
`scripts/lib/arch-metrics.mjs` (единственный код измерения),
`scripts/audit-arch.mjs` (отчёт, код выхода 1 на крипто-логику и провал
самопроверки), `scripts/js-logic-ratchet-gate.mjs` (потолок по трём величинам,
только затягивается). Оба подключены к `npm run build`. Подстановка трёх
нарушений: `1 / 1 / 1 → 0` по коду выхода, тексты в комментарии гейта.
Побочно исправлен **дефект измерения**: `ctx` считался двумя правилами (735
сырых против 686 по гейту) — теперь правило одно, и обе цифры согласованы
(`docs/testing/js-logic-gate.md`).

### W1. Классификация входящих: решение → в Rust

`t_857ee662` + `t_99f22059`. Шаги:

1. расширить Rust `incoming::classify` до паритета по всем ветвям (profile,
   presence, call, poll, channel, group) под общей фикстурой, тот же принцип
   «сколько объявлено — столько проверено»;
2. в `features/incoming.js` вызвать Rust-классификатор; в JS оставить только
   **эффекты** (обработчики звонка, применение профиля, тосты, обновление
   бейджей);
3. удалить JS-дубль решений о типе конверта.

**Acceptance**: гейт паритета по всем типам конвертов; в `incoming.js` нет
ветвлений «какой это конверт»; `ctx` модуля 65 → ≤15.

**Статус W1 — ВЫПОЛНЕН 19.10.2026** (шаги 1–3 + `ctx`-контракт модуля):

- ✅ Rust `incoming::classify` приведён к паритету с прод-роутером: `call`
  (`type=call_*` + `call_id`) → `presence === 1` → vault-конверт (`vault=1` и
  `text` строкой; внутри `type=profile` → профиль) → `channel === 1` →
  `hav === 1`. Добавлены виды `channel` и `group-service`. Заодно исправлены
  расхождения, которые до W1 жили только в чтении: poll считался управляющим
  сигналом (в JS — сообщение), `call_id` без `type=call_*` считался звонком,
  профиль с `text` считался сообщением, `text:123` считался конвертом.
- ✅ Общая фикстура: **20 кейсов** (Rust 46/46, JS 48/48 проверок).
- ✅ `features/incoming.js`: решение заменено адаптером `classifyPlain` →
  `vault_classify_incoming`; эффекты остались. `parseCallSignal` /
  `isChannelEnvelope` / `hav` / `env.type==='profile'` как решения в роутере
  больше не участвуют. Появился эффект `presence.noteHeartbeat` — без повторной
  проверки `presence === 1`.
- ✅ Найден и исправлен скрытый дефект: `invoke` в `incoming.js` **не был
  импортирован**, поэтому `vault_store_incoming_message` (персист M1.10) падал
  `ReferenceError` в `catch` — мост не работал вовсе.
- ✅ `vault_classify_incoming` больше не создаёт `MessageStore` (чтение
  `~/.vault/messages.json` на каждое письмо) — вызов идёт в чистый `classify`.
- ✅ Новый гейт `smoke:incoming` (16 утверждений) в `npm run build`: маршрутизация
  message/profile/call/presence/channel/hav/null + отказ моста.
- ✅ **`ctx` модуля: 62 → 0** (цель была ≤15). Модуль больше не читает компонент:
  зависимости идут явным объектом `deps` (ADR-005 R3), контракт собирается в
  одном месте — `App.vue:processIncoming`. Методы обёрнуты стрелками (иначе
  теряется `this`), `channels`/`groups` — геттеры (ренейм адреса по ходу батча
  переприсваивает массив через `loadGroups`, снимок устарел бы). Мост каналов
  `ingestChannelEnvelope` связывает свой ctx сам в App.vue — модуль отдаёт
  только данные.
- ✅ Метрики после W1: `ctx` **683 → 621** (−62), `ctx-coupling` 589 → 527,
  протокольных решений 69 → 67; ратчеты затянуты через `--write`.
- ✅ Проверка: `npm run build` EXIT 0 (13 гейтов + `vite build` + boot-smoke),
  `smoke:incoming` 16/16, Rust 46/46, JS 48/48.

### W2. `ctx` → 0 по батчам (`t_d674affd`)

Партия = один модуль, порядок по числу взятых полей: `attachments` (106),
`send` (100), `messages` (73), `incoming` (65, после W1 меньше), `invites` (49),
`groups`/`recovery` (45), `calls`/`profiles` (40/37). Внутри партии: заменить
`ctx.*` на явные `deps` / метод владельца / вызов Rust. После партии — затянуть
потолок `ctx-ratchet` (механика уже есть, повышения не допускает).

### W3. `App.vue` → только вызовы (`t_48a61a71` + остаток ADR-001 этапа 4)

198 методов с логикой. Партия = группа методов одной темы; вынос в компонент
(UI) или в фичу/ядро (логика — по R1 в Rust). После партии — затянуть ратчет.

### W4. Протокол и формат — в Rust

`message-format.js` (`parseEnvelope`/`buildEnvelope`), редакции, TTL, реакции,
конверты вложений, состояние звонка (`calls.js`, 1094 строки — сюда же
`t_64e7241a` про Rust-сигнализацию). JS остаётся транспортом доставки.

### W5. Карта «фича → будущий сервис» и требования к границам

| сервис (горизонт) | что в нём | сегодня в коде | готовность границы |
|---|---|---|---|
| **Мессенджер** | ядро обмена: конверты, крипто, классификация, хранилища | `vault-client` (Rust) + `messages`/`send`/`incoming`/`attachments` | частично |
| **Соцсеть (local-first)** | профили, каналы/лента, подписки, релей | `profiles`, `channels`, `relay` | нет — живёт в JS |
| **Видеохостинг (частный)** | видео, поиск по доступным у контактов | `video.js` | нет — живёт в JS |
| **Стриминг (частный)** | поток для контактов, подписка на стримера | `calls.js`/медиа-слой | нет |

Требование к границе: сервис не вызывает сервис напрямую в JS; обмен — через
Rust-core и wire-конверты. Предусловие выноса — W1–W4: иначе «сервис» будет
переносом монолита в другой процесс.

## 7. Критерий готовности этапа

1. `ctx` = 0, потолок ратчета равен нулю;
2. в `App.vue` 0 методов с собственной логикой — файл описывает композицию;
3. в JS нет решений о протоколе, формате и крипто — это держит гейт с
   самопроверкой;
4. каждая фича проходит проверку «правка фичи не меняет поведение соседней» —
   на подставленном нарушении, а не на обещании;
5. фикстуры паритета Rust/JS покрывают все типы конвертов по принципу
   «объявлено = выполнено».

## 8. Чего этот ADR не решает

* UI-состояние остаётся в компоненте (ADR-003 §2);
* цена IPC: где вызов Rust на каждое сообщение дорог — решается по измерению
  (батч-команды), а не заранее; язык логики от этого не меняется;
* порядок микросервисов, монетизация, магазины — отдельные ADR/вехи ROADMAP;
* перенос эффектов (обработчиков) в Rust до появления событийной модели
  Rust → JS не делается: порядок «сначала решения, потом события».
