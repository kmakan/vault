# Vault (MailCipher) — Дорожная карта 2026-2027

**Дата переопределения**: 16 августа 2026
**Основание**: анализ возможностей Delta Chat (delta.chat/en), особенно релизов 2025-2026
**Принцип**: Vault предлагает пользователям тот же *интересный и современный* функционал,
что и Delta Chat. Устаревшее — не рассматриваем. Транспорт — email (serverless), как у Delta.

---

## 1. Что даёт Delta Chat в 2025-2026 (и что из этого берём)

### Современные возможности Delta Chat (релиз 2.48+, март 2026)

| Возможность Delta Chat | Суть | Берём в Vault? |
|---|---|---|
| **Zero metadata / Header Protection (RFC 9788)** | Subject, To, группа, Auto-Submitted, References, In-Reply-To — всё в шифре. Сервер видит минимум. | ✅ Да (у нас уже stealth-тема; доводим до полного zero-metadata) |
| **Рандомизированный Date** | Внешний Date ±5 дней — защита от корреляции по времени | ✅ Да |
| **SecureJoin v3** | QR-инвайт, скрытие крипто-идентичностей, все первые сообщения шифрованы | ✅ Да (у нас инвайты есть — дорабатываем до QR) |
| **OpenPGP anonymous recipients** | Нет инфо о ключах в сообщении | ✅ Да (у нас X25519 — уже анонимнее) |
| **Аудио/видео звонки (P2P WebRTC)** | Нативные звонки, сигнализация через сообщения, фон | ✅ Да (этап M3) |
| **Описания групп и каналов** | E2E, синхронизируются с добавлением участников | ✅ Да |
| **Каналы (broadcast)** | Шифрованные каналы-вещание — альтернатива Telegram-каналам | ✅ **Да, приоритет (монетизация)** |
| **Фоновый плеер аудио-сообщений** | Desktop + Android | ✅ Да |
| **Download on demand** | Два сообщения (малое+большое), получатель выбирает что качать | ✅ Да (этап M1) |
| **Multi-relay / multi-path delivery** | Профиль использует несколько релеяев; один упал — идёт через другой | ✅ Да (этап M6, устойчивость) |
| **Webxdc мини-приложения** | HTML5-приложения в ZIP, sandboxed, P2P API, без сервера | ✅ **Да (фундамент соцсети)** |
| **Редактирование/удаление/сохранение сообщений** | Базовые операции | ✅ Да (этап M1) |
| **Контактные профили (аватары, имена)** | Украшенные профили | ✅ Уже есть (аватары починены 16.08) |
| **E2E всегда и по умолчанию (V2)** | Без иконок замков, упрощённый UI | ✅ Да (у нас так и есть) |

### Что НЕ берём (неактуально / чужое)
- DeltaTouch (Ubuntu Touch) — чужая платформа.
- Старые миграции шифров Alpha/Columnar из прежнего плана — заменены на X25519+XChaCha20.
- Специфичные для email-серверов вещи (chatmail-релеи как бизнес Delta) — у нас свой подход.

## 2. Стратегическое видение (от пользователя)

**Конечная цель — локал-перст соцсеть поверх Vault:**
1. Сначала — конкурентный E2E-мессенджер (паритет с Delta Chat по интересным фичам).
2. **Каналы** — современный формат + база монетизации.
3. Публикация в магазинах приложений (Android, затем ПК) + сайт.
4. **Соцсеть**: пользователь открывает просмотр своим контактам из Vault в клиенте
   на своём устройстве (предположительно Android, возможно ПК). Устроено как приложение
   соцсети, но **вся информация хранится на устройстве** (local-first, без центрального сервера).

Мини-приложения (webxdc-подобные) + каналы — строительные блоки этой соцсети.

## 3. Новая дорожная карта по вехам

> Сегодня: 16.08.2026. Команда: 1 разработчик + AI-агент. Оценки реалистичные.

### M0 — Демо v0.1.0 (ядро 1-на-1) — **20.08.2026** ✅ в срок
Уже ~90% готово. Scope: стабильный 1-на-1 E2E (Desktop), аватары, реакции,
копирование, stealth-тема. Осталось: визуальные тесты ТЕСТ-01…09, полировка,
локальная история (минимум), GitHub-релиз.

### M1 — Паритет ядра обмена — **15.09.2026** (~4 недели)
- Группы E2E (sender keys) — ТЕСТ-05 «ключевое!»
- **Локальная история + инкрементальный фетч** (чаты в памяти/БД, не перезагрузка каждый раз)
- Редактирование / удаление / сохранение сообщений
- Файловые вложения + **download on demand** (малое+большое сообщение)
- Фоновый плеер аудио-сообщений
- CLI-совместимость (конверт, /react, stealth)
- Доведение zero-metadata (полный Header Protection, рандом Date)
- **Уведомления о новых сообщениях** (локальный поллинг + системные уведомления;
  базовый уровень без сервера) — **предусловие монетизации**: каналы/лента
  бесполезны на телефоне без своевременных уведомлений (решение 22.08.2026)

### M2 — Каналы + фундамент монетизации — **15.10.2026** (~4 недели)
- **Шифрованные broadcast-каналы** (создание, подписка, вещание)
- Описания каналов и групп (E2E, синк с добавлением)
- **Платные подписки на каналы** (монетизация №1)
- Базовые premium-возможности
- QR-онбординг (SecureJoin-подобный)
- **Push-релей (premium)** — поднимается из M6: единственный серверный компонент,
  он же платёжный хаб и точка контроля монетизации. Без него платные каналы
  на телефоне мертвы (решение 22.08.2026)
- Механика каналов = фундамент M5 (стены = личные каналы): анализ чужого опыта
  (Delta Chat broadcast, Nostr NIP-99/NIP-57) — docs/research/social-network-architecture.md

### M3 — Звонки + мини-приложения — **30.11.2026** (~6 недель)
- **Аудио/видео звонки** (P2P WebRTC, сигнализация через сообщения, фон)
- **Решение 22.08.2026** (research: docs/research/calls-research-2026-08-22.md):
  - Стандартный **WebRTC (webrtc-rs, Rust)** + **cpal** + **opus** — медиа P2P (DTLS-SRTP).
  - Сигнализация — конверты Vault `call_*` (зашифрованные email), доставка **IMAP IDLE**
    (~1-3с), фолбэк — ускоренный поллинг 2-3с на время звонка. Аудио-MVP ~12-16 дней.
  - Архитектура: docs/architecture/voice-calls.md (рерайт 22.08).
- **Требования устойчивости к блокировкам (решение 18.08.2026)**:
  - Оценка защищённости метода + «простые настройки обхода» для пользователя:
    docs/research/blocking-resilience-2026-08-22.md
  - Сигнализация — ТОЛЬКО через зашифрованные сообщения Vault (email/P2P), ни один
    публичный сервер установки звонка не требуется.
  - Медиа — P2P (SRTP пир-в-пир, резать нечего); TURN обязателен для NAT, но
    **только TURN over TLS/443** (неотличим от HTTPS для DPI) и **никаких
    хардкод-доменов STUN/TURN** — настройка пользователя + ротация (как Briar/SimpleX).
    Публичные STUN/TURN (stun.l.google.com и т.п.) — не более чем фолбэк в dev-сборках.
- **Мини-приложения** (webxdc-подобный контейнер: HTML5 в ZIP, sandboxed, P2P API)
- Каталог/обнаружение мини-приложений
- Маркетплейс мини-приложений (монетизация №2)

### M4 — Мобильный клиент + магазины + сайт — **31.01.2027** (~8 недель)
- **Android-клиент** (Tauri 2 / нативный)
- Публикация в магазинах приложений (Android, затем ПК)
- Сайт / лендинг + документация
- Push-уведомления (FCM / unified push)

### M5 — Соцсеть (local-first) — **31.03.2027** (~8 недель)
- **Единая модель (решение 22.08.2026)**: лента/стены/товары — НЕ отдельная
  подсистема, а **типы сообщений** в том же E2E-конверте (wall_post, listing,
  channel_post). Один транспорт, одно хранилище, один UI-каркас.
  Анализ: docs/research/social-network-architecture.md
- **Стена = личный broadcast-канал** с гранулярной аудиторией (все контакты /
  выбранные / никто); публикация = шифрованная рассылка зрителям (механика
  каналов M2)
- **Лента = локальная агрегация** wall_post'ов от контактов (sqlite, local-first)
- **Товары/услуги = типизированные посты (listings)** по модели Nostr NIP-99:
  цена, категория, статус; отклик = обычный 1:1 чат
- **Видео — открытый вопрос**: старт с вложений (download-on-demand, лимит
  провайдера); P2P WebRTC-стриминг проектировать в M3
- UX как у соцсети, но без центрального сервера
- Интеграция с каналами и мини-приложениями

### M6 — Устойчивость и крипто-апгрейд — **параллельно / 2027**
- Multi-relay / multi-path delivery (устойчивость к блокировкам)
- (Push-релей поднят в M2 — см. выше; здесь остаётся multi-relay как
  устойчивость, а не уведомления)
- **Принципы multi-relay (решение 18.08.2026)**:
  - Устойчивость достигается НЕ одним неубиваемым каналом, а **ротацией множества
    дешёвых труб**: несколько email-провайдеров + свой/премиум-релей + P2P WebRTC
    (мгновенный канал, когда оба online). Один упал/заблокирован — идём через другой.
  - Релей — это «труба», а не читатель: конверт E2E (AAD="VAULT") релей расшифровать
    не может физически; после zero-metadata (M1, RFC 9788) релей не видит и
    отправителя/адресата. Никакой логики в релеях, только пересылка байтов.
  - **Никаких хардкод-доменов релеев/провайдеров** в коде — только конфиг
    пользователя + ротация; дефолт-набор существует как стартовая точка, не догма.
  - Цензуроустойчивость Vault = «заблокировать нельзя один сервер, потому что его
    нет» (serverless) + «заблокировать все трубы сразу практически невозможно»
    (multi-relay). Это позиция конкуренции с серверными мессенджерами (Session/SimpleX-лига),
    где сервер = точка блокировки по определению.
- Post-quantum (Autocrypt2-подобный) + Forward Secrecy
- Sealed Sender (по возможности)
- Нагрузочное тестирование, security-аудит

## 4. Монетизация (если справимся с проектом)

Принцип: зарабатываем на **ценности**, никогда на данных (в этом суть E2E-децентрализации).

| Модель | Суть | Этап |
|---|---|---|
| **1. Платные каналы/подписки** | Авторы берут плату за доступ к premium-каналам (аналог платных Telegram-каналов / Patreon). Vault берёт комиссию или предоставляет инструмент. | M2 |
| **2. Маркетплейс мини-приложений** | Revenue-share с платных webxdc-приложений (игры, инструменты). | M3 |
| **3. Premium-релеи / хостинг** | Управляемый релеи-сервис для тех, кто не хочет self-host. | M6 |
| **4. Premium-функции** | Крупные вложения, больше контактов/каналов, приоритетная поддержка. | M2+ |
| **5. Enterprise / self-hosted** | Приватный E2E-мессенджер для организаций (лицензия). | M4+ |
| **6. Донаты** | Как у Delta Chat (open-source goodwill). | всегда |

**Главная ставка — каналы (M2)**: это и современный формат, и прямой путь к деньгам,
и фундамент для соцсети (M5).

## 5. Сравнение с прежним планом

Прежний TIMELINE.md (13.07) писался под **клиент-серверную** архитектуру
(PostgreSQL-backend, фазы 1-4, «отставание −56 дней»). От неё отказались в пользу
**serverless email-транспорта** — это сняло главный риск (не надо строить/деплоить backend).

Новая карта строится от **реального состояния** (ядро 1-на-1 работает) и от **рыночного
ориентира** (Delta Chat), а не от устаревших фаз.

## 6. Критические риски

1. **Группы (M1)** — самое сложное в ядре (sender keys, синхронизация). Начать сразу после демо.
2. **Звонки (M3)** — WebRTC + NAT-traversal; может потребовать больше времени.
3. **Android (M4)** — отдельная большая платформа; Tauri 2 на Android ещё имеет острые углы.
4. **Монетизация каналов (M2)** — нужны платёжные интеграции (карты РФ не подходят для
   зарубежных сервисов — продумать крипто/локальные платежи).
5. **Объём** — паритет с Delta Chat (8 лет, большая команда) в одиночку — амбициозно;
   приоритизируем «интересное пользователям», не всё подряд.
