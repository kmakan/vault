# Vault — Research: звонки (аудио/видео) в serverless-мессенджере

**Дата:** 22.08.2026 · **Статус:** исследование завершено, решение зафиксировано
**Связано:** ROADMAP M3 (30.11.2026), docs/architecture/voice-calls.md (нужен рерайт под решение)

---

## 1. Вывод (коротко)

**Звонки в Vault = стандартный WebRTC (DTLS-SRTP) с сигнализацией через
зашифрованные email-сообщения Vault и доставкой по IMAP IDLE.**

- Медиа: **P2P**, при недоступности — **TURN пользователя** (X2TURN-паттерн, TLS/443).
- Сигнализация: только зашифрованные конверты Vault (`call_*` типы) — ноль публичных серверов.
- Реализация: **webrtc-rs** (чистый Rust) в Tauri-бэкенде + **cpal** (микрофон/динамик) + **opus**.
- Никакой собственной криптографии медиа — стандартный DTLS-SRTP WebRTC (E2EE, forward secrecy).

## 2. Что дала документация проекта

### 2.1. Требования ROADMAP M3 (решение 18.08.2026) — жёсткие рамки
- Сигнализация — **ТОЛЬКО** через зашифрованные сообщения Vault (email/P2P);
  ни один публичный сервер установки звонка не требуется.
- Медиа — P2P (SRTP пир-в-пир); TURN обязателен для NAT, но **только TURN over TLS/443**
  (неотличим от HTTPS для DPI) и **никаких хардкод-доменов STUN/TURN** —
  настройка пользователя + ротация (как Briar/SimpleX). Публичные STUN — фолбэк dev-сборок.

### 2.2. Существующий docs/architecture/voice-calls.md — УСТАРЕЛ
- Написан под старую архитектуру: WebSocket-транспорт аудио, телефонные аккаунты,
  **собственная криптография фреймов** (ChaCha20-Poly1305 на Opus-фрейм + HKDF-voice_key).
- Конфликты с текущим решением:
  1. WebSocket-сервер = публичный сервер, запрещённый ROADMAP.
  2. Своя крипта медиа не нужна: WebRTC даёт DTLS-SRTP из коробки (E2EE, эфемерные ключи).
     «Изобретать крипто» — антипаттерн (см. §5.5).
- Вывод: документ переписать под новое решение (§6), старую схему — в архив/историю.

### 2.3. Инфраструктура, которая уже есть и пригодится
- IMAP IDLE **поддерживается вендоренным крейтом** `vendor/imap` (`Session::idle()`,
  extensions::idle::Handle) — быстрая доставка новых писем (~1-3с), как у Delta Chat.
- Шифрование сообщений: X25519 + ChaCha20-Poly1305, конверт `{vault:1, id, text,...}` —
  база для `call_*` сигнальных конвертов (тот же stealth: пустая тема, шифрованное тело).
- Поллинг 30с — фолбэк; при звонке ускорять до 2-3с (флаг), пока IDLE недоступен.
- Rust-бэкенд Tauri 2 = место для webrtc-rs (нативный путь, паритет desktop/android).

## 3. Сравнение похожих реализаций (интернет)

### 3.1. Delta Chat — ЗВОНКОВ НЕТ (важно!)
- В ядре/приложениях Delta Chat **нет** аудио/видео звонков (проверено: GitHub
  deltachat/deltachat-desktop — issues/PR про звонки закрыты без реализации).
- Ближайший эксперимент — PR #3741 «Realtime channels» (закрыт, не принят).
- Что у DC полезно: **IMAP IDLE** — их механизм «мгновенной» доставки сообщений.
  Для звонков DC потребовал бы ровно наш паттерн: сигнализация конвертами, медиа WebRTC.
- webxdc (мини-приложения) — отдельная фича M3, к звонкам отношения не имеет.

### 3.2. SimpleX — ближайший аналог по архитектуре (ВЫВОД №1)
Источники: simplex.chat/docs/guide/audio-video-calls.html, simplex.chat/docs/webrtc.html
- Звонки: WebRTC, E2EE, сигнализация через **сообщения SimpleX** (их SMP-транспорт) —
  аналог нашей «сигнализации конвертами».
- Медиа: по умолчанию **TURN-релей** (скрывает IP), опционально P2P; настройка
  «Always use relay» в UI.
- **X2TURN**: пользователь ставит свой coturn (`alt-tls-listening-port=443`,
  `lt-cred-mech`, long-term credentials, Let's Encrypt) и указывает ICE-серверы в
  настройках приложения. Ровно требование нашего ROADMAP (TURN/443, без хардкода).
- Групповые звонки НЕ поддерживаются — мы тоже не берём в MVP.

### 3.3. Briar — звонки через Tor
- Briar 1.4+ добавил голосовые звонки: WebRTC поверх Tor (со своей сигнализацией
  через Briar-сообщения). Для нас Tor не обязателен (email уже транспорт);
  полезен только принцип «никаких публичных серверов установки».
- Питфолл Briar: качество/задержки через Tor — не эталон для нас.

### 3.4. Session / Signal / Matrix — не эталон для serverless
- Signal/Session: центральные серверы сигнализации — противоречит ROADMAP.
- Matrix: WebRTC + TURN, сигнализация событиями (зашифрованными) — архитектурно
  похоже, но транспорт не наш (нужен сервер homeserver).
- Вывод: **SimpleX-модель** (WebRTC + X2TURN + сигнализация сообщениями) — образец.

## 4. Ключевая проблема: задержка сигнализации через email

| Сценарий | Доставка письма | Длительность установки звонка |
|---|---|---|
| Оба онлайн, **IMAP IDLE** | 1-3с | ~5-10с (2-3 раунда конвертов) — приемлемо, «гудки» |
| Оба онлайн, поллинг 30с | до 30с/раунд | 60-90с — плохо; **ускорять поллинг до 2-3с на время звонка** |
| Получатель офлайн | письмо ждёт | звонок невозможен (как и в любом мессенджере без push); при входе — отбой/«пропущенный» |

- ICE-кандидаты: **trickle ICE** через несколько конвертов ИЛИ собрать полный SDP
  (gathering 1-3с) и слать одним конвертом `call_sdp` — для MVP второе проще.
- Таймаут звонка: 30-45с ожидания accept → отбой (как в телефонии).
- Это принципиально **не мгновенно**, но сопоставимо с обычным «гудком» —
  приемлемый UX, фиксируем в требованиях.

## 5. Техническое решение

### 5.1. Транспорт медиа: webrtc-rs (чистый Rust)
- Проверено: репозиторий живой (обновления 19.08.2026, ~5k звёзд).
- Примеры: media tracks (play-from-disk-vpx/h26x, save-to-disk-vpx/av1), **trickle-ice
  host/srflx/relay**, ice-restart, ice-tcp, simulcast — всё для звонка есть.
- Интеграция: Tauri Rust-бэкенд, команды/события (invoke/emit) в Vue UI.
- Аудио-ввод/вывод: **cpal** (desktop: ALSA/Pulse; android: Oboe-бэкенд в cpal 0.15+).
- Кодек: **opus** (crate `opus` / `audiopus`), 48kHz mono, 20ms фреймы — как все VoIP.
- Видео: позже (захват с камеры нативный — отдельная работа; старт с аудио).

### 5.2. Почему не WebRTC в webview (getUserMedia)
- Android WebView (Chromium) и Windows WebView2 — работают.
- **Linux (WebKitGTK, наш desktop) — getUserMedia исторически неполноценен**:
  GStreamer-зависимости, permission-кошмары, частые «черные экраны». Риск для флагманской
  платформы. Нативный webrtc-rs обходит это полностью и даёт паритет desktop/android.

### 5.3. Сигнализация — конверты Vault (stealth)
Новые типы в шифрованном теле (пустая тема, как все письма Vault):
```
{vault:1, id, type:'call_request', call_id, ts}
{vault:1, id, type:'call_accept', call_id, ts}
{vault:1, id, type:'call_reject'|'call_end'|'call_missed', call_id, ts}
{vault:1, id, type:'call_sdp', call_id, sdp_offer|sdp_answer, ts}   // полный SDP (non-trickle)
```
- Классификация в App.vue: расширение parseEnvelope/processIncoming — `call_*` НЕ
  рендерится как сообщение чата (как квитанции), а уходит в call-state-machine.
- Дедуп по call_id, таймауты, повторная отправка при сбое SMTP (как квитанции).
- Zero-metadata: провайдер видит «ещё одно письмо»; длительность звонка видна
  по timestamps (принято, как и всё email-поведение).

### 5.4. ICE/TURN
- P2P: host/srflx кандидаты (частные сети и большинство домашних NAT).
- Symmetric NAT: без TURN звонок не пройдёт — TURN обязателен как настройка.
- **X2TURN** (паттерн SimpleX): пользовательский coturn —
  `alt-tls-listening-port=443`, `lt-cred-mech`, cert Let's Encrypt, релей 49152:65535.
  Настройки ICE-серверов в UI (STUN/TURN списком), **без хардкода**; ротация =
  смена конфигурации. Публичные STUN — только dev-сборки.

### 5.5. Криптография — НЕ изобретаем
- Сигнализация: существующий Vault-конверт (X25519+ChaCha20-Poly1305) — уже есть.
- Медиа: **DTLS-SRTP** WebRTC (эфемерные ключи, forward secrecy) — стандарт.
- Старую схему voice-calls.md (ChaCha per-frame + HKDF voice_key) — в архив:
  дублирует DTLS-SRTP, добавляет поверхности атак вместо их удаления.

## 7. Риски
1. **Задержка email-сигнализации** — смягчается IDLE + ускоренным поллингом; UX «гудков».
2. **Symmetric NAT без TURN** — звонок не пройдёт; TURN обязателен в настройках (X2TURN).
3. **webrtc-rs зрелость на android (cpal/Oboe)** — заложить запасной путь (webview-WebRTC на android).
4. **Google Play политики** (если будет в проде): микрофон/камера — runtime permissions (уже паттерн POST_NOTIFICATIONS).
5. **Лицензии**: webrtc-rs MIT/BSD, opus BSD, cpal Apache-2.0 — совместимо.

## 8. Выводы из SimpleX (повторное изучение 22.08, вечер)

Источник: simplex.chat/docs/guide/audio-video-calls.html (прочитано целиком).

1. **Сигнализация живёт в НАТИВНОМ слое, не в JS.** У SimpleX входящий звонок доходит и на
   lock screen (Android: 3 режима Disable/Show/Accept; iOS: CallKit). Наш IDLE-цикл — в JS
   (App.vue): при свёрнутом WebView Android замораживает JS-таймеры → call_request не читается.
   **Решение: перенести IMAP IDLE + обнаружение call_request в Rust-бэкенд** (emit во фронт).
   Desktop при этом тоже перестаёт зависеть от JS-поллинга (мы ловили его деградацию: поллинг
   молча пропускался при занятом lock — SKIPPED: client lock busy).
2. **Нет жёсткого таймаута приглашения** («as long as the caller is still waiting»). У нас
   ring-таймер 45с — ок для гудков, но timeout НЕ должен блокировать следующий звонок
   (починено: новый call_request вытесняет зависшее состояние; clearTimeout при ответе).
   Опция Ignore («принять позже из чата») — на потом.
3. **TURN-релей по умолчанию** (скрывает IP), P2P опционально; «Always use relay»; ICE-серверы
   настраиваются пользователем и хранятся на устройстве, не в БД. Наш план Фазы 3 (X2TURN,
   coturn на 443, настройки в UI) — ровно эта модель. Публичные STUN — только dev.
4. Групповые звонки не поддерживают — мы тоже не берём в MVP.
