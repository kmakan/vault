# Видео в дорожной карте: чего нет и почему

**Дата**: 19.10.2026
**Повод**: стоп-точка сессии `android_43` (18.10) — «разобрать, почему
видеохостинг/видеостриминг отсутствуют в дорожной карте».

## 2. Найденный дефект плана: висячая ссылка M5 → M3

M5 отсылает проектирование P2P-стриминга в M3, но в scope M3 (стр. 85-103)
**нет ни одного пункта про стриминг** — только звонки и мини-приложения.
То есть видео как контент (не как звонок) не имеет владельца вехи:

- звонок = real-time 1:1, M3;
- видео-пост/видео в канале = асинхронный контент, но в M2/M5 его нет;
- «видеохостинг» как сервис — отсутствует намеренно (см. §3).

Это не «забыли вписать», а незакрытый выбор: либо видео-контент делается
вложениями (тогда пункт живёт в M1/M2), либо стримингом (тогда пункт нужен
в M3 явно).

## 3. Почему «видеохостинг» не может появиться в этой архитектуре

Хостинг (YouTube-подобный) требует сервера, который хранит и раздаёт файл.
Vault по конструкции:

1. **Serverless**: транспорт — email-провайдеры пользователя, своего бэкенда нет
   (ROADMAP §5). Хранить видео негде.
2. **E2E (AAD="VAULT")**: релей физически не может прочитать конверт
   (ROADMAP M6, стр. 135-137). Он не может ни транскодировать, ни строить превью,
   ни отдавать HLS — он «труба», а не читатель.
3. **Zero-metadata (M1)**: после RFC 9788-подобной защиты релей не видит даже
   отправителя/адресата — то есть не может быть CDN с авторизацией.
4. **Local-first (M5)**: «вся информация хранится на устройстве». Видео на
   сервере противоречит целевой модели соцсети.

Платный релей (M2, монетизация №3) — единственное серверное место, но по
принципу «релей не читает» он тоже не хостинг: это пересылка байтов и
(возможно) буфер, а не библиотека контента.

**Вывод**: «видеохостинг» в Vault невозможен без смены архитектуры. Корректная
формулировка для карты — не «хостинг», а «доставка видео»: вложение (DoD),
P2P-стриминг, либо буфер premium-релея.

## 4. Что предложить в карту (минимальные правки)

1. **M1** — расширить пункт вложений до явного «видео-вложения (DoD,
   превью-кадр, встроенный плеер, лимит провайдера)». DoD уже реализован,
   не хватает плеера/превью и явного учёта лимитов (Gmail ~25 МБ и т.п.).
2. **M3** — добавить отдельный пункт «P2P видео-стриминг (WebRTC, media-only,
   без сервера)» рядом со звонками: тот же медиа-стек (`webrtc-rs` + `opus`),
   отличие — асинхронный контент и несколько зрителей (mesh на 2-4 участника).
   Это закрывает висячую ссылку из M5.
3. **M5** — переформулировать «Видео — открытый вопрос» в решение:
   «видео-пост = вложение в `wall_post` (DoD) + превью; стриминг — из M3».
4. **M2** — для каналов: видео-пост как обычное вложение; «крупное видео» —
   premium-возможность (лимит провайдера обходится DoD-разбиением, а не
   хостингом).

## 5. Смежный блокер: видео-звонки M3 упираются в энкодер

`vault-desktop/src-tauri/src/video.rs` (508 строк) содержит только пайплайн
кадров (шифрование кадра тем же E2E-слоем, что аудио, `TrackLocalStaticSample`,
RTP-пакетизация VP8) и **не содержит ни захвата камеры, ни VP8-энкодера**.
Шапка модуля прямо фиксирует причину: в `webrtc 0.20` нет VP8-энкодера, а в
дереве зависимостей нет libvpx/openh264/rav1e; ТЗ шага запрещало добавлять
крейты. То есть пункт M3 «Аудио/видео звонки» в части **видео** сейчас
заблокирован не архитектурой, а выбором кодека/энкодера.

Практический вывод: тот же выбор (энкодер) понадобится и для P2P-стриминга,
поэтому его надо принять один раз — до M3, а не внутри M3.

## 6. Открытые вопросы (нужно решение владельца)

- **Энкодер**: добавить `vpx-encode`/`libvpx-sys` (или ffmpeg-обвязку) —
  без него нет ни видео-звонков, ни P2P-стриминга.
- Максимальный размер видео-вложения и число частей DoD (сейчас лимит
  провайдера — единственный ограничитель).
- Нужен ли превью-кадр на стороне отправителя (требует того же энкодера/
  декодера; без него превью — только первый кадр, снятый при выборе файла).
- Стриминг на >4 зрителей потребует SFU, то есть сервера → это уже
  противоречит serverless; для каналов остаётся только асинхронное видео.
