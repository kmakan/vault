# Vault — Закрытая соцсеть: анализ чужого опыта и единая архитектура

**Дата**: 22.08.2026
**Статус**: аналитический документ (перед стартом push/каналов)
**Конечная цель продукта**: закрытая (contact-gated) соцсеть — лента контактов,
стены с контентом, товары/услуги, каналы, мини-приложения. Всё в одной
работающей системе с контролируемой монетизацией. Транспорт — serverless email,
принцип — зарабатываем на ценности, никогда на данных.

---

## 1. Чужой опыт

### 1.1 Delta Chat — каналы поверх email (главный ориентир)

Каналы в Delta Chat **уже реализованы и стабильны** (v2.59, «Channels are no
longer experimental»). Механика по исходникам deltachat-core-rust:

- Канал = **broadcast-группа с секретом**: `create_broadcast()` генерирует
  `broadcast_secret`, хранится в таблице `broadcast_secrets`.
- Вступление по **QR**: `OPENPGP4FPR:FINGERPRINT#a=ADDR&b=BROADCAST_NAME&x=BROADCAST_ID&j=INVITENUMBER&s=AUTH`.
  `j` (номер инвайта) позволяет **отзывать и возобновлять** QR-приглашения
  (WithdrawJoinBroadcast / ReviveJoinBroadcast).
- У подписчика канал **read-only** (`Chattype::InBroadcast` — «Broadcast
  channel is read-only»); вещает только владелец.
- Счётчик просмотров, реакции в каналах, mute владельцем, повторная отправка
  последних 10 сообщений новому участнику.

**Вывод для Vault**: механика «один вещает — многие читают» поверх email
уже отработана. Наш канал = та же модель: broadcast-секрет + QR-инвайт +
read-only у подписчика. Не изобретаем, адаптируем.

### 1.2 Nostr — децентрализованная соцсеть + маркетплейс + платежи

Nostr — протокол децентрализованной соцсети (без единого сервера, релеи —
только пересылка). Полезные стандарты (NIPs):

- **NIP-99 (Classified Listings)** — `kind:30402`: структурированное
  объявление о товаре/услуге (заголовок, описание в markdown, цена, теги,
  изображения, статус). Черновики — `kind:30403`. Автор = продавец.
  Расширение market-spec стандартизирует e-commerce.
- **NIP-57 (Zaps)** — платежи Lightning прямо в ленте: zap request (9734) →
  invoice → zap receipt (9735). Квитанции публичны — используются и как
  анти-спам.
- Лента = агрегация постов подписок, хранится у клиента.

**Вывод для Vault**: Nostr доказал, что «соцсеть + товары + платежи» работает
без центрального хранилища. Берём **модель данных** (типизированные посты:
пост/объявление/платёж), но не транспорт (у нас email, не релеи).

### 1.3 Telegram — каналы + платежи как бизнес-модель

- Каналы — основной формат вещания; монетизация через Telegram Stars и
  bot-payments (комиссия платформы ~30%).
- Контроль монетизации возможен **только потому, что есть центральный сервер**,
  который видит платежи и выдаёт доступ.

**Вывод для Vault**: в serverless-системе нет сервера, который мог бы
принудительно брать комиссию. Контроль монетизации концентрируется в
**единственном опциональном серверном компоненте** — premium-релее/сервисе
подписок (см. §5).

### 1.4 ActivityPub/Mastodon — почему не подходит

Федеративная лента, но каждый узел — сервер с хранилищем. Противоречит
serverless-принципу Vault (нет точки блокировки, нет чужого хранения данных).

### 1.5 SimpleX/Briar — serverless, но без соцсети

Ближайшие по архитектуре (без серверов), но соцсетей/лент/маркетплейсов нет —
опыта «соцсеть без сервера» у них не берём, только подтверждаем: транспорт
решает, контент-модель строим сами.

## 2. Единая модель: «всё — типизированное сообщение в E2E-конверте»

Ключевое решение: **не строить отдельную подсистему под каждый формат**.
Лента, стены, товары, каналы — это **типы сообщений** в том же зашифрованном
конверте (AAD="VAULT"), что и чаты. Один транспорт, одно хранилище, один UI-каркас.

```
Envelope (X25519 + XChaCha20-Poly1305, AAD="VAULT")
└── Payload: { type, body, meta }
    type:
      chat_message      — 1:1 / группа (уже есть)
      channel_post      — пост канала (broadcast, M2)
      wall_post         — пост на стене (личная broadcast-лента, M5)
      listing           — товар/услуга (структурированный пост, M5)
      payment_request   — запрос оплаты / подписки (M2+)
      miniapp           — webxdc-подобный ZIP (M3)
```

### 2.1 Стена = личная broadcast-лента с аудиторией

Serverless-ограничение: читатель не может «зайти на сервер и посмотреть стену».
Значит, **контент стены доставляется читателю** (push-модель):

- Стена пользователя = **его личный канал** (broadcast), подписчики — только
  те контакты, которым он разрешил просмотр (гранулярно: все контакты /
  выбранные / никто).
- Публикация на стене = шифрованная рассылка поста по списку зрителей
  (механика Delta Chat broadcast, адаптированная).
- **Лента читателя = локальная агрегация** wall_post'ов от контактов
  (хранится в sqlite, как история чатов). UX как у соцсети, но без
  центрального сервера — всё на устройстве (local-first, M5).

Это **унифицирует каналы и стены**: один механизм broadcast, разница только в
авторе (владелец канала vs обычный пользователь) и аудитории (публичный по QR
vs contact-gated).

### 2.2 Товары и услуги = типизированный пост (listing)

По модели Nostr NIP-99, но внутри нашего конверта:

```
listing: {
  title, description, price { amount, currency },
  category, images[], status: active|sold|draft,
  contact: chat_id   // откликнуться = написать продавцу
}
```

- Объявление публикуется на стену (видят контакты) и/или в каналы.
- Отклик на объявление = обычный 1:1 чат с продавцом (уже есть).
- «Продано» = обновление статуса поста (edit сообщения, M1).

### 2.3 Видео — открытый вопрос (не решено)

Варианты, по возрастанию сложности:
1. **Вложение с download-on-demand** (M1-механика): видео как файл в письме,
   лимит размера провайдера (~25 МБ). Просто, но короткие ролики.
2. **Внешний хостинг + ссылка**: ломает serverless/приватность — отклоняем
   как базовый вариант; допустим только как явная опция пользователя.
3. **P2P WebRTC-стриминг** (M3): видео пир-в-пир, сигнализация через
   сообщения Vault. Мгновенно и приватно, но только когда оба онлайн.

Рекомендация: начать с (1) для коротких видео, (3) проектировать в M3.

## 3. Как это сходится в одну работающую систему

| Слой | Что используется | Новое |
|---|---|---|
| Транспорт | IMAP/SMTP, stealth, zero-metadata | — |
| Крипто | X25519+XChaCha20, AAD="VAULT" | broadcast-секреты каналов |
| Хранилище | sqlite (история, контакты, группы) | таблицы: channels, wall_posts, listings |
| Доставка | поллинг (M1) → push-релей (premium) | push как предусловие ленты |
| UI | чаты, группы, темы | вкладки: Лента / Каналы / Объявления |

**Критическая зависимость**: лента и каналы на телефоне **бесполезны без
push** — подписчик должен узнавать о новом контенте вовремя. Поэтому
push-поллинг (базовый) и push-релей (premium) идут **до/вместе** с каналами,
а не после (см. §6).

## 4. Монетизация и её контроль

Проблема: в децентрализованной системе нет сервера, принудительно берущего
комиссию. Решение — **контроль концентрируется в опциональном premium-релее**
(единственный серверный компонент, он же монетизация №3).

| Модель | Механика | Точка контроля | Этап |
|---|---|---|---|
| **1. Платные каналы** | Подписка: оплата → релеи выдаёт broadcast-секрет канала | Premium-релей (платёжный хаб) | M2 |
| **2. Маркетплейс мини-приложений** | Revenue-share с платных webxdc | Каталог/релей | M3 |
| **3. Premium-релеи** | Мгновенный push + хостинг + платёжный хаб | Сам релеи | M6 (но нужен раньше) |
| **4. Premium-функции** | Крупные вложения, лимиты, приоритет | Релей/клиент | M2+ |
| **5. Enterprise** | Self-hosted лицензия | Договор | M4+ |
| **6. Донаты** | Добровольные | — | всегда |

**Платный канал (детально)**:
- Владелец создаёт канал, выставляет цену подписки.
- Бесплатный путь: владелец вручную подтверждает подписчиков после оплаты
  вне платформы (P2P, крипта) — без комиссии Vault.
- Контролируемый путь: оплата через premium-релей (фиат/крипта), релеи
  автоматически выдаёт подписчику broadcast-секрет и берёт комиссию.
- Это даёт авторам выбор (как у Patreon vs прямой подписки), а Vault —
  комиссию только там, где он предоставляет ценность (автоматизация, гарантия).

**Платежи**: карты РФ не подходят для зарубежных сервисов → ориентируемся на
крипту/локальные платежи (риск из ROADMAP §6.4). Конкретный провайдер —
отдельное решение на этапе M2.

## 5. Что это меняет в дорожной карте

1. **Push поднимается в предусловие монетизации**: базовый поллинг-уведомления
   (M1/M2), premium push-релей — раньше M6, вместе с каналами.
2. **M2 (каналы)** = фундамент и для M5 (соцсети): broadcast-механика общая.
3. **M5 (соцсеть)** = стены (личные каналы) + лента (локальная агрегация) +
   listings (типизированные посты). Не новая подсистема, а типы сообщений.
4. **Видео** — решение отложено; старт с вложений (download-on-demand).

---

## 6. Открытые вопросы

1. Видео: лимиты email vs P2P-стриминг (решить до M5).
2. Платёжный провайдер для premium-релея (крипта/локальные, карты РФ).
3. Спам в листах объявлений: нужен ли анти-спам (опыт Nostr zaps — платёж как
   фильтр) или достаточно contact-gating (стены видят только контакты).
4. Гранулярность аудитории стены: все контакты / списки / per-post.
5. Синхронизация ленты между устройствами пользователя (multi-device, FUTURE).
