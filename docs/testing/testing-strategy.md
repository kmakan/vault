# Стратегия проверок

Как мы проверяем Vault и ПОЧЕМУ проверки устроены именно так. Документ
обязателен для любой новой фичи: он отвечает на вопрос «чем закрывать
изменение», чтобы решение принималось одинаково, а не «как получится».

## Уровни (от дешёвого к дорогому)

| Уровень | Что проверяет | Где | Скорость |
|---|---|---|---|
| Гейты (статика) | структура и ЗАПРЕЩЁННЫЕ состояния | `scripts/*-gate.mjs` | < 5 c |
| Смоуки модулей | поведение фичи | `scripts/*-smoke.mjs` | ~14 c на все |
| Свойства | инварианты на классах входов | `scripts/property-smoke.mjs` | < 1 c |
| Мутации | «а смоук вообще что-то проверяет?» | `scripts/mutation-gate.mjs` | 13 c |
| Живое устройство | сквозной путь на телефоне | `scripts/device-accept.mjs` | 3-5 мин |

Каждый уровень отвечает на СВОЙ вопрос; вместе они закрывают то, что
остальные не видят.

## Что ловит каждый уровень

### Гейты (статика) — «так нельзя делать»

- `ctx-ratchet-gate` — модули не читают компонент (`ctx` = 0).
- `ctx-coupling-gate` / `ctx-cycles-gate` — нет связности и циклов между
  модулями.
- `js-logic-ratchet-gate` — логика не копится в `App.vue`; потолок можно
  только затягивать.
- `options-dup-gate` — в Options API нет дублей ключей; **и** нет коллизий
  МЕЖДУ блоками (`data ∩ computed` перекрывает компьютед → владелец
  недостижим).
- `feature-import-gate` — фича не импортирует фичу (кроме примитивов и
  владельцев).
- `feature-coverage-gate` — у каждой фичи есть смоук; у каждого смоука — набор
  мутаций. Ратчет: ухудшаться нельзя.

### Смоуки — «этот случай работает»

Один смоук — одна фича; проверяем ЧЕРЕЗ публичный API модуля (как его видит
приложение), а не через внутренности.

### Свойства — «это верно для всех входов»

Примеры ловят «этот случай сломался»; свойство ловит «класс поломок».
Утверждения вида «ответ Rust доезжает дословно», «toggle ∘ toggle =
тождество», «счётчик неотрицателен» — на сотнях детерминированно
сгенерированных входов.

**Правило эталона.** Эталон свойства НЕ ДОЛЖЕН совпадать с реализацией:
иначе свойство не отличает «позвали Rust» от «посчитали сами». Для этого
мок Rust-моста возвращает МАРКЕР, а не ту же формулу (см.
`property-smoke.mjs` → expireAt).

### Мутации — «а тест вообще что-то проверяет?»

Подставляем поломку в модуль и требуем, чтобы смоук покраснел. Мутация, на
которой смоук остался зелёным, — это дырка в проверках, которую не найдёт ни
один обычный тест.

**Наборы лежат в репозитории** (`scripts/mutations/sets/*.mjs`) — не в
/tmp: набор, который никто не видит, завтра потеряется.

**Гейт требует:**
- выжившая мутация (смоук зелёный) — провал;
- мутация, которая НЕ ПРИМЕНИЛАСЬ (строка не найдена) — провал: набор
  устарел, его надо чинить, а не молча пропускать;
- смоук, который ЗАВИС — провал.

### Живое устройство — «это работает у человека»

`scripts/device-accept.mjs` + `docs/testing/device-acceptance.md`. Проверяет
то, чего не видит ни один модульный тест: связность компонента с владельцами,
жизненный цикл, реальные жесты.

## Команды

```bash
npm run build                 # гейты + все смоуки + vite + boot-smoke
npm run quality               # build + мутации + покрытие  (полный запуск)
npm run gate:mutations        # только мутационное тестирование (13 c)
npm run gate:feature-coverage # только покрытие
npm run smoke:<имя>           # один смоук
```

Мутационное тестирование — в CI (`.github/workflows/ci.yml` ✔): 13 секунд
не могут быть причиной «проверки отложим на потом».

## Правила для новой фичи

1. Фича = `src/features/<имя>.js`. Состояние — у владельца (ADR-004), не в
   компоненте. Эффекты — явный `deps`.
2. **Смоук обязателен** (иначе гейт покрытия упадёт). Смоук проверяет
   поведение через публичный API.
3. **Набор мутаций обязателен**: 3-8 ключевых поломок, которые смоук обязан
   поймать. Начните с «что будет, если условие перестанет работать».
4. Свойства — когда есть класс входов (строки, ключи, числа).
5. Проверка на устройстве — если трогаете UI, навигацию или ввод.

## Уроки, оплаченные временем (20.10.2026)

За один день мутационное тестирование вскрыло девять классов слабых
проверок. Каждый из них молча оставлял фичу без настоящей проверки:

1. **Проверка, отложенная от своих данных** — «счётчик сброшен» проверялось
   на значении, которое и так было нулевым.
2. **Проверка-декорация** — `|| true` в конце условия: всегда зелёная.
3. **Незначимое начальное значение** — `picked = null` до проверки
   «пикер закрылся»: и без закрытия проходило.
4. **Стенд, повторяющий НЕ поведение владельца** — `removeById` в стенде
   ЗАМЕНЯЛ массив, а настоящий chat-store делает `splice`; проверка «кэш без
   удалённого» проходила всегда.
5. **Мутация не в той функции** — одинаковая строка в двух модулях: паттерн
   применился не туда.
6. **Эквивалентная мутация** — `allowCreate || allowCreate` не меняет
   поведения; ловить её бессмысленно (убрали, а не «доусилили» смоук).
7. **Эталон == реализация** — свойство с тем же правилом не отличает «позвали
   Rust» от «посчитали сами».
8. **Фича без смоука** — `features/drafts.js` и `features/group-avatars.js`
   прожили без проверок; в `group-avatars.js` из-за этого скрывался живой баг
   (`groupKeyOf(ctx, ...)` — `ReferenceError` глотал catch, и heal-запрос/ответ
   молча не работали).
9. **Мок, который проверял мимо** — `export default globalThis.__CRYPTO__`
   захватывает значение ПРИ ИМПОРТЕ; если мок выставлялся позже, проверки
   шли мимо (фича получала `undefined` и падала в catch).

Каждый пункт — это не «не повторять ошибку», а **гейт**, который ловит
следующий такой случай: мутационный (1-7), покрытия (8), живой мутацией
(9 — проверено негативным тестом: смоук краснеет).

### Вторая волна (20.10.2026, вечер): владельцы состояния

Наборы для владельцев (chat/sending/identity/folders/groups/mailbox/relay/
notes/channels/messages/session/contacts) вскрыли ещё четыре класса:

10. **У владельца нет СВОЕГО смоука — покрытие случайное.** `notes-store.js`
    и `channels-store.js` покрывались лишь ПОПУТНО (смоук фичи дёргал
    `store.add` в своём стенде). Семантика владельца (откат при ошибке
    записи, дедуп по id, ЗАМЕНА постов, обнуление счётчика, полный сброс)
    не проверялась нигде. Лечится гейтом покрытия: смоук владельца —
    отдельный файл, набор мутаций ссылается именно на него.
11. **Мутация, вставляющая no-op, эквивалентна.** `void 0;` В НАЧАЛЕ тела
    метода не ломает код — тело продолжает выполняться. Бить надо по ТЕЛУ:
    `list.push(note)` → `void 0;`, а не `add(email, note) {` → `void 0;`.
12. **«Ключ отсутствует» ≠ «состояние чистое».** Проверка «`getGroupKey('g1')`
    === undefined» проходит и при мутации, оставляющей чужие ключи. Проверять
    ФОРМУ состояния (`Object.keys(map).length === 0`), а не отдельные значения.
13. **Два инварианта в одном сценарии.** `clearUnread` проверялся на счётчике,
    который и так был нулём (после `setUnread('c1', 0)`) → проверка-декорация.
    Перед обнулением нужен НЕНУЛЕВОЙ счётчик.

Проверка-декорация (13) и «нет своего смоука» (10) — самые дорогие: они
прячутся именно там, где состояние считается «очевидным».

### Третья волна (20.10.2026, ночь): бэклог закрыт, 559 мутаций

Добивание бэклога наборов (45 → 0 смоуков без набора) вскрыло ещё четыре
класса — и один из них нашёл НАСТОЯЩУЮ дыру в коде, а не в тесте:

14. **Проверка, которая смотрит не туда.** В `mailbox-api-deps-smoke` стояло
    `check('loadGroups: ctx доехал', groupsSpy.calls.at(-1).ctx === appCtx)` —
    но `at(-1)` брал ПОСЛЕДНИЙ вызов, а после `loadGroups` шёл
    `loadGroupMessages` → проверка фактически смотрела на следующий вызов и
    была зелёной при СЛОМАННОМ `loadGroups`. Лечится снимком индекса:
    `calls[gBefore]`, где `gBefore` — длина массива ДО вызова.
15. **Модуль без своего смоука вовсе — но «покрытый».** Владельцы таймеров
    звонков (`call-clock`, `call-ring`, `call-terminal`, `call-watchdog`,
    `timing`, `call-idle`, `call-resend`) упоминались в смоуке `calls-deps`,
    но ТОЛЬКО как список файлов: ни одна их ветка не проверялась. Написан
    `call-owners-smoke` (46 утверждений): незакрытый интервал держит
    событийный цикл, незакрытый таймер гудка звонит через минуту после отбоя,
    а незатухающие повторы ретрансляции — это инцидент 12.10 (лавина писем).
16. **Проверка-декорация через `at(-1)` и через ЗНАЧЕНИЕ ДО.** Своё письмо
    отбрасывалось «по отсутствию ключа пира», а не по сравнению с `myEmail` —
    сценарий был зелёным и при сломанном сравнении. Для «своё письмо» нужен
    ключ СВОЕГО адреса, иначе тест проходит по чужой ветке.
17. **Эквивалентность по СПЕЦИФИКАЦИИ, а не по коду.** `atob` (WHATWG
    forgiving-base64) терпит пробелы и отсутствие пэйдинга → мутации
    «вырезать `.replace(/\s+/g,'')`» и «не восстанавливать `=`» ЭКВИВАЛЕНТНЫ
    и убраны из набора (ловить их бессмысленно — врать о покрытии).

Отдельно: **договор wire-формата был неполон.** В фикстуре
`m0-wire-contract.json` не было кейса «`text` есть, метки `vault:1` нет» —
при мутации «метка не проверяется» JS-сторона принимала такой JSON за
конверт, и гейт паритета этого не видел. Кейс добавлен в ОБЩУЮ фикстуру
(её читает и Rust-тест) → паритет теперь проверяет и этот случай.

### Итог третьей волны

- 87 наборов мутаций, **559 мутаций, все пойманы**, 102 с на полный прогон;
- **0 фич без смоука, 0 смоуков без набора мутаций** (ратчет покрытия пуст);
- `boot-smoke` (гейт рендера СОБРАННОГО приложения) исключён из требования
  «у смоука есть набор» с причиной: мутация в исходнике видна только после
  `vite build` — мутационная проверка бандла остаётся отдельной задачей;
- новый смоук `call-owners-smoke` (владельцы таймеров) — 46 утверждений.

**Правило, которое стоит запомнить:** мутационный гейт полезен ровно настолько,
насколько честно сделаны мутации. Мутaция должна ЗАМЕНЯТЬ решение, а не
вставлять рядом `void 0;`; эквивалентные мутации — убирать, а не «доусиливать»
смоук под них; выжившая мутация — это не «не поймали», а «смоук ничего не
проверяет».

### Четвёртая волна (20.10.2026, ночь): RUST-ядро и гигиена текста

Мутационный гейт закрыл JS-сторону, но **Rust-ядро — то, куда W4 переносит
решения о протоколе — проверялось ТОЛЬКО обычными тестами**. Обычный тест не
отвечает на вопрос «а он вообще что-то проверяет?». Построен гейт
`scripts/rust-mutation-gate.mjs` (36 мутаций в 4 наборах: ephemeral, incoming,
filter, messages, crypto) и он сразу нашёл **три настоящих пробела**:

18. **Тест на переполнение не переполнял.** Проверка «огромный TTL
    насыщается, а не переливается» брала `i64::MAX / 1000` — а это значение
    при умножении на 1000 ВМЕЩАЕТСЯ в `i64`, то есть переполнения не было и
    тест был зелёным и при обычном перемножении без насыщения. Мутация
    «снять `saturating_mul`» оставалась зелёной — то есть тест проверял не
    то, что заявлял.
19. **Формат fingerprint не проверялся.** Релей-сервер сверяет fp издателя с
    fp, привязанным к read-токену; несовпадение = 403 «token bound to another
    account» для того же ключа. Тест проверял «есть двоеточие и звёздочки» —
    на этом зелёном держалась поломка «взяли 4 байта вместо 8» и «склеили
    без разделителей».
20. **Длина ключа голоса не проверялась.** Тест на плохой ключ брал `"zz"` —
    это не hex, он не декодируется ВООБЩЕ, и проверка длины (строго 32 байта)
    не выполнялась. Плюс не проверялось, что ключ зависит от `info`.

Добавлены также: тест «`store_incoming` сообщает о дубле» (иначе уведомление о
новом письме приходило бы на каждую переотправку), тест на пустое имя в
заголовке и кейс в общей wire-фикстуре «`type` НЕ `call_*` + `call_id` → всё
равно сообщение» (его не было — а именно этот случай ловит мутацию «call по
наличию `call_id`»).

Отдельно: **гигиена текста.** Иероглифы в русском тексте появлялись пять раз
за сессию (в коммите, в модуле, в журнале, в смоуке, в черновике) — разовый
прогон по репозиторию делался и не помогал. Теперь это гейт
`scripts/hygiene-gate.mjs` (+ шаг в CI): ищет CJK/кана/хангыль и битые байты
(U+FFFD) вне `src/locales/zh.js` и вне строки `language_zh` (название языка в
выпадающем списке — там китайский законен).

### Пятая волна (20.10.2026, ночь): РАТЧЕТ ПЛОТНОСТИ МУТАЦИЙ — дыры стали видны

Мутационный гейт отвечает на вопрос «а тест что-то проверяет?» — но только
для модулей, для которых наборы УЖЕ написаны. Про остальные гейт молчит: у
модуля может быть смоук с тремя проверками на 900 строк, и это формально
«покрыто». Оказалось: **49 модулей (≈19,7 тыс. строк) без единой мутации** —
слепые зоны, о которых не знал никто.

Построен `scripts/mutation-density-gate.mjs` — ратчет по образцу покрытия:
- у каждого модуля длиннее ~40 строк (кроме исключений С ПРИЧИНОЙ) есть хотя бы
  одна мутация;
- список модулей без мутаций лежит в baseline и может только СОКРАЩАТЬСЯ
  (закрытая дыра из списка уходит; новый модуль без набора — регресс, гейт
  падает);
- счётчики мутаций по модулям уменьшаться не могут.

Текущее состояние: **135 модулей под ратчетом, 639 мутаций, 43 дыры** (было
49). Бэклог виден в отчёте (`--report`) и не может вырасти.

Наборы на группы и контакты ядра (42 мутации в 5 наборах Rust) дали ещё три
настоящих пробела:

21. **Правило повышения роли не проверялось.** Legacy-роль `Moderator` при
    повышении обязана становиться обычным участником, а не админом — иначе
    участник, которому раньше дали «среднюю» роль, молча получил бы права
    администратора группы.
22. **Флаг «ключ у участника» не проверялся.** Новый участник не может
    иметь общий ключ группы (ключ он получит отдельным сообщением) — по флагу
    приложение решает, можно ли шифровать ему.
23. **Мутация не в той функции.** Строка `key_shared: false` встречается в
    трёх местах (создание группы, добавление участника, импорт) — без
    контекста мутация била по создателю, а проверяла добавленного. Лечится
    указанием полного контекста в паттерне.

### Шестая волна (20.10.2026): дыры плотности — 43 → 34

Закрыты 9 модулей из списка «без единой мутации». Четыре из них не были
покрыты смоуком вообще — написаны новые (`provider-limits-smoke` 28,
`mail-providers-smoke` 27, `bounce-smoke` 22, `identity-smoke` 17). Остальные
получили наборы мутаций.

Найденные и закрытые пробелы (все — в ПРОТОКОЛЬНЫХ местах):

24. **Квитанции не различали «доставлено» и «прочитано»** — тест знал только
    про «прочитано»; разбор тела квитанции принимал письмо без `message_id` и
    без отправителя (чужая квитанция помечала бы сообщение прочитанным).
25. **Отключение проверки подписи оставалось зелёным**: тест на подделку
    принимал ЛЮБУЮ ошибку — «отвергли по подписи» и «отвергли по AEAD-тегу»
    неразличимы. Обрезанный конверт не проверялся вовсе.
26. **Заголовки конверта не проверялись**: `X-Vault-From`/`X-Vault-ID` можно
    было бы писать пустыми, и получатель не узнал бы, кто прислал и по чему
    дедуплицировать. Конверт БЕЗ payload принимался как валидный.
27. **«Запомнить меня» не проверялось**: при `remember: false` учётные данные
    всё равно могли сохраниться на диск.
28. **commit входа без сессии в памяти проходил тихо** — «успех» без
    durable-состояния.

29. **Дубль реакции заново отправлял уведомление.** `ReactionStore::add_reaction`
    по своему же докову возвращает `Ok(false)` для «уже есть», а возвращал
    `Ok(true)` всегда. Вызывающий (CLI) по `Ok(true)` не только печатает
    «Reacted …», но и **отправляет письмо-уведомление** — то есть повтор той
    же реакции приводил к повторной отправке. Исправлено по докову (считаем
    «до/после», как в `remove_reaction`).
30. **Правило эмодзи было продублировано в двух структурах** (`StoredReaction`
    и `ReactionStore`) — правка одной копии оставляла вторую со старым
    поведением. Схлопнуто в один источник.

Два урока про сами мутации (важнее находок):

* **Мутация должна быть ВАЛИДНОЙ.** `void 0;` вместо операции компилятор
  отвергает — это не пробел в тестах, а опечатка в наборе. Такие мутации
  переписаны в валидные (нулевые ключи, пустые заголовки).
* **Мутация должна быть ЗНАЧИМОЙ.** Обрезка ключа канала в JS дублирует
  обрезку в Rust → эквивалентна → убрана. Проверка длины payload в
  конверте недостижима (подпись проверяется раньше) → убрана.

### Восьмая волна (22.10.2026, ночь): граница «фича ↔ композиционный корень»

Приёмка 0.1.256 прошла 19/19 CDP-проб — а сообщение всё равно исчезало. Потом
тот же чат показал 17 «пустых пузырей». Ни один уровень проверок не ловил ни
того, ни другого, потому что оба дефекта живут НА ГРАНИЦЕ, а не внутри модуля:

35. **Объект-владелец передаётся фиче, и фича читает поле мимо `.state`.**
    `saveCurrentHistory(email, chatKey, chat)` читал `chat.messages`, у
    владельца переписки такого поля нет (`chat.state.messages`) — значит в
    архив всегда уходил пустой список, «успешно». Локальная история не
    наполнялась НИКОГДА, и это не видели ни смоуки (собирали самописный
    `{messages: [...]}` «по форме»), ни мутации (ломать было нечего).
36. **Замыкание зависимости принимает меньше аргументов, чем ему передают.**
    `{ setPendingOutgoing: v => this.setPendingOutgoing(chatKey, v) }` при
    вызове фичей `setPendingOutgoing(chatKey, msg)`: в метод попало
    `(chatKey, chatKey)`. Бакет pending стал СТРОКОЙ, `Object.assign` по строке
    рассыпает её по символам, `Object.keys` такой бакет считает непустым, и
    поллинг подмешал 17 символов в чат вместо переписки. Тихо, без единого
    исключения — ровно тот класс «правка фичи ломает приложение».

Что добавлено в барьер:

* **`owner-contract-gate`** — три правила на одной границе: (а) поле владельца,
  прочитанное мимо `.state` или отсутствующий член; (б) параметр замыкания
  обязан стоять на СВОЁМ месте в вызове (`(k, m) => this.f(k, m)`); (в) арность
  замыкания обязана совпадать с числом переданных фичей аргументов. Сдвиг
  параметра вправо допускается только если освободившиеся места заняты литералом
  или контекстом (`console.log('текст', e)`, `F.f(this.deps, force)`), и
  нарушается, если спереди встало простое имя переменной из объёма корня —
  это и есть потерянный аргумент. Гейт привязан к ФАЙЛУ владельца (имена
  фабрик повторяются) и имеет слепую самопроверку: не нашёл ни одного
  владельца — падение, а не «зелёно».
* **Урок внутри урока — ослеплённый хелпер гейта.** `splitArgs` прилипал
  открывающую скобку к первому аргументу (`f(this.chat)` читалось как
  `(this.chat`), поэтому ПЕРВЫЙ аргумент каждого проверяемого вызова не
  проверялся вообще. Самопроверка гейта это не поймала: её примеры начинались
  со второго-третьего аргумента. Самопроверка обязана включать ПЕРВЫЙ
  аргумент вызова — иначе слепой гейт выглядит как работающий.
* **Защита во владельце, а не в семи вызывающих.** `sending-store` теперь не
  принимает не-запись ни в `setPendingOutgoing`, ни в `mergePendingOutgoing`
  (warn + состояние не трогается), а `mergePending` игнорирует бакет не-объект.
  Три новых мутации (две в `sending-store-mut`, одна в `history-mut`) это
  проверяют; смоук `sending-store-smoke` — пункты 17.
* **Правило арности меряет ОБА конца отношения и оба стиля инъекции.** Замыкание
  обязано принимать РОВНО столько аргументов, сколько ему передаёт фича: недобор
  = потерянный аргумент (22.10), перебор = параметр, который никогда не получает
  значения. Считается СТРОГО внутри тела функции-приёмника и по алиасу
  деструктуризации: поиск по всему модулю дал пять ложных срабатываний —
  декларация `export function dep(a, b, c)` считалась вызовом на три аргумента,
  а имя `loadHistory` в модуле значит одновременно и инжектированную
  зависимость, и импорт адаптера из другой функции. Направление «никогда не
  получает» наоборот меряется по МОДУЛЮ: у общей зависимости много вызывающих, и
  если хоть один передаёт аргумент — параметр жив (`startPolling`: `changeEmail`
  зовёт без интервала, логин — с 60000). Покрываются оба способа инъекции
  корня — литерал прямо в вызове и `Фича.fn(this.<deps>-геттер)`; второй способ
  даёт 206 из 220 границ, без него гейт молчал бы почти на всём.
* **Что правило нашло в первый же прогон** (кроме уже починенного
  `setPendingOutgoing`): `dropBucket: () => this.dropBucket(chatKey)` при вызове
  фичей `dropBucket(chatKey)` — аргумент упирался в стену, а значение совпадало
  только потому, что замыкание захватило ту же переменную; и
  `broadcastGroupMeta: (groupId, payload) => …(groupId, payload, { groupKeys:
  this.groupKeys, … })`, где фича передавала контекст ТРЕТЬИМ аргументом, а корень
  подставлял вместо него свой (совпадавший по случайности). Оба заменены на

* **Инструмент приёмки меряет сам симптом.** `phone-persist-check.mjs` проверяет
  метку в трёх точках (сразу / после переключения чата / после живого поллинга)

  KDF эскроу-архива проверялся только парой wrap→unwrap в одной версии: оба
  конца считают одинаково, поэтому дрейф вывода (итерации, passphrase,
  доменная привязка, счётчик блока) остаётся незамеченным, а уже созданные на
  устройстве архивы перестают открываться. KAT на канонической мнемонике
  (`abandon … about`) фиксирует seed и KEK. При его написании выяснилось, что
  PBKDF2-HMAC-SHA512 в мосте писал блок-счётчик 8 байтами (`usize`), а не 4
  (INT(i) по RFC 8018): учебный эталон и фактический архив расходятся. Это не
  баг, который можно молча исправить, — архивы уже созданы этим кодом, и
  «починка» сделала бы их неоткрываемыми. Поэтому вектор закрепляет
  ФАКТИЧЕСКОЕ значение, отклонение задокументировано в коде, а мутация
  «исправить на 4 байта» обязана ловиться: это регресс совместимости.

  солью), тестов ядра 453 (+31).

  `now`: на границе окна разница в 1 мс меняла ответ. Лечение — строить метку
  от ТОГО ЖЕ `now`, что получает предикат. Проверка: 80 прогонов подряд без
  единого падения. Правило: если тест зависит от часов, часы должны быть
  параметром, и все входы теста обязаны считаться от одного захваченного
  значения.
* **Домен KDF — протокол, а не константа (23.10, партия 5c, `t_a2da57c0`).**
  Гибрид PQ-V1 проверялся только round-trip'ом: соль, `info`, порядок ног

### Десятая волна (24.10.2026): «медиа есть» ≠ «кадры идут» — живой тест захвата отдельно от звонка

### Одиннадцатая волна (24.10.2026, вечер): мутационный гейт — процесс, который ПИШЕТ в дерево

### Двенадцатая волна (24.10.2026, ночь): hardened-страж без своей меры — это необнаруженный дефект

* **Усиление правила надо мерить в том крейте, где оно живёт.** SELF-KEY GUARD

  `identity::same_public_key`, чтобы ключ `"ABCD1234"` больше не проходил стража.
  Тест на это был — но в мосте (`src-tauri`), а `rust-key-store` гоняет
  `cargo test -p vault-core --lib`: выключенный страж и сравнение строкой
  не поймал бы НИ ОДИН прогон. Мера появилась только после того, как в ядро
  добавлен `add_peer_rejects_own_pubkey` с перечислением написаний ключа.
  Проверка «тест есть» без проверки «тест в нужном крейте» — иллюзия.
* **Ветка предиката без отдельного утверждения не покрыта, даже если предикат
  «полностью протестирован».** `peer_is_self` = адрес ∪ ключ. Тест проверял
  случай «наш адрес + наш ключ» — снятие любой из двух веток давало зелёный
  прогон. Понадобилось утверждение «наш ключ под ЧУЖИМ адресом — всё равно мы»
  (peer-store общий на машину), и только оно умерло от мутации «предикат забыл
  про ключ».

### Тринадцатая волна (24.10.2026, день): правило в ядре без живой проводки — это не фича

### Четырнадцатая волна (24.10.2026, вечер): один код ответа — два разных решения

* **Правило «на сервере» ничего не значит, пока порог не измерен.** Требование
  владельца (100 конвертов/сутки) формально выполнялось и раньше: `relay_pub`
  брал `VAULT_RELAY_FREE_DAILY_LIMIT` и `unwrap_or(100)`. Но строка внутри
  `main()` не измерялась ничем: опечатка в имени переменной, «0» вместо ста,
  мусор вместо числа — всё это молча открывало бы релей без лимита. Порог
  вынесен в `DEFAULT_FREE_DAILY_LIMIT` + чистую `daily_limit_from_env`, и
  теперь «мусор = дефолт, а не ноль» и «ноль = сознательный выключатель»
  проверяются тестом и мутацией.
* **Ветка, которая не срабатывает ни в одном прогоне, не покрыта, сколько бы
  тестов ни было.** Счётчик суточного лимита жил прямо в обработчике, и его
  ветка смены суток (`entry.0 != day`) не выполняется НИ В ОДНОМ тесте: прогон
  живёт внутри одной секунды. Снятый сброс дал бы зелёный прогон — лимит
  стал бы пожизненным для каждого, кто дожил до полуночи. Вылечено не
  «ожиданием полуночи», а параметром: `tally_daily(map, publisher, day, limit,
  now)` — чистая функция, сутки подставляются фикстурой.
* **Одинаковый HTTP-код ≠ одинаковое решение, и симметричные ветки требуют
  симметричных утверждений.** Сервер отдаёт 429 и за суточную квоту
  (`daily relay limit reached`), и за вспышку 10 rps (`rate limit`). Клиент
  различал их односторонне: любой 429 писал в kv «лимит дня», а значит пачка
  сигналов звонка (setup + ICE-кандидаты) глушила ускорение до полуночи UTC.
  Пока смоук проверял только «лимит записан», мутация «любой 429 = лимит»
  жила зелёной; нужно второе утверждение — «вспышку НЕ записали и следующая
  публикация всё-таки ушла на сервер».
* **Живой прогон нашёл то, что не видели 58 юнит-тестов релея.** Первый же
  сценарий «104 публикации через реальный HTTP» дал 16 принятых и 87 отказов —
  это был burst-лимит, а не суточный: тест, который не различает два вида 429,
  проверяет не то. Порог удалось подтвердить честно только с паузами:
  100 принятых, 101-й — `429 daily relay limit reached`, `retry-after`
  совпадает с телом и кратно полуночи UTC, `limit_hit` растёт, в очереди ровно
  100 конвертов.
* **Правило, продублированное во втором клиенте, — тот же дефект, что копия в
  JS.** CLI (`vault-client/src/vault/relay.rs`) имел свою ветку `429 =>
  limit_day = Some(today)`; починить только десктоп значило оставить
  «телефон/десктоп ведут себя иначе, а CLI нет». Теперь классификация одна —
  `vault_core::relay::pub_rejection`, её зовут и фронт (через команду моста), и
  CLI.
* **Fail-open обязан быть направлен в дешёвую сторону.** Не распознанный 429
  (чужой релей, битое тело, старая сборка моста без команды) трактуется как
  вспышка: ошибка стоит одного лишнего запроса, который сервер всё равно
  отвергнет. Обратная ошибка стоила бы сутки без ускорения у живого
  пользователя. Это зафиксировано тестом, а не комментарием.
* **Неприменившаяся мутация — снятая проверка, и она не меняет цвет гейта.**
  Полный прогон дал `477/489`, и часть недобора — не выжившие мутанты, а
  паттерны, которых в файле уже нет: `cargo fmt` разбил однострочные ветки
  `Plan { … }` и `if enabled { "1" } else { "0" }` на несколько строк, после
  чего 5 мутаций `rust-settings`/`rust-transport` перестали применяться.
  Набор выглядел «почти зелёным», потому что runner печатает их отдельным
  списком, а итоговая строка считает только пойманные. Паттерн мутации —
  контракт с форматированием: после `cargo fmt` и после любой правки
  мутируемого региона наборы прогоняются целиком, а сломанный паттерн чинится,
  а не выбрасывается (`44cca04` → `rust-settings` 9/9, `rust-transport` 11/11).
* **Сломанная проверка выглядит как прошедшая — и её никто не собирает.**
  Правка пробы `flags` оставила в `scripts/device-accept.mjs` незакрытый
  литерал: файл не разбирался, приёмка на телефоне падала на `SyntaxError`, а
  все гейты перед этим были зелёные, потому что ни vite, ни cargo, ни `cargo
  test` этот скрипт не читают. Добавлен `gate:parse` (`node --check` по всем
  `.mjs` в `scripts/` — 353 файла, ~8 сек), он первым в `npm run quality` и в
  CI: проверочный инструмент теперь тоже под проверкой.

  что переносить нельзя (`is_global`: `''`/`anon`/`local`). 9 мутаций → 9/9.
  Дыра была в измеримости, а не в покрытии: 13 тестов `storage/sqlite.rs`
  эти строки уже закрывали.
* **Правило, которое из этого следует.** Класс повторился второй день подряд:
  24.10 паттерны оборвал `cargo fmt`, 25.10 — переезд решения между функциями.
  Запись «паттерн — контракт с форматированием, после правки мутируемого
  региона прогонять наборы целиком» была в журнале, но не мешала ничего:
  долгий прогон никто не повторяет лишний раз, а `--set` одного модуля не
  показывает, что набор потерял половину проверок. Поэтому правило стало
  инструментом: `--check-patterns` в ОБОИХ мутационных гейтах (JS и Rust) —
  проверка «каждый паттерн до сих пор находится в своём файле» без cargo и без
  смоуков, секунды на все 1496 мутаций (983 JS + 513 Rust). Вызывается одной
  командой `npm run gate:mutation-patterns`, стоит вторым шагом в `quality`
  (сразу после `gate:parse`) и отдельным шагом в CI — перед долгими
  мутационными прогонами, чтобы класс был виден немедленно. Режим отказывается
  работать при непустом дисковом журнале: значит в дереве лежит мутант, и
  сверять паттерны по нему нельзя. Заодно он печатает паттерны, которые
  встречаются в файле больше одного раза, — мутация сядет на ПЕРВОЕ совпадение,
  и это другой риск того же класса: проверка может бить не по тому решению.
  Отличать надо и текст отказа: «мутация выжила» = дыра в тестах, «паттерн не
  найден» = дыра в инструменте — чинят разное.

### Восемнадцатая волна (25.10, вечер): путь денег по байтам и третья копия правила чтения тела

* **Расхождение ядро↔мост в правиле чтения тела.** Ядро восстанавливало
  хвостовой padding только на выходе QP-декодера, мост — всегда: письмо,
  пришедшее с обрезанным `=`, читалось на телефоне и не читалось в CLI. Закрыто
  `b5f99bb` — и, что важнее для стратегии, ЗаМЕРЕНО: набор `crypto` +4 мутации
  (14/14), unit-проба на инвариант «длина кратна 4», integration-проба
  `tests/qp_transport.rs` на фолд + снятый padding.
* **Релей: путь денег и троттлинга размечен мутациями впервые.** `tokens` 26/26
  (после выжившей мутации «v2: scope вне MAC» добавлена проба на подмену байта
  8 read→write), `payments` 22/22 (таблица цен, копейки, `capture`, идемпотентность,
  карта HTTP-кодов и статусов провайдера), `persist` 24/24 (64 символа ≠ hex
  выбрасывается при загрузке, файл состояния 0600), новые наборы `rate` 9/9 и
  `store` 9/9. Из семи названных дыр волны 17 закрыто пять; остались
  `channel_keys.rs` и `fcm.rs`.
* **Выжившая мутация оказалась не «нет теста», а «тест меряет соседнюю функцию».**
  «TTL не фильтруется в drain» выжила на зелёном тесте `expired_are_dropped_by_every_read_path`:
  `retain` у peek и drain удаляет просрочку ИЗ ОБЩЕЙ очереди, поэтому drain
  проверялся уже на вычищенном peek'ом. Правило: функции-читатели с побочным
  эффектом меряются раздельно — каждой свой ключ очереди. Тот же класс, что
  «мутация не в той функции» из волны 20.10, только побочный эффект прячет след.
* **«Поймано компилятором» — это не покрытие.** Мутация «peek изымает конверты»
  в варианте `.drain(..)` не компилировалась и засчитывалась пойманной, хотя
  проверяемая свойствами она ничего не проверяла. Заменена наблюдаемой (собрать
  и очистить) + assert второго peek — 9/9 без «поимок компилятором».
* **Гейт по крейту с незакоммиченными правками врёт два раза.** Пока цепочка
  шла, в `vault-relay` была добавлена проба, которая не была проверена
  компилятором, — baseline набора `persist` упал, и набор отчитался 0/24 как
  дырявый. Отсюда порядок: перед запуском набора — `cargo test -p <крейт> --lib`
  зелёный и дерево в этом крейте чистое; сломанный baseline выглядит как дыра в
  тесте, и это разные диагнозы.
* **Третья копия правила чтения тела (JS) измерена, и измерение отделило
  нагрузочное от страховки.** Новый набор `urlsafe-body` — 10/10: перевод
  алфавита `-`/`_` (atob бросает на обоих), точное число доклеенных `=`
  (недобор терпится, перебор — нет), UTF-8-раундtrip кириллицы (без него

  роняет весь скан». Срез пробелов и починка padding в JS оказались
  эквивалентными мутантами: `atob` по WHATWG «forgiving-base64» сам выкидывает
  ASCII-пробелы и терпит недобор `=` (замер 25.10), поэтому в набор они не
  включены — комментарий в `api.js` утверждал обратное и поправлен.
* **Разделка амбивалентных паттернов (Rust) закрыта: 8 → 0.** `protocol`

## Чего проверки НЕ делают

- Не заменяют живую приёмку: статика не знает про Android WebView, про
  long-press с `clientX/Y = 0`, про то, что `computed` без реактивных
  зависимостей кэшируется навсегда.
- Не ловят «фича есть, но ею никто не пользуется» — для этого нужен
  сценарий пользователя, а не тест.
- Не дают права ослаблять потолки: ратчеты только затягиваются.
- Не знают целостности рабочего дерева: зелёный прогон мутационного гейта
  ничего не говорит о правках, внесённых в те же файлы во время него (24.10 —
  одиннадцатая волна). Обратный случай дороже: незакоммиченная и не
  скомпилированная правка в том же крейте валит baseline, и красный прогон
  выглядит как дыра в наборе мутаций (25.10 — восемнадцатая, `persist` 0/24 при
  исправном наборе).
