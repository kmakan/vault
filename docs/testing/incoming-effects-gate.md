# Гейт эффектов входящих (`smoke:incoming-effects`)

`vault-desktop/scripts/incoming-smoke.mjs` — входит в `npm run build`
(сразу после `smoke:incoming`).

## Зачем

`smoke:incoming` (маршрутизация) отвечает на вопрос «какой `kind` от Rust →
какой эффект». Этот гейт отвечает на вопрос «что происходит ПОСЛЕ
маршрутизации» — там, где маршрутизация ничего не решает, а только считает,
дедуплицирует и уведомляет.

Этот слой стоит отдельно: почти все его инварианты — **отрицательные**
(«не должно»), и ломаются молча. Письмо, посчитанное дважды, или push,
съеденный тихим поллингом, или heartbeat, доехавший до чата сырым JSON, —
всё это «работает» и выглядит как «просто странный счётчик».

## Разделение с `smoke:incoming`

| | `smoke:incoming` (маршрутизация) | `smoke:incoming-effects` (эффекты) |
|---|---|---|
| Rust-классификатор | замокан на `kind` | замокан на `kind` |
| что проверяется | `kind` → эффект | дедуп, уведомления, свежесть, mute/visible, баунс, пул, порядок батча, ренейм, группа |
| сколько утверждений | 16 | 40 |

## Что проверяется (40 утверждений)

| Слой | Инвариант |
|---|---|
| no-op | пустой батч, своё письмо, не-Vault тело — ничего не происходит |
| ignore-лист | проверка ДО расшифровки и ДО дедупа: письмо остаётся «необработанным» (после разблокировки всплывёт) |
| дедуп | три ключа: `uid|folder`, `mid:Message-ID`, `env:envId` (кросс-канальный: relay-копия + email-копия одного конверта — один бейдж) |
| уведомление | отделено от дедупа счётчика: тихий поллинг не съедает push монитора (регресс `2fa9103`) |
| свежесть | старше окна (15 мин) — бейдж растёт, уведомления нет |
| mute / видимый чат | бейдж есть, уведомления нет |
| группа | `chatKey = group:<id>`, `title` = имя группы |
| смена почты | полный ренейм: перенос истории с картой алиасов, переименование в группах, привязка ключа, чистка старого адреса, счёт по новому адресу |
| эхо | письмо с моим ключом — помечено обработанным, но не сообщение |
| пул | за прогон обрабатывается не больше 50 писем |
| порядок батча | ХРОНОЛОГИЯ, а не «как вернул IMAP»: `call_cancel` (UID больше) разбирается ПОСЛЕ `call_request` (иначе звонок гаснет без рингтона, `t_674c770f`); UID сравнивается ЧИСЛОМ (`9` < `10`) |
| баунс (DSN) | `onMailBounce` вызван с получателем и причиной; письмо — не сообщение |
| баунс по теме | тема ловит, даже когда `From` — другой демон |
| звонок под новым адресом | сигнал уходит под ИЗВЕСТНЫЙ адрес пира, а не под `fp:<…>` (регресс `25dd18a`) |
| мост упал | письмо не считается, в дедуп не пишется (повторится), ошибка громкая; классификатор позван ровно один раз — письмо не пошло дальше по путям |

## Мутационная проверка (обязательна)

Правило журнала (17.10): «зелёный смоук не равен «путь исполняется»», и
«мутационная проверка самого теста обязательна, иначе тест декоративен».

Гейт проверен на 12 подставленных поломках роутера — все краснеют:

| Мутация | Провалов |
|---|---|
| уведомление без гейтов (`notify && …`) | 3 |
| дедуп счётчика отключён (`counted = true`) | 3 |
| окно свежести отключено | 1 |
| UID сравнивается строкой | 1 |
| ветка баунса (DSN) удалена | 4 |
| пул не усекается (`MAX_POOL` 50 → 1000) | 1 |
| `muted` игнорируется | 1 |
| видимый чат игнорируется | 1 |
| перенос истории при ренейме не вызывается | 1 |
| ignore-лист не проверяется | 1 |
| эхо-защита отключена | 1 |
| отказ моста выглядит как «не наше» (`undefined` → `null`) | 1 |

Три первых прогона были красными не из-за роутера, а из-за СЛАБЫХ кейсов
смоука — и это тоже результат: кейс ignore-листа без ключа пира проходил бы
и при сломанном ignore-листе, а кейс «мост упал» не отличал `null` от
`undefined`. Оба кейса переписаны (в первом теперь ЕСТЬ ключ пира, во втором
считаются вызовы классификатора).

## Как воспроизвести мутационную проверку

```bash
# один дефект → один красный прогон, потом откат
cp src/features/incoming.js /tmp/incoming.js.bak
python3 - <<'EOF'
p='src/features/incoming.js'; s=open(p).read()
open(p,'w').write(s.replace('const MAX_POOL = 50;', 'const MAX_POOL = 1000;', 1))
EOF
node scripts/incoming-smoke.mjs      # красный
cp /tmp/incoming.js.bak src/features/incoming.js
```

## Чего гейт не проверяет

- Реальный Tauri-мост и сам `vault_classify_incoming` — это Rust (`cargo test`)
  и общая фикстура паритета (`smoke:m0-wire`).
- Семантику эффектов (что именно делает `handleCallSignal`, `onMailBounce`) —
  у них свои смоуки.
- Тексты уведомлений и UI.

## История: как файл умер и ожил

Смоук был написан до W1 (19.10) под старый API роутера: `processIncoming(ctx,
…, deps)` (четыре аргумента), решение типа в JS, состояние из компонента.
W1 перенёс решение в Rust и перевёл модуль на явный контракт `deps` — и смоук
мгновенно сломался: `@tauri-apps/api/core` в копии остался настоящим, и копия
падала при загрузке с `ERR_MODULE_NOT_FOUND`.

Поломку никто не видел: смоук **не был подключён к сборке**, а `import-gate`
проверял моки ФАЙЛОВО (`body.includes(spec)`) — '@tauri-apps/api/core' был
замотан для копии `channels.js`, и этого хватало, чтобы гейт пропустил
копию `incoming.js` с незамотанным импортом.

Обе дырки закрыты:

1. `import-gate` проверяет моки **покопийно** (карта моков разбирается из
   вызова `prepareModuleCopy`; `extra`-замены учитываются отдельно);
2. сам хелпер `prepareModuleCopy` **не создаёт** копию с нерезолвящимся
   статическим импортом — падает сразу, называя и спецификатор, и модуль.

Динамические импорты проверкой не ловятся намеренно: `try { await
import('@tauri-apps/plugin-http') } catch { /* фолбэк на window.fetch */ }` —
законный способ подключить опциональный плагин (`relay-client.js`).
